# InventoryAccountment — складской учёт

MVP одного склада: единицы измерения, материалы, поставщики, поступления, синхронное проведение, история статусов и отчёт по поставкам с CSV. Backend — FastAPI, SQLAlchemy и PostgreSQL; Frontend — React/TypeScript и Vite. RabbitMQ, outbox и фоновые обработчики в согласованный MVP не входят.

## Текущее состояние

Сверено с исходниками ревизии 9701e9d. API поддерживает многопозиционные черновики, PATCH, удаление, переход draft → posted и безопасный повтор проведения. История хранится в PostgreSQL; отчёт включает только posted, количества передаются десятичными строками.

В браузере работают вход, профиль, справочники, список/создание/удаление/проведение поступлений, просмотр истории и отчёт/CSV. Форма поступления пока создаёт одну строку; редактирование сохранённого черновика и остальные фильтры списка доступны через API, но не реализованы в UI. Администрирование показывает health-проверки; API управления пользователями, backup и мониторингом отсутствуют.

Последние результаты и ограничения проверок — в [TEST_DEFECTS.md](TEST_DEFECTS.md).
Полный make verify, успешный CI и человеческая приёмка подтверждаются
отдельно для актуальной ревизии; наличие тестов не означает выпуск.

## Запуск всего приложения в Docker

PostgreSQL, миграции, API и Frontend работают в одном Compose-проекте.
Внешняя БД не нужна. Создаётся новая пустая БД, старые данные не переносятся.
Проект по умолчанию inventory-compose использует отдельный том inventory_data;
тома прежних вариантов запуска не переиспользуются автоматически.

На Windows (только Docker Desktop и PowerShell), из корня:

```powershell
docker compose up -d --build --wait
```

На Linux с GNU Make:

```bash
read -r -s -p 'Путь к env-файлу (вставьте его после приглашения): ' ENV_FILE; printf '\n'
```

После запуска вставьте путь к файлу и нажмите Enter. Путь вводится после
приглашения, не в кавычках команды. Затем задайте переменную и запустите:

```bash
export ENV_FILE
make setup
make run
```

Подробности и проверка доступности файла — в [руководстве](GUIDE.md#внешний-файл-настроек).

Откройте http://localhost:5180 и создайте первого администратора.
Swagger: http://localhost:8010/docs. Настройки необязательны: для изменения
портов/пароля используйте внешний файл через ENV_FILE или локальный .env
по .env.example. PostgreSQL не публикует порт.
Реквизиты по умолчанию учебные; публичный production требует отдельной настройки.

API и миграции работают от app, Frontend — от node. При остановке API
завершает активные запросы в пределах 30 секунд и освобождает пул БД;
Compose даёт ему 45 секунд до принудительного завершения.
Данные PostgreSQL находятся в именованном томе и сохраняются при пересоздании
контейнеров и обновлении совместимых образов с тем же именем Compose-проекта.
Подробнее: [жизненный цикл контейнеров](GUIDE.md#пользователи-остановка-и-сохранность-данных).

Миграции Alembic применяются автоматически до запуска API.
make down или docker compose down сохраняют данные. Для обновления кода
остановите приложение, пересоберите образы и запустите снова.
[Краткая инструкция Windows](docs/DOCKER_WINDOWS.md).

## Make-команды и проверки

Флаг DOCKER удалён: все команды контейнерные. run/up/status/down/migrate,
backup/restore работают с приложением; test/quality/verify/migration-check,
mutation/backup-restore-check используют отдельный тестовый Compose-проект.
make test-clean очищает только тестовые ресурсы. make verify не запускает
рабочее приложение после завершения. Полный перечень: [GUIDE.md](GUIDE.md).

Обязательная проверка — make verify. Она включает lock-check, качество,
тесты с покрытием 80%, mutation, миграции, backup/restore, smoke, сканирование
реального image ID и проверки Git. Frontend coverage-порог пока не настроен.
CI запускает те же команды и сохраняет reports/ при отказе и успехе.
Успешный CI, релиз и человеческая приёмка не следуют из наличия конфигурации.

Для Windows без GNU Make остаётся [Linux test-образ](docs/UNIX_TESTS.md).
Он проверяет тесты и миграции, но не заменяет весь verify.

## Разработка и приёмка

Обязательная цепочка: задача → код → локальные проверки → Git → CI → образ → CD → проверка релиза → наблюдение. Изменения — в отдельной ветке, для агента с префиксом codex/. До слияния нужны успешные обязательные проверки актуального коммита и независимое одобрение; их нельзя заменять локальной самооценкой.

Изменения README, ТЗ, тестов, Make/Docker/CI, миграций и эксплуатации перечисляются в PR/MR с причиной и влиянием на приёмку. Проверки, пороги и требования не ослаблять для получения успешного результата. Финальная приёмка требует живой демонстрации и контрольного изменения по цепочке либо контролируемого отказа с восстановлением; подтверждения сохраняются в задаче/релизе.

Формат коммита: [TAG] краткое описание на русском. Используемые теги: [ADD] — добавление, [FIX] — исправление, [IMP] — улучшение, [REF] — рефакторинг, [TEST] — тесты, [REM] — удаление, [MOV] — перенос, [REV] — откат, [REL] — релиз, [I18N] — локализация, [PERF] — производительность, [CLN] — очистка, [LINT] — форматирование. Подробности при необходимости добавляются отдельным абзацем тела коммита.

Внешние настройки задаются через ENV_FILE: [правила передачи и изоляция тестов](GUIDE.md#внешний-файл-настроек).
Make и deploy учитывают переменную автоматически. В прямых рабочих командах
Compose добавляйте `--env-file "$ENV_FILE"` (Linux) или
`--env-file "$env:ENV_FILE"` (PowerShell), если переменная задана.

[Миграции, backup/restore и ограничения ресурсов](docs/DATABASE_OPERATIONS.md) — команды для Make, Linux и PowerShell.

## Политика контейнеров

Все контейнеры, включая PostgreSQL и проверки, запускаются без root.
`make container-check` автоматически проверяет правила и изолированный запуск;
команда включена в `make verify`. Нужен Python 3.11+ на хосте.
Перед прямыми командами Compose подготовьте каталоги и UID/GID по
[инструкции безопасности контейнеров](docs/CONTAINER_POLICY.md).
