# InventoryAccountment — Складской учёт

Учебное приложение для учёта материалов, единиц измерения, поставщиков и поступлений на склад. Проект развивается вместе с инфраструктурой: PostgreSQL, очередь обработки поставок, контейнеры, Nginx, CI/CD, резервное копирование и мониторинг.

## Состояние проекта

Сейчас репозиторий содержит исходную документацию. Приложение, Makefile, тесты, контейнеры и CI/CD ещё не реализованы. Команды ниже задают обязательный интерфейс будущей реализации; сейчас выполнить их нельзя.

- [Краткое техническое задание](docs/Техническое_задание.md) — функции, модель данных, ограничения, ошибки, хранение и приёмка.
- [Правила работы с репозиторием](AGENTS.md) — инструкции разработчикам и автоматизированным агентам.

## Планируемая архитектура

Минимально работоспособное приложение использует Python, FastAPI и PostgreSQL:

```text
HTTP-клиент → FastAPI → PostgreSQL
```

API выполняет операции со справочниками и поступлениями, а PostgreSQL хранит все данные. На следующих этапах к работающему приложению добавляются RabbitMQ, фоновые обработчики, Nginx, CI/CD и мониторинг. Их добавление не должно требовать перестройки модулей сущностей.

## Структура проекта

Для MVP достаточно одного пакета приложения. PostgreSQL и HTTP-обработчик представлены отдельными модулями, а каждой сущности БД соответствует один файл-модуль.

```text
InventoryAccountment/
├── app/
│   ├── __init__.py
│   ├── main.py               # точка запуска приложения
│   ├── http.py               # FastAPI, маршруты и обработка ошибок
│   ├── postgresql.py         # engine, сессии и базовая модель SQLAlchemy
│   └── entities/
│       ├── __init__.py
│       ├── unit.py           # единица измерения
│       ├── material.py       # материал
│       ├── supplier.py       # поставщик
│       ├── receipt.py        # поступление
│       └── receipt_item.py   # строка поступления
├── migrations/
│   ├── env.py                # подключение Alembic к моделям
│   └── versions/             # миграции Alembic
├── tests/
│   └── test_api.py           # основные HTTP- и DB-сценарии
├── .env.example
├── alembic.ini
├── compose.yaml
├── Dockerfile
├── Makefile
└── pyproject.toml
```

### Ответственность модулей

- `main.py` импортирует приложение из `http.py` и служит точкой запуска Uvicorn.
- `http.py` создаёт FastAPI, объявляет HTTP-маршруты, получает сессию БД и преобразует ошибки в HTTP-ответы.
- `postgresql.py` создаёт engine, базовый класс SQLAlchemy и фабрику сессий. В нём нет маршрутов и правил отдельных сущностей.
- Каждый файл в `entities/` содержит SQLAlchemy-модель, связанные Pydantic-схемы и минимальные CRUD-функции только для своей сущности.
- `migrations/` изменяет схему БД, а `tests/test_api.py` проверяет основной сценарий через HTTP с тестовой PostgreSQL.

Зависимости направлены в одну сторону:

```text
main → http → entities → postgresql
```

`postgresql.py` не импортирует HTTP-модуль. Модули сущностей не создают собственные подключения к БД и не импортируют `main.py`. Транзакцией управляет HTTP-обработчик сценария: он выполняет `commit` после успеха и `rollback` при ошибке.

Необходимость нового слоя или каталога должна подтверждаться реальным повторным использованием. Пока проект мал, не создаются отдельные пакеты `repositories`, `services`, `schemas`, `utils` и `common`: их преждевременное разделение усложняет навигацию. Когда файл сущности станет слишком большим или получит несколько независимых обязанностей, его можно разделить отдельной задачей с сохранением публичного интерфейса.

## Командный интерфейс

Для реализации потребуются Git, GNU Make, Python и Docker с Compose. Точные версии и зависимости должны быть закреплены при создании каркаса приложения. На Windows команды предполагается выполнять в WSL2 с Docker Desktop.

| Команда | Обязательное поведение после реализации |
| --- | --- |
| `make setup` | Подготовить локальное окружение, установить закреплённые зависимости; создать локальную конфигурацию из примера, не перезаписывая существующую |
| `make run` | Запустить приложение локально; необходимые БД и очередь и способ их запуска должны быть описаны при реализации |
| `make test` | Запустить модульные и интеграционные тесты, проверить порог покрытия; использовать изолированные тестовые данные |
| `make quality` | Проверить форматирование и выполнить статический анализ без изменения файлов; исправление форматирования при необходимости вынести в отдельную команду |
| `make migrate` | Применить миграции к явно выбранному окружению |
| `make backup` | Создать проверяемую копию БД и вывести путь, время создания и версию схемы; исключить пароли из вывода |
| `make restore BACKUP=<path>` | Проверить копию и восстановить её в явно указанную отдельную БД; перезапись существующей БД требует явного подтверждения цели |
| `make verify` | Выполнить `quality`, `test`, проверку миграций и `container-check`; любая ошибка завершает команду ненулевым кодом |
| `make up` | Собрать и запустить контейнерное окружение, дождаться готовности обязательных сервисов |
| `make down` | Остановить контейнерное окружение с сохранением данных и томов |
| `make container-check` | Собрать образ, запустить изолированное контейнерное окружение, проверить готовность и сквозной сценарий API → очередь → БД → отчёт, затем убрать только его временные ресурсы |

Планируемый первый запуск после реализации: `make setup` → `make up` → `make migrate` → `make verify`. Конкретные адреса API, имена переменных и доступ к панелям появятся вместе с работающим окружением и `.env.example`.

Повторный запуск setup и migrate должен быть безопасен. Проверки не должны обращаться к рабочей БД. Пароли, токены, реальные `.env`, дампы и пользовательские данные не хранятся в Git.

## Разработка и выпуск

**Задача → изменение кода → локальные проверки → Git → CI → образ → CD → проверка релиза → наблюдение.**

1. Создать задачу: проблема, границы изменения, критерии приёмки и риски для данных.
2. Создать отдельную ветку (`feature/<task>-<name>`, `fix/<task>-<name>` или `codex/<name>` для работы агента).
3. Реализовать изменение и необходимые тесты, обновить документацию, выполнить `make verify`.
4. Открыть PR/MR с привязкой к задаче, результатами проверок и описанием миграций/отката. Отдельно перечислить изменения критических файлов приёмки.
5. Получить успешный CI на актуальном коммите и независимое одобрение. Основная ветка защищается обязательными проверками и запретом прямой записи.
6. Собрать и проверить образ; CD доставляет артефакт по digest. Проверить развёртывание и сквозной сценарий, зафиксировать результат релиза, наблюдать метрики и логи.

Проверки обязательны для любого способа создания кода. Запрещено удалять тесты, отключать анализаторы, снижать пороги качества или ослаблять CI ради прохождения проверки. До начала функциональной разработки нужно реализовать обязательные команды и настроить проверки: отсутствие инструмента не считается успешной проверкой.

Финальная приёмка всегда включает живую демонстрацию и контрольное изменение через процесс либо контролируемый отказ с обнаружением и восстановлением. Подробные критерии — в [ТЗ](docs/Техническое_задание.md#6-процесс-и-критерии-приёмки).

### Правила коммитов Git

Структура коммита:

```
[TAG] Краткое описание правок

Детальное описание правок
```

Пример:

```
[ADD] Модуль для  работы с PostgreSQL

Новый модуль, содержащий набор функций 
для работы с базой данных PostreSQL
```

В коммитах принято использовать следующие теги:

- [FIX] для исправлений ошибок: в основном используется в стабильной версии, но также действителен, если вы исправляют недавнюю ошибку в версии разработки;
- [REF] для рефакторинг: когда функция сильно переписана;
- [ADD] для добавления новых модулей;
- [REM] для удаления ресурсов: удаление мертвого кода, удаление просмотров, удаление модулей, ...;
- [REV] для возврата обязательств: если обязательство вызывает проблемы или не требуется Обратная обработка производится с помощью этого тега;
- [MOV] для перемещения файлов: используйте git move и не меняйте содержимое перемещенного файла в противном случае Git может потерять отслеживание и историю файла; также используется при перемещении код от одного файла к другому;
- [REL] для релизных коммитов: новые основные или незначительные стабильные версии;
- [IMP] для улучшений: большинство изменений, сделанных в версии разработки являются постепенными улучшениями, не связанными с другим тегом;
- [I18N] для внесения изменений перевода;
- [PERF] для патчей производительности;
- [CLN] для очистки кода;
- [LINT] для устранения синтаксических ошибок;

## Этапы реализации

1. Каркас приложения, закреплённые зависимости, Makefile, тесты, CI, правила защиты ветки и владельцы критических файлов.
2. Схема БД и миграции, справочники, черновики поступлений и отчёты.
3. Outbox, очередь, worker, идемпотентность, повторы и очередь ошибок.
4. Контейнерное окружение, Nginx, backup/restore с демонстрацией восстановления.
5. Реестр образов, CD, проверка релиза и откат, метрики, dashboard и оповещения.

Каждый этап разбивается на задачи и проходит PR/MR. До появления автоматизации исходная документация проходит ручную проверку; функциональные изменения нельзя принимать с заглушками вместо обязательных проверок.
