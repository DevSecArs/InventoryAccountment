# InventoryAccountment — складской учёт

FastAPI / SQLAlchemy / PostgreSQL и статический интерфейс на HTML, JavaScript и CSS.
Приложение содержит авторизацию, справочники единиц, материалов и поставщиков,
поступления, проведение, историю статусов и отчёт по поставкам с CSV.
UI создаёт поступление с одной позицией; API поддерживает несколько позиций.

## Защита приёмки изменений

Критические файлы (тесты, Makefile, конфигурации анализаторов,
Docker и GitHub Actions) перечислены в `.github/CODEOWNERS`.
Для них предусмотрено обязательное одобрение `@DevSecArs`.

Шаблон `.github/pull_request_template.md` требует обоснования
изменений, влияющих на проверки качества.

Скрипт `scripts/acceptance_policy.py` обнаруживает изменения
критических файлов, удаление тестов и признаки ослабления проверок.
Скрипт `scripts/check_pr_review.py` содержит логику проверки
GitHub Reviews. Автоматическая обязательная проверка одобрения
пока не подключена.

Настройки защиты веток `dev` и `main` описаны в
`GITHUB-SETTINGS.md` и включаются владельцем вручную.
До подтверждения этих настроек блокировка слияния не гарантируется.

## Структура

- `backend/app/` — Python-приложение.
- `backend/alembic/` и `backend/alembic.ini` — миграции.
- `backend/pyproject.toml` и `backend/uv.lock` — зависимости и настройки Python.
- `backend/tests/` — unit- и интеграционные тесты backend.
- `frontend/` — веб-интерфейс; `tests/docker/` — проверки Compose и тестовые Docker-конфигурации.
- `reports/` — общие отчёты проверок.

## Запуск

Для Ubuntu Server нужны Docker Engine, Docker Compose v2 версии 2.22.0 или новее,
GNU Make и POSIX shell. Настройте Docker daemon и доступ текущего пользователя.
Создайте `.env` в корне проекта или запустите `make setup`: при отсутствии файла
команда создаст его из `.env.example` с правами 0600. Заполните `POSTGRES_PASSWORD`
в файле или передайте через окружение; setup проверяет итоговую конфигурацию
Compose и завершается ошибкой при отсутствующем или пустом секрете. Существующий
`.env` не перезаписывается. Setup проверяет Docker, daemon, исходные файлы и Compose;
может точечно добавить владельцу право чтения исходного файла или чтения/прохода
каталога, только если объект принадлежит текущему пользователю.

Из корня репозитория:

```bash
make setup
make build
make migrate
make up
make test
make quality
make verify
make status
```

`make test` собирает тестовый образ backend, запускает изолированную PostgreSQL,
применяет миграции и выполняет backend-тесты через `backend/tests/main.py`
и мутационные проверки.
Рабочий Compose и `.env` не используются. Конфигурации находятся в `tests/docker/`. После завершения удаляются тестовые контейнеры, сеть и том.
Отчёты отдельного запуска сохраняются в `reports/<идентификатор-запуска>/`.
После SIGKILL или аварии хоста очистка не гарантируется.

`make quality` выполняет backend Ruff, форматирование, mypy и Bandit.
Автоматические frontend-тесты и проверки удалены по решению пользователя;
регрессии интерфейса требуют проверки в браузере. `make verify` последовательно
запускает test, quality и security, останавливаясь при ошибке. `make security` проверяет полную историю Git и текущие исходники через Gitleaks.
Отчёты находятся в `reports/<идентификатор>/security/`; находки, неполная история
и ошибки блокируют результат. Рабочие env-файлы не копируются и не сканируются.

GitHub Actions дополнительно проверяет Bandit, зависимости backend из lock-файла
через pip-audit и образы backend, db и nginx через Trivy. Любая находка pip-audit,
а также HIGH, CRITICAL или неизвестная severity Trivy с доступным исправлением
блокируют CI. Включён `ignore-unfixed: true`: CVE без исправления исключаются
из отчёта и не блокируют проверку; LOW и MEDIUM
сохраняются в отчётах. Ошибки сканирования также блокируют результат. Отчёты
сохраняются как artifacts на 14 дней. Для ручного запуска workflow должен
присутствовать в default branch. Для временных файлов security можно задать
`SECURITY_TMPDIR`; отчёты сохраняются после очистки временного каталога.
CI использует фиктивный `POSTGRES_PASSWORD` для проверки Compose и сборки;
рабочий пароль сервера ему не требуется. Задание build сохраняет backend, nginx
и полученный из Compose образ db в artifacts. Матричное image_scan проверяет
их через Trivy Action; publish загружает те же backend, nginx и db из artifacts
и проверяет image ID перед отправкой в локальный registry без пересборки.
Nginx публикуется под именем frontend, каждый тег содержит SHA коммита.
Digest и вывод push сохраняются как artifact на 14 дней.
Режим `sh scripts/security.sh dependencies` выполняет только pip-audit;
старый режим `ci` сохранён для совместимости, workflow его больше не вызывает.

`make build` собирает backend и nginx со статикой и загружает закреплённый образ PostgreSQL.
`make migrate` запускает только БД, ждёт её healthcheck и применяет миграции
до head в одноразовом контейнере из готового backend-образа. Команда не собирает
и не скачивает образы; при их отсутствии выполните `make build`. После изменения
файлов миграций пересоберите образы перед запуском `make migrate`.
`make up` запускает готовые образы в фоне, две реплики backend и ждёт healthcheck;
сборку и миграции он не выполняет. После успешного запуска откройте http://localhost:8080.
При диагностике используйте `docker compose logs --tail=100 backend db nginx`.

Зарегистрируйте первого администратора после открытия интерфейса.
Nginx работает с UID:GID 101:101 из закреплённого образа `nginxinc/nginx-unprivileged` и является
единственной внешней HTTP-точкой входа: порт 8080 хоста направлен на 8080 контейнера.
Образ использует `/tmp` для PID и временных файлов; версия и digest закреплены.
При сборке Nginx обновляет пакеты Alpine; чтобы сбросить кеш этого слоя,
используйте сборку с `--no-cache` и повторите проверку образов в CI.
Nginx направляет `/api` и `/health` к двум backend, а остальные запросы
обслуживает из статического каталога. Для путей страниц используется History
fallback; отсутствующие JS, CSS и SVG возвращают 404. Индекс и нефингерпринтованные
файлы не помечаются immutable. Backend и PostgreSQL не публикуют порты на хост.

Dockerfile содержит цели backend и nginx. Backend запускает Uvicorn напрямую;
миграции применяются явно командой `make migrate`. Прямой `docker compose up`
не подготавливает схему. `/health/ready` проверяет соединение с PostgreSQL,
но не актуальность схемы. Backend устанавливается по `backend/uv.lock`, работает
от UID 1001, PostgreSQL — от postgres. Frontend состоит из статических файлов и не требует установки пакетов.

Compose автоматически читает необязательный `.env`; образец — [.env.example](.env.example).
Git исключает `.env` и файлы `.env.*`; исключение оставлено только для
`.env.example`. Не добавляйте реальные реквизиты даже принудительно через `git add -f`.
Для другого файла: `docker compose --env-file /путь/к/файлу up -d --build --wait`.
Примерный пароль предназначен для локального учебного запуска.
Перед первым запуском задайте `POSTGRES_PASSWORD` в `.env`: пустое значение
намеренно блокирует `make setup` и Compose с понятной ошибкой. `make setup`
создаёт файл из образца только при его отсутствии, сохраняет существующий без
перезаписи, проверяет его права и объясняет необходимость заполнить секрет.
Рабочий `.env` должен принадлежать владельцу и иметь права 0600.
Изменение переменных не меняет реквизиты уже созданной БД и не меняет пароль
PostgreSQL в существующем томе; смену пароля выполняет владелец отдельно.
Кеши сборки содержат только загруженные пакеты, без `.env` и секретов.
Для CI используйте GitHub Actions Secrets и минимальные права штатного
`GITHUB_TOKEN`; не передавайте секреты через build args или Docker ENV.

## Локальный Docker Registry

Для локальных сборок используется Docker Registry по адресу
`192.168.56.111:5000` в host-only сети VirtualBox.

Registry работает по HTTP без TLS и аутентификации. Он предназначен
только для доверенной локальной сети и не должен публиковаться в интернет.
Любой узел с доступом к порту может читать и записывать образы. Доступ
ограничивается сетевым экраном только доверенными узлами; привязка к адресу VM
не ограничивает отправителей, а опубликованные Docker порты могут обходить UFW.
Сетевое ограничение пока отложено владельцем стенда и не проверено.

### Настройка Docker Engine

На Ubuntu VM в `/etc/docker/daemon.json` должен присутствовать параметр:

```json
{
  "insecure-registries": ["192.168.56.111:5000"]
}
```

Сохраняйте остальные существующие параметры Docker Engine.

В Windows Docker Desktop тот же адрес добавляется через
Settings → Docker Engine. После изменения настроек перезапустите
соответствующий Docker Engine.

### Запуск Registry

Из корня проекта:

```bash
docker compose -f docker-compose.registry.yml up -d
curl -f http://192.168.56.111:5000/v2/
```

Успешный ответ Registry: `{}`.

Данные хранятся в Docker-томе `inventory-registry_registry_data`.
Имя проекта `inventory-registry` задано в Compose; не переопределяйте его
через `-p` или `COMPOSE_PROJECT_NAME`, иначе будет выбран другой том.
Не удаляйте этот том при очистке Docker.
Контейнер настроен на автоматический перезапуск (`unless-stopped`).

Для первоначального запуска образ `registry:2.8.3` должен быть
заранее доступен локально или загружен из внешнего Registry.

### Образы и SHA256

Dockerfile, Compose и security-скрипты используют локальный Registry
с закреплёнными SHA256. Изменение одного тега без обновления digest
не меняет фактически используемый образ.

Перед сборкой приложения необходимые образы должны находиться
в локальном Registry.

### Наполнение registry

После запуска registry администратор копирует исходные многоплатформенные
образы с сохранением digest. На VM установите `skopeo` из репозитория Ubuntu;
для загрузки исходников нужны интернет и доступ к источникам. Команда ниже
копирует все платформы и метаданные; ошибка означает, что наполнение не завершено.
Не заменяйте её на обычные `docker pull/tag/push`: так переносится только
текущая платформа. Теги назначения менять нельзя: ссылки сборок закреплены
одновременно по версии и digest.

```bash
sudo apt-get update
sudo apt-get install skopeo
registry_copy_status=0
while read -r source destination; do
  skopeo copy --all --preserve-digests --dest-tls-verify=false \
    "docker://$source" "docker://192.168.56.111:5000/$destination" || { registry_copy_status=1; break; }
done <<'EOF'
docker.io/library/registry@sha256:a3d8aaa63ed8681a604f1dea0aa03f100d5895b6a58ace528858a7b332415373 library/registry:2.8.3
ghcr.io/astral-sh/uv@sha256:f459f6f73a8c4ef5d69f4e6fbbdb8af751d6fa40ec34b39a1ab469acd6e289b7 astral-sh/uv:0.9.5
registry.access.redhat.com/ubi9/python-312@sha256:19e1e927138b40454858f297884c2c4e2f13f5ba95b3f55faea174d3cbb57067 ubi9/python-312:1
docker.io/nginxinc/nginx-unprivileged@sha256:5aea7cc516b419e3526f47dd1531be31a56a046cfe44754d94f9383e13e2ee99 nginxinc/nginx-unprivileged:1.29.3-alpine
docker.io/library/postgres@sha256:665dc7b37ac52a17e298511414c21d23ffa4e6a6ef6225b3e5d59c7afb35e994 library/postgres:17.11-bookworm
docker.io/library/golang@sha256:dc0963f32053e4bc451d24d87e3892d42d01021b61f093e98eb95c0352bb84b0 library/golang:1.27-bookworm
docker.io/library/python@sha256:f3fa41d74a768c2fce8016b98c191ae8c1bacd8f1152870a3f9f87d350920b7c library/python:3.12.12-slim
docker.io/zricethezav/gitleaks@sha256:b5918eb91b8d2473cec722f066abb4352e4ffdc4ec9f4283ec143aba9ec9ebc4 zricethezav/gitleaks:v8.24.2
docker.io/aquasec/trivy@sha256:029e990b328d149bf0a9ffe355919041e1f86192db2df47e217f8a36dd42ceac aquasec/trivy:0.59.1
EOF
test "$registry_copy_status" -eq 0
```

Для проверки каждой ссылки сравните digest исходного и локального манифеста
через `skopeo inspect --raw` и `sha256sum`, а платформы — через
`docker buildx imagetools inspect`. В Bash перед проверкой конвейеров включите
`set -o pipefail`: иначе ошибка Skopeo может выглядеть как хеш пустого ввода.
В источниках Skopeo используйте `имя@digest` без тега: сочетание тега и digest
эта утилита не принимает. Версия сохранена в теге назначения. Загрузка базы уязвимостей Trivy из внешнего
OCI-источника разрешена отдельно от исполняемых образов. Trivy Action в CI —
composite action, устанавливающий исполняемый файл, а не Docker action.

Сборки и локальные проверки после наполнения используют локальные ссылки.
На Docker Desktop с containerd image store
возможен сбой HTTP pull; на проверенной конфигурации Windows помогло переключение
на классическое хранилище. Переключение меняет видимость образов и контейнеров.

### Исправленный PostgreSQL

Используется PostgreSQL 17.11 с заменённым `gosu 1.20`,
собранным с Go 1.27.3 и `golang.org/x/sys v0.44.0`.

Исходники и инструкции сборки находятся в:

- `docker/gosu/`
- `docker/postgres/Dockerfile`

Сборка:

```bash
docker build -f docker/postgres/Dockerfile -t inventory-postgres-reproducible:local .
```

Исходные образы PostgreSQL и Go берутся из локального Registry.
При отсутствии кеша Go-модулей требуется доступ к внешнему
источнику зависимостей. Полностью автономная сборка пока
не гарантируется.

Рабочая и тестовая конфигурации ожидают в локальном Registry образ PostgreSQL:

`192.168.56.111:5000/inventory/postgres:17.11-gosu1.20`

Его закреплённый digest:

`sha256:beda889504259e25f6a148e9460de62ade9072d48a48c31483a3c9d80e6aa0e4`

Проверьте его наличие по digest до запуска проверок. Приведённая выше сборка
создаёт локальный образ и сама по себе не публикует его. Сборка и публикация
не гарантируют совпадения digest с закреплённым; при несовпадении не меняйте
рабочие ссылки без проверки образа и согласования нового набора.

### Проверки

Из корня проекта:

```bash
make test
make quality
make security
sh scripts/security.sh dependencies
sh scripts/security.sh ci
make container-check
```

`make security` проверяет историю и исходники через Gitleaks.
Режим `dependencies` выполняет pip-audit.
Режим `ci` выполняет pip-audit и сканирование образов
backend, db и nginx через Trivy.

Отчёты сохраняются в каталоге `reports/`.
Для Trivy требуется достаточное свободное место на диске.

Тесты используют изолированную PostgreSQL и не должны
подключаться к рабочей базе данных.

### Ограничения

CI использует self-hosted Linux x64 runner с метками `self-hosted`, `linux`,
`x64`, `inventory-registry`, Docker daemon с доступом к registry, Docker Compose,
make, Python 3 и доступом к GitHub, пакетным источникам и базе Trivy. Метку
`inventory-registry` администратор назначает при регистрации runner. Запуск
предусмотрен только для push в `dev` и `main`, а также для ручного запуска на
этих ветках. Pull request не запускает этот workflow: его проверки не появятся
в PR, и обязательные проверки защиты ветки потребуют отдельного решения владельца.

Runner и Docker-хост должны быть доступны только доверенным пользователям.
Защита веток и доступ к runner настраиваются владельцем отдельно; одних условий
в workflow недостаточно для защиты от изменения других workflow или вручную
запущенного недоверенного кода. Не используйте runner с доступом к registry для
непроверенных PR. До подтверждения этих условий не регистрируйте runner для
недоверенных запусков.

Публикация выполняется только после push в `dev`, после успешных всех заданий
из `needs`, и не запускается вручную. Имена образов —
`192.168.56.111:5000/inventory/{backend,frontend,db}:<SHA коммита>`.
Публикация последовательная: при ошибке после одного или двух push часть тегов
может уже существовать; до исправления не используйте такой набор. Вывод push
и digest выполненных отправок сохраняются в artifact `published-images-*`.
Результат CI и наличие набора требуется проверять по фактическому прогону.

Registry работает по HTTP, поэтому доступ к порту 5000
должен быть ограничен доверенной сетью.

## Управление и диагностика

Backend устанавливается и запускается в одной стадии Red Hat UBI9 Python 3.12.
Базовый образ закреплён по digest; для обновления проверьте новый digest UBI,
обновите его в обоих Dockerfile, пересоберите образы и повторите проверку образов в CI.
Исправления и оставшиеся уязвимости оцениваются по результатам сканирования.
Виртуальное окружение находится в `/opt/app-root/src/.venv`; healthcheck
использует его Python. Для проверки миграций в работающем контейнере:
`docker compose exec backend /opt/app-root/src/.venv/bin/python -m alembic current`.
Для применения используется `make migrate`.

```bash
docker compose ps
docker compose logs --tail=100 nginx backend db
curl http://localhost:8080/health/ready
docker compose exec nginx nginx -t
curl -sSI http://localhost:8080/health/live
make migrate
docker compose down
```

`make container-check` проверяет нормализованный Compose JSON и статические
ограничения Dockerfile, `.dockerignore`, портов, пользователей, лимитов ресурсов,
healthcheck и включения конфигурации в образ. Команда требует Docker CLI и Compose,
но не запускает контейнеры. Это ограниченный статический аудит: он не доказывает
содержимое образов, фактические UID процессов, работоспособность и отказоустойчивость.

Ответы backend содержат `X-Instance-ID` (hostname контейнера). Nginx обновляет
DNS backend каждые 5 секунд, пассивно исключает неисправный узел на 5 секунд и
повторяет только GET/HEAD один раз. Таймаут подключения 3 секунды ограничивает
установление соединения; read timeout 30 секунд ограничивает паузу между чтениями
от backend, но не полное время ответа. Отказоустойчивость покрывает отказ одной
backend-реплики на одном хосте; Nginx, PostgreSQL и хост остаются единичными
точками отказа.

Данные находятся в именованном томе inventory_data проекта inventory-compose.
`make down` и `docker compose down` сохраняют том. Существующий том того же
проекта переиспользуется. Для обновления выполните `make build`, `make migrate`,
затем `make up`. Для отката кода
вернитесь к совместимой ревизии и пересоберите образы. Миграции и данные
автоматически не откатываются. Перед работой с ценной БД нужна резервная копия.
Логи идут в stdout/stderr, readiness проверяет PostgreSQL.

## Проверки без оболочек команд

Для локальных проверок backend нужны Python 3.12 и uv. Установка зависимостей и запуск unit-тестов:

```bash
cd backend
uv sync --locked --extra dev
uv run --extra dev pytest tests/unit
uv run --extra dev ruff check app tests
uv run --extra dev mypy app
uv run --extra dev bandit -r app
uv run --extra dev pip-audit
```

Команды Python выполняются из `backend/`.
Порог покрытия бизнес-логики в backend/pyproject.toml — 80%.
Отчёты создаются в корневом `reports/`. Unit-тесты покрывают
только часть приложения; команда может завершиться ошибкой порога, даже если
все выбранные тесты прошли. Полное покрытие проверяется вместе с интеграционными
тестами; порог не снижен.

Интерфейс проверяйте в браузере на изолированной БД.

Проверка Docker-конфигурации отдельно от unit-тестов, из корня:

```bash
docker compose --env-file .env.example config --quiet
python -m unittest tests.docker.test_simple_docker -v
```

Полный backend-набор в одноразовой изолированной среде:

```bash
make test
```

Точка входа `python backend/tests/main.py` обнаруживает тесты рекурсивно в
`backend/tests`, останавливается при первой ошибке и сохраняет JUnit/XML/HTML
отчёты и покрытие в корневой `reports/` (при запуске через Make — в уникальном
подкаталоге запуска).

Интеграционные тесты требуют отдельную PostgreSQL, применённые миграции,
`APP_ENV=test` и одинаковые `DATABASE_URL` / `TEST_DATABASE_URL` с именем БД,
заканчивающимся на `_test`. В отдельном терминале с этими переменными, из корня репозитория:

```bash
cd backend
uv run alembic upgrade head
uv run --extra dev pytest tests/unit tests/integration
```

Не используйте рабочую БД: тесты очищают таблицы. Локальный `.env` автоматически
читает Compose, но не приложение; для uv-команд задавайте переменные явно.

## Состояние инфраструктуры

Прежний DevOps-контур удалён по решению начать его заново. Запуск приложения
не зависит от старых scripts или Linux test-образа; `make test` использует
отдельные тестовые Docker-файлы. Workflow CI содержит проверки и публикацию образов; сбор метрик предстоит спроектировать отдельно. Наличие Dockerfile
не подтверждает успешную сборку, релиз или приёмку.

Правила изменений — [AGENTS.md](AGENTS.md).

Перенос backend — задача без номера: цель — изолировать Python-проект,
сохранив приложение, миграции и тесты. Критические изменения: Dockerfile,
.dockerignore, backend/pyproject.toml, backend/alembic.ini и пути тестов.
Новых миграций и изменений данных нет. Проверка: сборка backend, существующие
тесты и миграции на отдельной БД; перед слиянием нужно независимое одобрение.
Откат — возврат структуры и путей предыдущей ревизии, без изменения БД.

Локальная проверка переноса: backend-образ собран с `uv sync --locked`;
миграции применены на новой отдельной БД; 61 backend-тест прошёл,
покрытие 84,72%; четыре проверки Compose и `git diff --check` прошли.
Отчёты находятся в `reports/`. Рабочие контейнеры не перезапускались;
CI, релиз и человеческая приёмка не проводились.
