## 1. Цель и согласованные решения

Добавить Make-команду `test` для Ubuntu Server: автоматически собрать тестовые
образы, подготовить отдельную БД, применить миграции, запустить все backend-тесты
через `backend/tests/main.py`, сохранить отчёты и удалить тестовое окружение.

Решения пользователя:

- Тесты выполняются в отдельном контейнере с backend-зависимостями; Python,
  uv, Node.js и pnpm на хосте не требуются.
- Использовать собственные Docker-файлы тестового окружения. Рабочие Dockerfile,
  docker-compose.yml и .dockerignore не изменять.
- Подготовка тестовой БД и сборка тестового образа — автоматические.
- Frontend-образ также обязательно собирать, но frontend-тесты пока не запускать.
  Сервис frontend и рабочее приложение для backend-тестов не запускать.
- Сохранить формат заголовков файлов/функций, русские названия с идентификаторами,
  остановку при первой ошибке и сводку успешных/провальных тестов.
- После успеха и ошибки удалять исключительно тестовые контейнеры, сеть и том БД.
  Отчёты сохранять в корневом reports/.
- Перенести main.py из test/ в backend/tests/main.py и удалить каталог test/.
  Новая точка входа включает только backend-тесты.

## 4. Тестовые образы

### backend-test

- Python и установщик зависимостей закрепить совместимыми версиями из текущего
  проекта. Устанавливать backend-зависимости с extra dev из backend/uv.lock
  в locked-режиме, без обновления lock-файла.
- Включить приложение, Alembic, конфигурацию и все backend/tests, включая main.py.
- Рабочий каталог организовать так, чтобы backend/pyproject.toml и относительные
  ../reports разрешались корректно, например /workspace/backend и /workspace/reports.
- Основная команда тестового сервиса — python tests/main.py из backend-каталога.
  Не подменять её прямым pytest в Makefile или Compose.
- Не запускать Uvicorn или приложение; не публиковать порты.
- Сохранить запуск от непривилегированного пользователя. Обеспечить доступ
  к каталогу отчётов без chmod 777 и запуска тестов от root.

### frontend-test

- Самостоятельная цель тестового Dockerfile, не изменение рабочего образа.
- Использовать закреплённые совместимые Node.js/pnpm и frontend/pnpm-lock.yaml;
  устанавливать зависимости с --frozen-lockfile.
- Включить frontend-исходники и нужные конфигурации, чтобы образ был пригоден
  для последующего добавления frontend-тестов.
- В рамках этой задачи только собрать образ. Не выполнять Vitest, pnpm quality,
  production-сборку, не поднимать Vite и не добавлять frontend-результаты в сводку.

### Контекст

Тестовый ignore должен включать только нужные исходники, конфигурации и lock-файлы,
исключая .git, env/секреты, локальные зависимости, кеши, дампы и reports.
Избегать COPY всего репозитория и wildcard COPY, вызывающих обход недоступных
pnpm-ссылок на Windows. Не копировать реальные env в образы.

## 5. Изоляция БД и Compose

1. Все тестовые команды используют явно `-f tests/docker/docker-compose.test.yml` и отдельное
   уникальное имя Compose-проекта каждого запуска. Рабочий Compose автоматически
   не подмешивается; имя inventory-compose не использовать.
2. Создавать отдельные db, сеть и именованный том в рамках этого проекта.
   Запрещены external-тома, рабочие bind-mount данных и фиксированное volume.name,
   совпадающее с рабочими ресурсами. Не задавать общие container_name.
3. БД имеет имя, оканчивающееся на _test. Использовать только обезличенные
   тестовые реквизиты. APP_ENV=test; DATABASE_URL и TEST_DATABASE_URL идентичны
   и указывают на тестовый db. Рабочие .env и переменные подключения не должны
   переопределять эту цель. Не source/include и не печатать рабочий .env.
4. В тестовом Compose использовать внутреннюю сеть без публикации портов db
   или тестового backend. Frontend-сервис не запускать.
5. Запустить только db и дождаться штатного healthcheck Compose. Затем отдельно
   применить существующие Alembic-миграции в тестовом backend-образе. При ошибке
   миграции не запускать main.py.
6. Не использовать make migrate: эта команда относится к рабочему окружению.
7. Дополнительный API-контейнер не нужен: интеграционные тесты используют TestClient.

## 6. make test: последовательность и завершение

1. Добавить test в .PHONY, не менять цель по умолчанию setup и существующие
   setup/build/up/down/migrate. Не вызывать рабочие build/up/migrate/down.
2. Подготовку ограничить необходимыми проверками Docker, Compose, доступности
   daemon и исходников. Допустимо переиспользовать setup, если его побочные
   эффекты ограничены согласованной подготовкой файлов и он не запускает среду.
3. Уникальный идентификатор запуска создать один раз на весь рецепт. Использовать
   одни и те же Compose-файл, project name и образы на всех этапах и при очистке.
4. Подготовить writable reports/ в корне проекта; не очищать существующие
   пользовательские отчёты и не менять владельцев посторонних файлов.
5. Собрать обе цели тестового Dockerfile через тестовый Compose. Ошибка любой
   сборки должна завершать make test ошибкой до запуска тестов.
6. Получить/использовать закреплённый образ PostgreSQL, запустить db, дождаться
   готовности, применить миграции и выполнить backend/tests/main.py.
   Все контейнеры создавать только в изолированном тестовом проекте.
7. Сохранить точный код завершения основного шага (сборка, БД, миграция, main.py).
   Не подменять ошибку тестов успешным кодом cleanup.
8. Организовать cleanup через POSIX trap для обычного завершения, ошибок,
   SIGINT и SIGTERM: `docker compose ... down --volumes` только с точным
   уникальным именем тестового проекта. SIGKILL/авария хоста не позволяют
   гарантировать cleanup — это ограничение честно указать.
9. Cleanup удаляет тестовые контейнеры, сеть и созданный тестовый том БД,
   но не образы, кеш, рабочие ресурсы или reports/. Не использовать global prune.
10. При ошибке очистки сообщить project name для диагностики. Если основной
    шаг успешен, неуспешный cleanup делает всю команду неуспешной; если основной
    шаг уже упал, сохранить его код и отдельно сообщить ошибку cleanup.
11. Не обрабатывать ошибку через `|| true`, префикс `-` рецепта или exit 0.
    Не выполнять cleanup, если нельзя надёжно определить безопасную тестовую цель.
12. Использовать определение корня и корректное цитирование путей, включая
    запуск Makefile по абсолютному пути из другого каталога. Не требовать
    интерактивного ввода и не использовать sudo.

## 7. backend/tests/main.py

- Поддержать прямой запуск python backend/tests/main.py из корня репозитория
  и по абсолютному пути из другого каталога при подготовленном окружении.
- Определять корень backend по __file__, запускать pytest с его конфигурацией
  и рабочим каталогом backend. Отчёты направлять в корневой reports/.
- Запускать одной pytest-сессией все обнаруженные тесты в backend/tests,
  рекурсивно. Не поддерживать ручной фиксированный список модулей/функций.
  Сам main.py не является тестовым модулем и не должен повторно запускать себя.
- Не вызывать тестовые функции напрямую: сохранить фикстуры, параметризацию,
  unittest-совместимость и asyncio. Для представления результатов использовать
  небольшой встроенный pytest-плагин/hooks; не разбирать текст консоли pytest.
- Сохранить суммарное покрытие и порог 80%, настройки строгих маркеров и отчётов.
  Не запускать отдельную pytest-сессию на каждый файл/функцию.
- Последовательное выполнение с группировкой по файлам, без параллелизма.
  Остановка при первой ошибке теста/setup/teardown через штатный fail-fast pytest.
  Очистка уже начатых фикстур должна завершиться.
- При ошибке сбора, неправильном окружении, отсутствии pytest/найденных тестов,
  отказе БД и порога покрытия возвращать ненулевой код и понятную причину.
  Сам main.py не подготавливает БД, не устанавливает зависимости и не запускает Docker.
- Пробрасывать итоговый код pytest. Если тесты прошли, но порог покрытия не
  достигнут, явно сообщить отказ проверки покрытия, не объявлять весь запуск успешным.

## 8. Формат вывода

```text
==========Проверка паролей / backend/tests/unit/test_password_verification.py==========
----------Верный пароль проходит проверку / test_verify_password_valid----------
{stdout, stderr, логи этого тестового случая при наличии}
Результат: УСПЕШНО

----------Неверный пароль отклоняется / test_verify_password_invalid----------
{вывод и диагностика ошибки}
Результат: ПРОВАЛ

Результат файла: успешно — 1, провально — 1

Результат: успешно — 1, провально — 1
```

Названия и идентификаторы примера иллюстративные. Заголовки файлов оформлять
`==========`, функций — `----------`. Название — русское описание / технический
идентификатор. У файлов указывать путь относительно корня репозитория, у функций —
pytest-идентификатор с классом и параметрами при наличии. Каждый параметризованный
случай отображать и учитывать отдельно.

Использовать существующие русские docstring или краткие названия внутри main.py,
не менять существующие тесты ради оформления. Для неизвестных новых случаев
допустим fallback «Тест / <идентификатор>», для файла — «Файл тестов / <путь>».
Механизм русских названий не должен становиться списком обнаружения тестов.

Заголовок функции печатать перед выполнением. Вывод stdout/stderr/логов и
traceback связывать с нужным случаем, не дублировать по фазам. Не создавать
фиктивный вывод для молчащих тестов. Стандартный прогресс pytest можно заменить,
но сохранить существенную диагностику, предупреждения и итог покрытия.

Один случай учитывать один раз по окончательному результату setup/call/teardown.
Падение любой фазы — провал, даже если call успешен. Пропуски и ожидаемые падения
показывать отдельными статусами/причинами и не включать в успешные/провальные.
Незапущенные после fail-fast случаи не считать выполненными или пропущенными.
Ошибки сессии показывать отдельно, не выдумывать для них провальные функции.
Сводку файла выводить после его последнего выполненного случая, включая досрочную
остановку, общую сводку — один раз после pytest-сессии.

## 9. Отчёты и параллельные запуски

Использовать существующие coverage XML/HTML, JUnit и .coverage из конфигурации
backend. Выгрузить их в reports/ на хосте до уничтожения тестовых контейнеров.
Допустим bind-mount отчётов с согласованными UID/GID или безопасное копирование
из контейнера; не открывать права на запись всем пользователям и не менять
рабочие Docker-файлы. Сохранять доступ к результатам текущему пользователю.

При fail-fast сохранять фактически сформированные отчёты; не создавать фиктивные
при ошибке сборки/подготовки. Старый отчёт не выдавать за результат нового запуска.
Не создавать дополнительные форматы, логи и служебные постоянные файлы.

Уникальные Compose-проекты должны изолировать ресурсы. Если параллельные запуски
могут перезаписать общие имена отчётов, их либо явно запретить с диагностикой,
либо сохранять результаты в reports/<идентификатор_запуска>/ с минимальным
переопределением путей pytest/coverage, сохраняя порог и форматы. Предпочесть
минимальное решение и описать фактическое размещение в README.

## 10. Стиль и ограничения

Комментарии и docstring в новом коде обязательно писать на русском языке;
сообщения — на русском, идентификаторы — на английском.
Строго соблюдать Keep It Simple, Stupid! (KISS), Don't Repeat Yourself (DRY)
и SOLID: разделять оркестрацию среды и представление результатов, переиспользовать
Compose/pytest, не дублировать команды, учёт тестов и определения зависимостей.
Не создавать ненужные классы, интерфейсы, обёртки и архитектурные уровни.

Тестовая БД должна быть технически отделена от рабочей; одного суффикса _test
недостаточно, если URL может быть переопределён рабочим окружением. Не отключать
защитные фикстуры и не запускать TRUNCATE на рабочем PostgreSQL ради проверки.
В cleanup разрешено удалять только созданный этой командой тестовый том.

## 11. Критерии приёмки

1. make test работает на Ubuntu с GNU Make и Docker/Compose без Python/Node на
   хосте; автоматически собираются backend-test и frontend-test.
2. Frontend-тесты, Vite и рабочие сервисы не запускаются. Рабочие Docker-файлы
   и данные не изменены. Наличие/отсутствие рабочего окружения не влияет на тестовую БД.
3. БД создаётся отдельно, проходит healthcheck, все существующие миграции
   применяются до head. При ошибке любого этапа последующие не выполняются.
4. Фактическая точка запуска — backend/tests/main.py; автоматически включены
   все pytest-совместимые тесты под backend/tests, без tests/docker и frontend.
5. Файлы, функции, параметризованные случаи, их вывод и сводки соответствуют
   согласованному формату. Первая ошибка останавливает дальнейшие тесты.
6. Сохраняется правильный итог при setup/teardown/collection error, пропуске,
   отсутствии тестов и недостигнутом покрытии; нет двойного счёта и ложного успеха.
7. Отчёты доступны в reports/ после успеха и ошибки тестов; порог покрытия 80%
   не снижен. Ошибка подготовки не выдаёт старый отчёт за новый.
8. После успеха, ошибки сборки/миграции/теста и SIGINT/SIGTERM тестовые ресурсы
   очищены, рабочие тома и отчёты сохранены. Ошибка cleanup диагностируется.
9. Повторный запуск работает с новой БД; ресурсы и отчёты параллельных запусков
   не смешиваются согласно выбранному решению.
10. main.py существует только в backend/tests, каталог test/ удалён без потери
    посторонних файлов. Старые пути точки входа исправлены в разрешённых документах.
11. Существующие Make-цели сохраняют поведение; git diff --check проходит.

## 12. Проверки и отчёт исполнителя

Проверить реальный make test в Ubuntu, успешный сценарий и контролируемые
ошибки в изолированной среде. Hooks можно проверять объектами в памяти,
не меняя существующие тесты. Для cleanup проверить сохранённый код ошибки
и точное имя удаляемого проекта/тома. Не считать make -n живой проверкой.

В итоговом сообщении указать файлы, команду запуска, реальные результаты,
количество тестов, покрытие, место отчётов и пропуски с причинами.
Критические изменения: Makefile, новые тестовые Docker-конфигурации,
backend/tests/main.py и правила документации. Требуется независимая проверка
