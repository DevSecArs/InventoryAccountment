# Задание ИИ-агенту 5.6 Terra: завершение сущностей MVP складского учёта

## 1. Цель и согласованные решения

Реализовать сквозной сценарий одного склада: создать поступление со строками → сохранить черновик → синхронно провести → просмотреть историю → получить отчёт и CSV. Работать в существующем приложении FastAPI/PostgreSQL и React/TypeScript.

Номер задачи отсутствует; этот файл является описанием для переноса в трекер. Задача и PR в трекере не создавались в рамках подготовки документа.

Пользователь согласовал упрощение MVP: проведение выполняется непосредственно HTTP-запросом в одной транзакции PostgreSQL, переход — `draft → posted`. RabbitMQ, outbox, publisher, worker, DLQ, фоновые повторы и промежуточные состояния в новом сценарии не реализовывать. Историю статусов и отчёт сохранить.

Это явное изменение требований для данной задачи относительно асинхронного сценария в [исходном ТЗ](docs/Техническое_задание.md) и [ТЗ интерфейса](docs/WEB_UI_CODEX_SPEC.md). Frontend входит в текущую задачу по прямому поручению пользователя. Исходные документы не переписывать. Остальные применимые бизнес-ограничения сохраняются.

При возникновении вопроса, неоднозначности или необходимости расширить согласованные границы **остановиться и спросить пользователя**, не выбирать новый продуктовый сценарий самостоятельно.

## 4. Модель и миграции

### 4.1. Сохранность существующих данных

Добавить новую Alembic-ревизию после актуального head; опубликованные миграции не редактировать. Сохранять документы, строки, справочники, идентификаторы, ограничения количества и уникальности. Не менять текущий способ хранения UUID только ради унификации.

Не удалять старые поля и допустимые значения статуса в этой задаче: это позволяет обновить существующую схему без принудительного преобразования данных. Новое API создаёт только `draft` и переводит его только в `posted`. Если в целевой БД обнаружены `queued`, `processing`, `failed`, сохранить их и остановиться для согласования обработки таких документов. Автоматически проводить или возвращать их в черновики запрещено.

### 4.2. История статусов

Добавить `ReceiptStatusHistory` в `app/entities/receipt_status_history.py`, таблицу `receipt_status_history`:

- `id` — UUID в принятом в проекте представлении, первичный ключ;
- `receipt_id` — обязательный FK на поступление;
- `from_status`, `to_status` — обязательные строки; для новых записей только `draft`, `posted` соответственно;
- `changed_at` — обязательный `TIMESTAMPTZ`, время перехода в UTC;
- `reason` — необязательный безопасный текст до 500 символов, без трассировок и секретов.

Индексировать чтение по `(receipt_id, changed_at, id)`. Ограничение уникальности `receipt_id` допустимо и требуется для этого MVP: разрешён ровно один переход за жизнь документа. Запись добавляется вместе с проведением; редактирование и удаление истории через API не предоставлять. FK не должен позволять удалить документ вместе с историей проведения.

Создание черновика не считать переходом статуса. Для существующих документов не выдумывать исторические даты и записи: история до внедрения функции может отсутствовать, UI должен пояснять это. Подключить модель к Alembic metadata.

### 4.3. Ограничения

Сохранить `NUMERIC(18,3)`, положительность количества, уникальность `(receipt_id, material_id)` и `(supplier_id, document_number)`. Количества в Python — `Decimal`, в JSON — десятичные строки. Не округлять лишние знаки молча.

Запретить изменение `unit_id` материала, если материал уже используется хотя бы в одной строке поступления, включая черновик. Проверку согласовать с конкурентным созданием строк. Физическое удаление используемых справочников должно отклоняться и возвращать понятный конфликт, сохраняя FK. Архивирование сохраняет исторические ссылки.

## 5. API поступлений и синхронное проведение

Все пути ниже указаны относительно `/api/v1`. Существующие поля запросов и ответов сохранять; новые поля добавлять совместимо. Контракт описать Pydantic-схемами и OpenAPI непосредственно в коде.

| Метод и путь | Назначение и результат |
| --- | --- |
| `POST /receipts/` | Существующее создание черновика со строками, HTTP 201 |
| `GET /receipts/` | Список `{items, total, skip, limit}`; сохранить существующие значения и ограничения пагинации |
| `GET /receipts/{id}` | Карточка со строками, HTTP 200 |
| `PATCH /receipts/{id}` | Изменение только черновика; замена набора строк атомарна, HTTP 200 |
| `DELETE /receipts/{id}` | Удаление только черновика и его строк, HTTP 204; отсутствующий документ — 404 |
| `POST /receipts/{id}/post` | Синхронное проведение без тела запроса; вернуть карточку `posted`, HTTP 200 |
| `GET /receipts/{id}/history` | `{items: [...]}` в порядке `changed_at, id`; отсутствующий документ — 404, отсутствие истории — пустой массив |

Для списка добавить необязательные фильтры `supplier_id`, `status`, `search` по номеру и `from`, `to` по `received_at`. Обе границы времени независимы для списка; если указаны обе, требовать `from < to`. Интервал полуоткрытый. Сортировка стабильная: `created_at DESC, id DESC`. `total` считать после фильтрации до пагинации.

Дополнить карточку `created_at`, `updated_at`; названия поставщика, материала и единицы, нужные для отображения, получать с сохранением архивных ссылок — в ответе API либо через существующие списки с `include_archived`. Не превращать архивный документ в набор неразрешимых UUID.

### 5.1. Транзакция проведения

1. Проверить аутентификацию, роль и CSRF.
2. Загрузить поступление с блокировкой строки в рамках транзакции запроса. Отсутствие — 404.
3. Если статус уже `posted`, вернуть существующую карточку 200 без изменений, новой истории или обновления времени. Это безопасный повтор после двойного клика или потери ответа.
4. Если статус иной, чем `draft` или `posted`, вернуть 409 без изменения документа.
5. Для `draft` повторно проверить поставщика, каждую строку, материал и его единицу: все существуют и не архивированы; строк хотя бы одна; материалы не повторяются; количества корректны.
6. Атомарно изменить статус на `posted`, обновить `updated_at`, добавить одну запись `draft → posted` в историю.
7. Вернуть успех только после успешного commit. При ошибке откатить все изменения; документ остаётся черновиком, история не пополняется.

Блокировка должна согласовываться с PATCH и DELETE: нельзя проверить `draft`, дождаться чужого проведения, а затем изменить проведённый документ. Проверять статус после получения блокировки. Защитить также проверку архивности и единицы от конкурентных изменений справочников; блокировки брать в стабильном порядке. Не полагаться только на блокировку кнопки во Frontend.

Повторный вызов для `posted` не проверяет заново архивность справочников: архивирование после проведения допустимо. Для MVP естественный ключ операции — ID поступления, запрос проведения не несёт изменяемого содержимого; новый обязательный `Idempotency-Key` и реестр запросов не нужны. Существующее nullable-поле `idempotency_key` сохраняется без использования в новом сценарии.

### 5.2. Валидация, ошибки и права

- `received_at` и временные фильтры принимают ISO 8601 с часовым поясом; даты без пояса отклонять. Номер документа обрезается по краям, непустой, не длиннее 64 символов.
- PATCH не принимает `null` для обязательных полей и пустой набор строк. Переход статуса через PATCH запрещён; неизвестные управляющие поля не должны обходить проведение.
- Сохранить единый формат `{code, message, details, request_id}`. Ошибка ввода — 422, отсутствие — 404, конфликт уникальности/статуса/архивности при проведении — 409, недоступность БД — 503, непредвиденная ошибка — 500. Не выдавать технические подробности клиенту.
- `admin` и `operator` могут создавать, редактировать, удалять черновики и проводить. `reporter` читает документы, историю и отчёты, но не изменяет поступления. Неавторизованный запрос — 401, запрещённая роль или неверный CSRF — 403.
- Реализовать проверки на сервере и соответствующие ограничения UI, используя текущие сессии. Не расширять задачу до переработки всей системы ролей справочников или управления пользователями.

## 6. Отчёт по поставкам

Добавить прикладной модуль `app/entities/supply_report.py` со схемами и SQL-запросами. Отчёт вычисляется из `receipts`, `receipt_items` и справочников; отдельная таблица отчётов или таблица остатков не нужна.

| Метод и путь | Контракт |
| --- | --- |
| `GET /reports/supplies` | Обязательные `from`, `to`; необязательные `supplier_id`, `material_id`; `skip=0`, `limit=100`, диапазон limit 1–1000 |
| `GET /reports/supplies/export` | Те же период и фильтры, CSV по всей выборке без постраничного ограничения |

Правила:

- Только `status = posted`, фильтрация по `received_at` в интервале `[from, to)`, `from < to`.
- Архивность справочников не исключает исторические поступления. Группировать по ID, отображать текущие коды и названия.
- Детальная строка содержит `receipt_id`, `document_number`, `received_at`, `supplier_id`, `supplier_name`, `material_id`, `material_sku`, `material_name`, `unit_id`, `unit_code`, `unit_name`, `quantity`.
- JSON содержит `{items, total, skip, limit, totals}`. `total` — число детальных строк, `totals` — суммы по `(material_id, unit_id)` по всей отфильтрованной выборке, а не текущей странице; включить идентификаторы, названия и `quantity`.
- Порядок строк: `received_at, receipt_id, material_id`. Пустой результат — 200 с пустыми массивами и `total=0`. Несуществующий корректный UUID фильтра даёт пустую выборку.
- Считать суммы в PostgreSQL с десятичной точностью; не объединять разные единицы в общий итог и не называть результат доступным остатком.
- Список, число строк и итоги одного ответа должны соответствовать одному согласованному снимку данных при конкурентном проведении.
- CSV содержит все детальные строки в том же порядке и с теми же полями; заголовок присутствует и при пустой выборке. Формат: UTF-8 с BOM, запятая, стандартное экранирование кавычек и переводов строк, точка в десятичных значениях, даты с поясом. Ответ `text/csv; charset=utf-8`, `Content-Disposition: attachment` с безопасным именем файла.
- Защитить текстовые поля CSV от формул табличных редакторов. JSON и хранимые значения при этом не изменять. Итоги доступны через JSON, отдельные итоговые строки в CSV не добавлять.
- Проверить план запроса на обезличенных данных; использовать существующие индексы и добавлять новые только при обоснованной необходимости.

## 8. Проверка и критерии готовности

Новые тесты по ограничению пользователя не писать; существующие не менять. Проверить следующие сценарии вручную через API и UI в изолированной БД и зафиксировать фактические результаты:

3. Проверить конкуренцию проведения с PATCH и DELETE: ни один сценарий не изменяет или удаляет уже проведённый документ.
4. Проверить отрицательное/нулевое количество, более трёх десятичных знаков, пустые строки, дубль материала, дубль номера у поставщика, дату без пояса и PATCH с недопустимыми полями.
5. Архивировать справочник после сохранения черновика: проведение отклоняется без смены статуса и истории. Архивирование после проведения не убирает строки из отчёта и не ломает повторный запрос проведения.
6. Проверить запрет смены единицы использованного материала и удаления используемых справочников, включая конкурентные действия.
7. Проверить отчёт на границах периода, по каждому фильтру, с архивными ссылками, разными единицами и несколькими страницами. Суммы `0.100 + 0.200` дают `0.300`. Черновики не входят; CSV включает строки за пределами первой страницы, корректно передаёт кириллицу и кавычки.
8. Проверить права всех трёх ролей, отсутствие сессии и неверный CSRF. Доступ reporter не позволяет изменять поступления прямым HTTP-запросом.
9. Проверить отказ БД и откат транзакции проведения в изолированном окружении: нет частично записанной истории или ложного успеха. Не останавливать рабочую БД пользователя.
10. Применить миграции на пустой БД и на копии схемы предыдущей ревизии с обезличенными связанными данными; подтвердить сохранение значений и работоспособность нового API.

Запустить доступные существующие проверки: `make verify LOCAL=1`, а для Frontend из `frontend/` — `pnpm quality`, `pnpm build`. Не менять окружение доставки и проверки ради результата. Если общий запуск уже выполняет часть проверок, не дублировать их без причины. При отсутствии инструментов/изолированного окружения указать конкретные пропуски: критерии остаются незавершёнными. Ошибки, пороги покрытия и необходимость новых тестов нельзя скрывать ручной демонстрацией.

Готовность функциональности означает выполнение перечисленных сценариев и согласованность API с UI. Она не означает успешный CI, разрешение на слияние, выпуск или состоявшуюся человеческую приёмку. При запрете добавлять тесты достаточность автоматического покрытия остаётся отдельным ограничением, которое нужно явно отразить в отчёте.

## 9. Порядок работы, данные и передача результата

1. Прочитать [README](README.md), [исходное ТЗ](docs/Техническое_задание.md), [AGENTS.md](AGENTS.md) и ближайшие инструкции. Проверить Git и актуальный head миграций; сохранить чужие изменения, работать в отдельной ветке `codex/`.
2. Реализовать модель истории и миграцию, затем атомарное проведение и недостающие операции документов, отчёт и CSV, затем подключить Frontend. При вопросах остановиться и обратиться к пользователю.
3. Выполнить разрешённые проверки. Проверить diff: кроме прикладных файлов и миграций запрещённые категории не изменены; `git diff --check` не сообщает ошибок.
4. Подготовить описание PR/MR: задача без выдуманного номера, согласованное упрощение, результат, реальные проверки, ограничения, список критических файлов и влияние на данные. Не создавать впечатление, что PR уже открыт, если это не так.
5. Миграции отдельно перечислить как критические изменения. Для отката предпочесть возврат приложения при сохранённой совместимой схеме и истории. Удаление заполненной истории через downgrade разрушительно: не выполнять без отдельного разрешения; проверку downgrade проводить только на изолированных одноразовых данных. Новые проведённые документы при откате приложения сохранять.
6. В итоговом отчёте указать изменённые файлы, маршруты, ревизии, результаты API/UI и миграционных проверок, пропуски и причины, оставшиеся риски. Независимое одобрение, CI и выпуск не заменять собственной оценкой.

Ожидаемый результат работы Terra — реализация описанной функциональности в API, миграциях и Frontend. Задание не разрешает менять тесты, Docker или существующие инструкции даже ради завершения общего MVP.
