## 2. Источники требований и согласованный MVP

Перед работой прочитать [AGENTS.md](AGENTS.md), [README.md](README.md), [исходное ТЗ](docs/Техническое_задание.md), [описание API](docs/API.md), [ТЗ интерфейса](docs/WEB_UI_CODEX_SPEC.md), этот файл и ближайшие инструкции. Исходники и OpenAPI использовать для понимания реализации; не считать любую текущую реализацию правильным ожидаемым поведением.

Пользователь ранее согласовал упрощение, которое сохраняется для тестирования:

- Один склад; справочники единиц, материалов, поставщиков; поступления и их строки.
- Проведение синхронное: `draft → posted` одной транзакцией PostgreSQL вместе с историей статуса.
- Повторное проведение того же документа безопасно и не создаёт вторую историю или повторный учёт.
- Только черновик можно редактировать и удалять; проведённый документ неизменяем.
- Отчёт и CSV строятся только по проведённым поступлениям; доступные остатки не вычисляются.
- RabbitMQ, outbox, worker, DLQ и фоновые повторы исключены. Не писать тесты, требующие их появления.
- Существующие поля и старые статусы в БД сохраняются для совместимости; их наличие не означает разрешение нового асинхронного сценария. Для `queued`, `processing`, `failed` проведение возвращает конфликт без преобразования данных.

Эти согласованные решения имеют приоритет над прежними требованиями об очереди. Иные расхождения между документацией и реализацией не разрешать молча. Ошибки, очевидные из согласованного сценария, проверять тестами правильного поведения, а не закреплять как норму.

## 5. Архитектура тестов и безопасное окружение

### 5.1. Разделение уровней

- **Backend unit:** чистая валидация, периоды, форматирование CSV, пароли и преобразования без БД, Docker, HTTP-сервера и внешней сети. Если импорт требует настроек, использовать обезличенные тестовые значения без соединения с БД. Не переносить чистые функции из приложения ради удобства теста.
- **Backend integration:** реальный FastAPI и PostgreSQL, схема из Alembic; отдельно проверять ответ HTTP и состояние после commit/rollback новой сессией.
- **Frontend unit/component:** Vitest и Testing Library, пользовательские события, доступные имена элементов, типизированные ответы.
- **Frontend integration:** страница + Router + AuthProvider + QueryClient + настоящий API-клиент; подменять только HTTP-границу. Не мокировать сами проверяемые hooks, мутации и инвалидацию кэша. Такие тесты не называть интеграцией с реальным Backend.
- **Container integration:** реальный HTTP к приложению в Docker и реальная БД; отдельно проверка сборки/доступности Frontend и проксирования. HTTP-проверка страницы не заменяет браузерную проверку интерфейса.

### 5.2. Фикстуры и изоляция

1. Разнести общие и DB-фикстуры по областям. Запуск `tests/unit` должен работать при недоступном PostgreSQL, без DB-очистки и соединений. Для отдельного unit-прогона не выдавать частичное покрытие за выполнение общего порога; итоговый порог проверяется на полном наборе.
2. Для интеграций требовать `APP_ENV=test`, явные `DATABASE_URL`/`TEST_DATABASE_URL` и совпадение разобранных адресов. Имя БД проверять через URL parser: точный суффикс `_test` или контролируемое имя временной БД, а не наличие подстроки в пароле/хосте.
3. Схему создавать миграциями, не `Base.metadata.create_all()`. Очистку всех бизнес-таблиц и истории выполнять только после проверки тестовой цели; служебную Alembic revision сохранять.
4. Данные фабрик обезличенные и детерминированные; время и UUID фиксировать там, где от них зависит ожидаемый результат. Не читать реальный `.env`, дампы и рабочую БД.
5. Пользователей трёх ролей создавать тестовой фабрикой в изолированной БД; вход выполнять через настоящий auth API. Не добавлять API управления пользователями и не обходить проверяемую авторизацию dependency override.
6. Конкурентные тесты используют отдельные соединения/сессии и отдельные HTTP-клиенты. Одна общая rollback-транзакция не подходит для проверки видимого commit.
7. Синхронизация гонок — события, барьеры и блокировки с ограниченными тайм-аутами. Не основывать результат на случайном `sleep`; зависание — ошибка проверки. Все ресурсы освобождать в `finally`.
8. Frontend: новый QueryClient на тест, сброс сессии/CSRF, mocks, таймеров, Router и DOM. Отключать автоматические retry только в тестовом QueryClient для детерминизма, не в приложении.
9. Не вводить параллельный DB-прогон без независимой БД на worker. Очистка одной БД не должна затрагивать другой тест или независимый запуск.

### 7.3. Права и ошибки

- I15: параметризованная матрица `admin`, `operator`, `reporter`, аноним. Admin/operator изменяют поступления; reporter только читает поступления, историю, отчёты и CSV. Мутации reporter — 403, отсутствие сессии — 401, неверный/отсутствующий CSRF — 403.
- I16: валидация — 422, отсутствие — 404, конфликт — 409, временная недоступность БД — 503, непредвиденная ошибка — 500; единый JSON и request ID. Прямые ограничения БД проверять отдельно от API-валидации.
- I17: управляемая ошибка записи истории, flush и commit. После отказа нет сочетания «posted без новой истории» или «история при draft». Для ошибки commit нельзя мокировать endpoint целиком: внедрять отказ на границе соединения/сессии и проверять данные независимой сессией.
- Для HTTP 500 использовать клиент, позволяющий исследовать HTTP-ответ, а не только поднятое исключение сервера. Отдельно различать управляемую инъекцию отказа и реальный отказ соединения с PostgreSQL; подтвердить восстановление после устранения отказа.

### 7.4. Конкурентность

- C01: два одновременных проведения — одна история, posted, количества не удваиваются.
- C02: проведение против PATCH. Если PATCH завершился первым, проводится обновлённый документ; если проведение первым — PATCH отклоняется. Недопустимо изменение после зафиксированного posted.
- C03: проведение против DELETE. Допустимы удалённый черновик с 404 у проведения либо posted с конфликтом удаления. Не допустимы потеря проведённого документа и осиротевшая история.
- C04: проведение против архивирования поставщика/материала/единицы; проверить обе управляемые последовательности. Архивирование до проведения блокирует его, после проведения сохраняет исторический документ.
- C05: добавление строки против смены единицы материала. После первого использования единица неизменна; результат должен соответствовать последовательному выполнению одной из операций первой.
- C06: проведение во время формирования отчёта — `items`, `total`, `totals` относятся к одному согласованному снимку. Синхронизировать запросы наблюдением SQL/барьерами, не подменять результаты SQL.

Проверять наблюдаемые инварианты и отсутствие необработанных ошибок, а не конкретный порядок взятия блокировок. Для критических гонок повторить целевой прогон несколько раз как проверку воспроизводимости, не превращая весь suite в нагрузочный тест.

## 8. Отчёт и CSV: интеграционные данные и ожидания

Подготовить небольшой фиксированный набор: два поставщика, минимум три материала и две разные единицы; несколько документов draft и posted; значения `0.100` и `0.200`; документы до начала, точно на начале, внутри и точно на конце периода. Дополнительно набор больше размера страницы. Ожидаемые строки/суммы задать независимо от проверяемой реализации.

- R01: `GET /reports/supplies` включает только posted в `[from,to)` по `received_at`; начало включено, конец исключён. Проверить часовые пояса и обязательность периода.
- R02: поставщик, материал и их сочетание; корректный неизвестный UUID фильтра даёт пустую выборку. Проверить пустой отчёт, неправильную пагинацию, отсутствие обязательных границ.
- R03: группировка по `(material_id,unit_id)`; разные материалы с одинаковыми именами не объединяются, разные единицы не суммируются. `0.100 + 0.200 = 0.300`, quantity в JSON — строка.
- R04: `total` считает строки, а `totals` — всю выборку независимо от skip/limit; страницы не теряют/не дублируют строки при равных датах. Архивные справочники остаются в отчёте, переименование отображается текущим именем.
- R05: `/reports/supplies/export` использует те же фильтры, экспортирует все строки за пределами первой страницы, а не только открытый UI-фрагмент. Сверить с независимым ожидаемым набором.
- R06: Content-Type, Content-Disposition, UTF-8/BOM, заголовки, пустой файл с заголовком, экранирование текстов и формул, точность количеств, даты с поясом. CSV не содержит лишних суммирующих строк.

Не сравнивать два одинаково ошибочных endpoint как единственное доказательство правильности. Для SQL NUMERIC учитывать, что PostgreSQL может округлять входной scale: требование отклонять лишние знаки проверять на API, а в БД — фактические CHECK, precision, scale, FK и UNIQUE. Не требовать от схемы несуществующего ограничения.

## 9. Миграции

Добавить проверки текущего head, не изменяя миграции. Временные БД создавать с уникальным контролируемым именем и удалять только собственные цели.

| ID | Сценарий |
| --- | --- |
| M01 | Единственный head, непрерывная цепочка; upgrade пустой БД до head; все ожидаемые таблицы и Alembic revision |
| M02 | Состояние `f4a6c8d0e003`: заполнить справочники, пользователей/сессии, черновики и posted со строками; upgrade до `a5b7c9d1e004`; сравнить ID, связи, статусы, количества, даты и прежние поля |
| M03 | История: таблица, обязательные колонки, FK, UNIQUE receipt_id, индекс `(receipt_id,changed_at,id)`, TIMESTAMPTZ; старым документам не выдумываются переходы |
| M04 | Реальные SQL-вставки: запрет второй истории на receipt_id, отсутствующего receipt_id, отрицательного/нулевого количества, дублирующих строк и номера поставщика; rollback после нарушения |
| M05 | Повторный upgrade head безопасен; соответствие metadata/схемы проверяется Alembic check; новую историю можно создать через API после upgrade |
| M06 | Downgrade последней ревизии и повторный upgrade только на одноразовой БД; бизнес-таблицы сохраняются. Отдельно показать, что downgrade удаляет историю, а не обещать её восстановление |

Перед M02 сверить актуальные ревизии. Если появились новые, включить актуальную пару предыдущая/head и сохранить значимую регрессию для миграции истории. Для M06 удаление тестовой истории допустимо только внутри явно одноразовой БД; это не разрешение на downgrade рабочей системы.

## 10. Frontend unit и интеграционные проверки

Использовать существующие Vitest, Testing Library и user-event. HTTP-моки держать на уровне fetch либо совместимого тестового адаптера. Непредусмотренный запрос должен падать, а не уходить в сеть. Не проверять только наличие заголовка страницы или snapshot.

| ID | Область | Ожидаемое поведение |
| --- | --- | --- |
| F01 | API-клиент | URL, method, body, cookie credentials, CSRF только для мутаций, request ID, 204, JSON-ошибки/не-JSON/сеть, AbortSignal |
| F02 | Blob-клиент | Успешный CSV читается как Blob; HTTP-ошибка не скачивается как файл; request ID и сообщение доступны пользователю |
| F03 | Auth/Router | Вход, выход, загрузка сессии, защищённые маршруты, профиль; авторизация восстанавливается через API, данные пользователя не смешиваются |
| F04 | Справочники | Создание, редактирование, поиск, пагинация, архивирование, права на purge, серверная ошибка и сохранность ввода; старые тесты сохраняются |
| F05 | Черновик | Несколько строк, добавление/удаление, запрет дублей, единица материала, количество как строка, дата с поясом, создание и редактирование сохранённого документа |
| F06 | Выбор справочников | Выбор активных записей, возможность получить элементы за первой страницей, видимость архивных ссылок в старом документе |
| F07 | Проведение/удаление | Подтверждение и отмена, отсутствие запроса при отмене, блокировка во время запроса, повтор после неопределённого сетевого результата, запрет редактирования posted |
| F08 | Кэш/история | После проведения обновляются список, карточка, уже загруженная история и затронутый отчёт; ошибка/загрузка истории не отображаются как её отсутствие |
| F09 | Права | Reporter не получает кнопки записи; admin/operator получают допустимые действия; серверный 403 отображается, запрет не сводится к UI |
| F10 | Отчёт | Период и фильтры из URL, изменение фильтра сбрасывает страницу, пагинация, состояние до выбора периода/загрузка/пустой результат/ошибка, точные серверные итоги |
| F11 | CSV | Запрос с применёнными фильтрами, создание/освобождение object URL, безопасное имя файла; отдельная видимая ошибка скачивания, отсутствие ложного успеха |
| F12 | Оболочка | Рабочая навигация к новым разделам; нет требований очереди для MVP; health-состояния и API-ошибки отображаются без фиктивных данных |

Для недоступной в UI функции писать тест ожидаемого действия через DOM, который воспроизводит отсутствие возможности; не импортировать несуществующий модуль так, чтобы сломать сбор всего набора. Даты проверять в контролируемом поясе, количества — без преобразования во float. Ошибки и ввод проверять через видимый интерфейс, а не внутренний state компонента.

## 11. Docker и команды запуска

На Windows доступен [отдельный Linux test-образ](docs/UNIX_TESTS.md), запускающий Backend, Frontend и миграции. Он не заменяет полный verify. После изменения исходников образ необходимо пересобрать.

Текущий обязательный интерфейс — `make ... DOCKER=1`; `LOCAL=1` не использовать. Перед запуском изучить актуальный Makefile, Compose и стадии Dockerfile: команды могут создавать/удалять тестовые ресурсы.

- Использовать уникальный `DOCKER_RUN_ID` и один и тот же ID во всех командах своего прогона. Не затрагивать production Compose-проект и чужие контейнеры/тома.
- Основной набор: `make test DOCKER=1 DOCKER_RUN_ID=<id>`, `make migration-check DOCKER=1 DOCKER_RUN_ID=<id>`, `make container-smoke DOCKER=1 DOCKER_RUN_ID=<id>`; для финальной оценки — `make verify DOCKER=1 DOCKER_RUN_ID=<id>` с нужными prerequisites.
- `make test` должен действительно выполнять Backend и Frontend и сохранять ненулевой exit code при падении любого теста. Не заменять его фиктивной успешной целью.
- Тестовые контейнеры используют PostgreSQL и Alembic, закреплённые зависимости и локальные фикстуры. Не требуется RabbitMQ. Не копировать реальные `.env` или данные в образы.
- Контейнерный HTTP-сценарий: readiness → авторизация → справочники → многопозиционный черновик → проведение → повтор → история → JSON/CSV. Проверять фактические ответы и данные, а не только код 200.
- Frontend должен проходить тесты и production-сборку (`pnpm build`) из актуальных исходников. Доступность страницы через Vite/proxy проверять отдельно от jsdom-тестов.
- Сохранять JUnit Backend и Frontend в разных файлах, coverage и логи отказов наружу, в `reports/`, включая неуспешный запуск. Проверить, что отчёт не остался только внутри удалённого контейнера.
- Проверить очистку после успеха и отказа. Общий pnpm-кэш не удалять как будто он одноразовые данные БД.
- Сканирование должно относиться к тому же image ID, на котором прошёл smoke. Несовпадение или жёстко заданный чужой тег — дефект проверочного контура; не объявлять образ проверенным.

Особенность текущего `make verify`: после проверок вызывается `make up`. Учесть этот побочный эффект, не принимать повторно поднятый тестовый контур за утечку внутри завершённой проверки; после наблюдения результата убрать только ресурсы своего запуска штатной командой. Не запускать команды в режиме production по умолчанию.

Если общий verify остановился на уже существующем lint/typecheck/другом дефекте, сохранить полный результат и отдельно выполнить независимые тестовые команды для диагностики. Это не отменяет отказ verify. Не менять продуктовый код или правила качества ради прохождения. Если неисправен сам тестовый стенд и его исправление выходит за минимальную настройку запуска новых тестов — зафиксировать и спросить пользователя.

## 12. Покрытие и качество тестов

- Сохранить backend-порог 80% и существующий сбор ветвей. Не сужать `source` и не исключать новые модули поступлений/истории/отчёта. Итоговое покрытие оценивать по полному набору, включая падающие тесты, если отчёт сформирован.
- Подключить отчёт покрытия Frontend совместимым с закреплённой версией Vitest dev-провайдером и обновить lock-файл. Включать рабочие `.ts/.tsx`, а не только импортированные тестами файлы; явно описать исключения деклараций и тестовых файлов. Не приписывать Frontend существующий порог, которого сейчас нет; привести реальные метрики и непокрытые критические ветви.
- Покрытие строк/ветвей не заменяет проверки поведения. Обязательны положительные, отрицательные и rollback-сценарии матрицы.
- Сохранить существующие mutation-проверки. В критических проверках проведения/отчёта показать, что удаление проверки статуса, записи истории или фильтра posted обнаруживается тестами; выполнять временные мутации только в изолированной копии/контейнере, не оставляя изменений приложения в рабочем diff.
- Ошибка подготовки, timeout и отсутствие выполненных тестов не считаются успешно обнаруженной мутацией.
- Не принимать «всё зелёное» без сверки числа collected/passed/failed/skipped и фактически выполненных сценариев. Не добавлять необоснованные skips/xfails для отсутствующих функций.

## 13. Перечень дефектов и отчёт

В `TEST_DEFECTS.md` включить:

1. Исходный commit SHA, ветку, версии инструментов, ревизию БД и идентификаторы тестовых образов без секретов.
2. Матрицу ID U/I/C/R/M/F → файл и конкретный тест → результат: passed / failed / blocked / not run. Не смешивать неподтверждённое предположение с воспроизведённым дефектом.
3. Точные команды и exit code, сводку тестов и покрытия, пути к отчётам, результаты полного verify и отдельных диагностических запусков.
4. Карточки дефектов со следующими полями:

   - локальный ID `DEF-001` и далее, без выдуманного номера трекера;
   - приоритет и влияние на пользователя/данные;
   - источник ожидаемого требования и ID сценария;
   - минимальные обезличенные данные и шаги/команда воспроизведения;
   - ожидаемый и фактический результат;
   - имя падающего теста, выдержка ошибки или ссылка на артефакт;
   - статус подтверждения и сведения о повторном воспроизведении;
   - затронутая область и краткое направление отдельной задачи на исправление, без патча.

5. Блокировки окружения отдельно от дефектов продукта и ошибок самих тестов. Новый неверный тест/фикстуру исправить в этой задаче; правильный тест на ошибку приложения оставить падающим.
6. Непокрытые сценарии и причины, риски для приёмки, перечень изменённых критических конфигураций с обоснованием.

Новый прогон не должен подменять описание требований текущим дефектным поведением. Если API и документация расходятся так, что правильный результат не определён согласованными правилами, остановиться для уточнения.

## 14. Порядок выполнения и критерии завершения

1. Проверить Git, сохранить чужие изменения и работать в отдельной ветке `codex/`. Зафиксировать исходный SHA и baseline существующих проверок без исправления приложения.
2. Составить инвентаризацию существующих тестов и связать их с матрицей этого задания; не дублировать уже достаточные проверки.
3. Разделить unit/DB-фикстуры, подготовить изолированные данные, добавить проверки последовательно: прежние контракты → проведение/история → отчёты → миграции/конкурентность → Frontend → контейнерный сценарий.
4. Запустить целевые проверки и полный набор; повторить затронутые проверки после изменения тестов/фикстур. Для воспроизводимых продуктовых дефектов добавить карточки, не чинить приложение.
5. Проверить `git diff --check` и границы diff: продуктовый код, миграции и production-конфигурации не изменены. Перечислить изменения тестовых конфигураций, Make/Docker и скриптов как критические для независимой проверки.
6. Подготовить описание PR/MR с задачей, матрицей, результатами, дефектами и ограничениями. При красных обязательных проверках не утверждать готовность к слиянию. Не обходить независимое одобрение.

Задание считается выполненным, когда для всех применимых обязательных сценариев есть реализованные проверки и фактический результат либо явно описанная блокировка; повторные и конкурентные сценарии воспроизводимы; отчёты доступны; перечень дефектов проверяем; приложение не исправлялось. Незапущенные проверки остаются незавершёнными критериями проверки продукта, даже если причина подробно описана.

В финальном сообщении указать изменённые файлы, число и результаты тестов, покрытие, подтверждённые дефекты, ограничения и путь к `TEST_DEFECTS.md`. Не объявлять CI, выпуск, исправление дефектов или человеческую приёмку состоявшимися без подтверждения.
