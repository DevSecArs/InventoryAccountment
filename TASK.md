# Техническое задание: устранение предупреждений backend-тестов

Исполнитель: ИИ-агент 6.0 Luna. Номер задачи отсутствует, задача в трекере и PR
не создавались. Этот документ полностью заменяет предыдущий TASK.md.

## 1. Цель и решения пользователя

Устранить причины всех перечисленных ниже предупреждений при запуске существующих
backend-тестов. Сохранить поведение приложения, API и тестового окружения.

Согласовано:

- Разрешены только необходимые изменения backend-зависимостей и backend/uv.lock.
  Массовое обновление пакетов не разрешено.
- Устранить все перечисленные предупреждения, включая исходящие из зависимостей.
- Не вводить постоянную политику warnings-as-errors.
- Не изменять и не дополнять существующие тесты, не создавать новые тестовые файлы.
- Комментарии и docstring нового кода — на русском языке; строго соблюдать
  Keep It Simple, Stupid! (KISS), Don't Repeat Yourself (DRY), SOLID.

## 2. Перед работой

Прочитать актуальные AGENTS.md, README.md, backend/pyproject.toml, backend/uv.lock,
затронутые модели, HTTP-обработчики и тестовые точки входа/фикстуры.
Проверить Git и работать в отдельной ветке codex/. Сохранить чужие изменения.
Не полагаться на старые результаты проверок и предполагаемые версии библиотек.

Проверить фактически установленные версии и воспроизвести предупреждения в текущем
тестовом контейнере. При подготовке задания lock-файл содержал FastAPI 0.141.1,
Starlette 1.6.0, HTTPX 0.28.1, AnyIO 4.15.1 и Pydantic 2.13.5; это исходные
ориентиры, а не предписание использовать именно эти версии в исправлении.

Если make test/тестовая Docker-конфигурация ещё не реализованы в актуальной копии,
использовать доступный способ запуска существующих тестов на отдельной тестовой БД.
Не реализовывать инфраструктурные задачи из прежних TASK.md ради этого задания.

## 3. Перечень предупреждений и требуемые изменения

### 3.1. Pydantic: class-based Config

Сообщение: `PydanticDeprecatedSince20: Support for class-based config is deprecated,
use ConfigDict instead`.

Модели из предоставленного лога:

- backend/app/entities/auth.py — UserResponse;
- backend/app/entities/unit.py — UnitResponse;
- backend/app/entities/material.py — MaterialResponse;
- backend/app/entities/receipt_status_history.py — ReceiptStatusHistoryResponse;
- backend/app/entities/supplier.py — SupplierResponse;
- backend/app/entities/receipt.py — ReceiptItemResponse, ReceiptResponse.

Заменить устаревшие вложенные class Config современным model_config = ConfigDict(...).
Переиспользовать уже имеющиеся импорты ConfigDict; добавлять импорт только там,
где он необходим. Сохранить from_attributes=True и все остальные действующие
параметры каждой модели. Проверить, нет ли других таких конфигураций в backend/app,
порождающих тот же вид предупреждения; менять только относящиеся к этой причине.

Сохранить сериализацию ORM-объектов, поля, обязательность, aliases, типы,
значения по умолчанию и JSON-представление, включая Decimal и даты.
Не вводить общую базовую модель ради замены семи коротких конфигураций:
простое локальное исправление предпочтительнее изменения иерархии моделей.

### 3.2. HTTP 422: устаревшее имя константы

Сообщение: `StarletteDeprecationWarning: HTTP_422_UNPROCESSABLE_ENTITY is deprecated.
Use HTTP_422_UNPROCESSABLE_CONTENT instead`.

Найти обращения к устаревшему имени в коде backend и заменить современным
HTTP_422_UNPROCESSABLE_CONTENT, если соответствующая константа предоставляется
согласованной версией используемых библиотек. Не заменять диагностируемое
обращение магическим числом только для сокрытия предупреждения.

Числовой статус остаётся 422. Сохранить форму JSON-ошибок, request_id, детали
валидации и описание ответов в API. Если предупреждение порождается исключительно
внешней библиотекой, устранить его через согласование зависимостей по разделу 4.
Существующие тесты и их ожидания не менять.

### 3.3. TestClient и HTTPX

Сообщение из fastapi/testclient.py: `Using httpx with starlette.testclient is
deprecated; install httpx2 instead`.

Определить по исходникам установленного FastAPI/Starlette и официальной
документации, какие клиентские зависимости реально поддерживаются этими версиями.
Проверить, является ли httpx2 официальным поддерживаемым пакетом для используемого
TestClient, его источник и совместимость; не добавлять пакет только по тексту
предупреждения и не придумывать существующие версии.

Выбрать минимальное подтверждённое решение: подключение официально поддерживаемой
тестовой зависимости либо узкое согласование FastAPI/Starlette и клиента.
Предпочесть вариант, сохраняющий существующие импорты TestClient и тестовый код.
Не заменять импорты во всех тестах: пользователь не разрешил править тесты.
В существующих tests/integration/test_api_catalogs.py и test_receipts.py
есть прямой импорт Response из httpx: сохранить его работоспособность без
редактирования тестов. Установка httpx2 не означает автоматическое разрешение
удалить прямую зависимость httpx.
HTTPX может использоваться другими dev-инструментами транзитивно; не требовать
его полного удаления из lock-файла, если он больше не является причиной предупреждения.

### 3.4. AnyIO BlockingPortal внутри Starlette

Сообщение из starlette/testclient.py: `DeprecationWarning: The anyio.abc.BlockingPortal
alias is deprecated, use anyio.from_thread.BlockingPortal instead`.

Источник находится во внешней библиотеке. Выбрать совместимый официальный
релиз/набор версий, в котором устаревший импорт не используется или соответствующее
предупреждение отсутствует вследствие корректной совместимости API.
Проверить совместно с исправлением TestClient, а не подбирать версии независимо.

Не редактировать site-packages, не добавлять monkeypatch, локальную копию Starlette,
подмену sys.modules, собственный TestClient и прочие обходные решения.

## 4. Работа с зависимостями

- Проверить ограничения FastAPI → Starlette → AnyIO/клиент и требования Python
  текущего проекта. Использовать официальные исходники, release notes и документацию
  как подтверждение совместимости, когда информации в установленных исходниках
  недостаточно. В отчёте привести основания выбранного изменения и ссылки при наличии.
- Обновлять только необходимые прямые/транзитивные пакеты. Не выполнять безусловное
  обновление всего lock-файла до последних версий.
- Перегенерировать backend/uv.lock штатным uv с минимальным целевым изменением.
  Не редактировать вручную хеши, URL пакетов и граф разрешения.
- Сохранить extra dev, конфигурацию uv overrides и остальные инструменты.
  Не удалять тестовые зависимости без проверки их фактической необходимости.
- Не выбирать заведомо уязвимые/несовместимые версии ради исчезновения warnings.
  Не делать широкий downgrade стека для маскировки проблемы.
- Подтвердить locked-установку в существующем тестовом окружении. Показать,
  какие версии изменились и какие транзитивные изменения были неизбежны.
- Если официальное совместимое исправление всех внешних предупреждений невозможно
  без изменения тестов, дополнительных файлов или более широкого обновления,
  не обходить ограничения: выполнить независимые исправления, объяснить конкретное
  препятствие и запросить разрешение на необходимое расширение. Не считать задачу
  выполненной, пока часть перечисленных предупреждений остаётся.

## 5. Допустимые изменения и запреты

Разрешены изменения только затронутых моделей/обработчиков backend/app,
backend/pyproject.toml и backend/uv.lock в пределах перечисленных причин.
Остальные исходники backend/app менять только при прямой связи с теми же warnings.
Сводку результата дать в финальном сообщении, отдельный документ не создавать.

Не менять существующие тесты, backend/tests/main.py или старую test/main.py,
фикстуры, Makefile, Docker/Compose-файлы, frontend, схему БД и миграции.
Не добавлять новые файлы, инструкции, зависимости без прямой необходимости.
Не создавать тестовые модули и не переписывать проверки под новый результат.

Запрещены filterwarnings, warnings.filterwarnings, simplefilter(ignore),
PYTHONWARNINGS=ignore, --disable-warnings и иные способы скрыть предупреждения
вместо устранения причины. Не уменьшать объём тестов и порог покрытия 80%.
Не вводить постоянный -W error или новую политику предупреждений в конфигурации.
Сохранять обычный вывод warnings, чтобы отсутствие сообщений можно было проверить.

## 6. KISS, DRY, SOLID

Комментарии и docstring, если добавляются/меняются, писать на русском языке,
идентификаторы — на английском. Комментарии объясняют нетривиальные решения,
не повторяют очевидный код.

Строго следовать KISS, DRY и SOLID соразмерно задаче совместимости:
локальная миграция конфигурации моделей, единый согласованный набор зависимостей,
сохранение разделения ответственности. Не создавать абстракции, адаптеры,
иерархии и совместимые обёртки там, где достаточно штатного API библиотеки.

## 7. Проверка и критерии приёмки

1. Исходные предупреждения воспроизведены либо факт невоспроизведения честно
   зафиксирован с версиями и командой. Не объявлять устранение только по поиску текста.
2. Во всех затронутых моделях нет class-based Config; from_attributes и прочие
   параметры сохранены. ORM-сериализация проверяется существующим набором тестов.
3. Устаревшая константа 422 не используется в исполняемом коде проекта;
   соответствующие API-ответы по-прежнему имеют статус 422 и прежний контракт.
4. TestClient работает без перечисленных предупреждений HTTPX и BlockingPortal;
   тестовые импорты/фикстуры не изменены, site-packages не патчится.
5. Установка по backend/uv.lock проходит без его модификации; необходимые
   изменения зависимостей согласованы и объяснены, нет массового обновления.
6. Полный существующий набор backend-тестов проходит в изолированной тестовой БД.
   В итоговых логах нет всех четырёх перечисленных видов предупреждений,
   включая семь предупреждений моделей и повторения HTTP 422.
7. Порог покрытия 80% сохранён и выполнен. Нет скрытых предупреждений,
   ослабления тестов и постоянной новой политики warnings-as-errors.
8. Выполнены применимые Ruff/mypy и проверка затронутых импортов. Проверить
   отсутствие новых проблем зависимостей доступным audit-инструментом; не
   отключать проверки при отказе. Если окружение/сеть мешают, указать причину.
9. git diff --check проходит; изменены только разрешённые файлы.

Использовать make test, если он уже реализован и действительно запускает
все backend-тесты, либо существующий эквивалентный способ с тем же набором.
Проверять на отдельной тестовой БД: интеграционные фикстуры выполняют TRUNCATE.
Рабочие контейнеры/данные не изменять ради проверки. При необходимости пересборки
собирать только тестовый образ из существующей конфигурации, не менять Docker-файлы.
Не добавлять новые постоянные тесты: пользователь это явно отложил.
