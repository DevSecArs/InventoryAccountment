# ТЗ: frontend только из статических файлов, удаление pnpm и frontend-проверок

Исполнитель: ИИ-агент 6.0 Luna. Полностью заменяет прежний TASK.md.
Задача без номера. Это реализация согласованного сокращения frontend-контура,
а не миграция на npm или другой пакетный менеджер.

## 1. Решения пользователя и процесс

Прочитать AGENTS.md, README.md и более близкие инструкции. Проверить Git и
сохранить чужие изменения. Работать в текущей ветке frontend/native-js-migration,
не создавать и не переключать ветки; не делать commit/push и не создавать PR.

Пользователь явно разрешил удалить все frontend-тесты и проверки, пороги их
покрытия, линтер и frontend SAST, аудит зависимостей и кеш pnpm. Это конкретное
решение имеет приоритет над прежним запретом удаления тестов и frontend-порогами.
Не распространять разрешение на backend-тесты, backend-порог 80%, Ruff/mypy/
Bandit/pip-audit и инфраструктурные защитные проверки.

Frontend содержит только статические HTML/CSS/JS и необходимые локальные assets.
Без pnpm, npm, yarn, Bun, package.json/lock/workspace, node_modules,
конфигураций линтера/сборки/тестов, dev-инструментов и собственного package manager.
Не заменять ESLint другим линтером или Vitest/node:test другим test runner.
Backend и его инструменты не подпадают под запрет frontend-зависимостей.
Не создавать новых инструкций и посторонних файлов; изменять существующий README.

## 2. Функциональность сохраняется

Не менять поведение пользователей, дизайн, SPA/History API, текущие URL, cookies,
CSRF, роли, API-клиент, валидацию, отчёты/CSV, справочники и поступления.
Не удалять browser-runtime код, используемый приложением, вместе с тестовыми
helpers. Сохранить локальные SVG/CSS и ES modules, отсутствие внешних библиотек.
Статические файлы по-прежнему отдаёт non-root Nginx на порту 8080; backend
балансируется как прежде. Backend API, миграции, БД и рабочие данные не менять.

## 3. Удаление frontend-инструментов

1. Удалить frontend/package.json, pnpm-lock.yaml, pnpm-workspace.yaml,
   frontend/eslint.config.js и остальные фактически оставшиеся конфигурации
   исключительно frontend-проверок. Ничего не заменять package-lock.json.
2. Удалить frontend/tests, setup/helpers для тестов и все frontend test/spec файлы,
   сохранив рабочие модули. Удалять именно существующие файлы по проверенным путям,
   не применять широкие маски, захватывающие runtime или backend.
3. Удалить локальные node_modules/кеши только при необходимости: сначала проверить
   абсолютную цель внутри frontend и отсутствие пользовательских данных.
   Игнорируемые локальные каталоги не считать tracked изменениями и не очищать
   принудительно ради diff. Не использовать git clean/reset.
4. Удалить frontend coverage/junit/LCOV генерацию, пороги и разбор этих отчётов.
   Не удалять сохранённые исторические пользовательские reports.
5. Удалить pnpm install/config/audit/lint и cache mounts, установку Node/pnpm,
   test stage/service frontend-test из тестового Dockerfile/Compose.
   Удалить frontend-sast stage/service и его frontend-only конфигурацию/fixtures.
   Если файл используется backend/общей проверкой, сохранить и сузить назначение.
6. Адаптировать тестовый .dockerignore, проверки исходных путей и копирование.
   Не оставлять COPY удалённых manifests/tests и ожидание удалённых сервисов.
   Не исключать frontend/src/features/reports: это рабочая страница отчётов.
7. Убрать pnpm-специфичные правила workspace-copy, parser/report стадии и тесты
   этих стадий. Сохранить необходимую защиту от случайного копирования локальных
   артефактов/секретов общими правилами, без мёртвых упоминаний pnpm.

## 4. Makefile и security

- make test: только backend с отдельной тестовой БД, миграциями, существующим
  main.py и мутационными проверками. Сохранить отчёты/cleanup и код ошибки.
- make quality: только backend Ruff/format/mypy/Bandit и уже действующие
  backend-проверки. Никаких frontend lint, typecheck, node:test и Semgrep.
- make security: удалить pnpm audit/frontend dependency audit и frontend SAST,
  обработку их JSON, summary stages и связанные фикстуры. Сохранить backend
  pip-audit и действующие общие проверки Gitleaks/Trivy.
- Глобальный Gitleaks продолжает защищать репозиторий, включая статические файлы:
  это общий контроль секретов, не возвращение frontend-пакетного контура.
  Trivy backend/db/nginx сохранить: Nginx теперь доставляет статику и остаётся
  инфраструктурным образом. Не создавать фиктивный frontend-image scan.
- make verify: сохранить последовательную композицию имеющихся test/quality/
  security, честную сводку и остановку при ошибке. Не оставлять frontend echo
  success, пропуски как успешные проверки, фальшивые отчёты или заглушки.
- setup/build/up/container-check адаптировать только в необходимых местах:
  не требовать frontend manifests/test-конфиги и не собирать frontend test-stage.
  Статическая доставка и базовые проверки наличия runtime файлов остаются.
- Если Node-контейнер используется общим security-скриптом не для frontend,
  определить его назначение и заменить только явно ненужное; не ломать backend
  проверки механическим удалением любого слова Node.

## 5. Документация и область diff

Обновить существующий README: frontend — статические файлы без установки пакетов,
тесты/quality относятся к backend, frontend coverage и audit удалены по решению
пользователя. Удалить команды pnpm, старые пороги/отчёты и требования frontend
Node.js. Не обещать автоматическую проверку интерфейса, которой теперь нет.
Отметить риск: регрессии UI больше не ловятся frontend-тестами.

Разрешены удаления перечисленных frontend-инструментов/тестов и изменения
Makefile, Docker/test Compose, .dockerignore, scripts/security*, соответствующих
инфраструктурных тестов, существующих pipeline при наличии и README.
Не внедрять новые CI, инструменты/сервисы, зависимости и отдельные инструкции.
Не править старые task-документы, Git-историю и исторические отчёты ради поиска
упоминаний pnpm. Настоящий .env не читать/не менять/не копировать; его наличие
не блокирует задачу. Проверки — с фиктивным env в изолированном окружении.

## 6. Проверки и приёмка

1. Поиск по tracked рабочим исходникам/конфигурациям: нет команд pnpm, pnpm
   manifests/lock/workspace, frontend npm/node test/lint/SAST стадий и зависимостей.
   Исторические документы/отчёты не являются остаточной runtime-зависимостью.
2. Подтвердить, что frontend состоит только из runtime статики, без тестов,
   конфигов инструментов и необходимости package install для доставки.
3. Проверить Compose config без вывода секретов, Dockerfile COPY и Makefile
   references: все используемые paths/stages существуют.
4. Выполнить backend test/quality, инфраструктурные тесты затронутых security
   handlers и фактический security при доступном Docker. Backend coverage >=80%.
   Ошибки уязвимостей не скрывать; успех удаления pnpm не означает чистый scan.
5. Собрать статический Nginx и проверить HTTP /, вложенный SPA URL/refresh,
   JS/CSS MIME, missing asset 404, /api и /health. Базовый browser smoke допускается
   как разовая приёмка без добавления тестового контура или новых библиотек.
6. Проверить коды ошибок verify и отсутствие ожидания frontend-отчётов.
7. git diff --check, проверить согласованность README/Makefile и отсутствие
   изменений рабочего .env/БД. Не удалять рабочие контейнеры и тома.

Docker для изолированных проверок разрешён в рамках продолжающейся миграции.
При недоступности выполнить независимые проверки и явно перечислить пропуски;
не завершать после одного аудита, если можно внести разрешённые изменения.

## 7. Качество и завершение

Комментарии/docstring — на русском, идентификаторы — на английском.
Строго соблюдать Keep It Simple, Stupid! (KISS), Don't Repeat Yourself (DRY),
SOLID. Не создавать новые абстракции для замены удалённых инструментов.

Итог: изменённые/удалённые файлы, фактические команды и результаты, оставшиеся
риски UI без тестов, пропуски и причины. Явно указать согласованное удаление
frontend-проверок и сохранность backend/инфраструктурной защиты. Миграций данных
нет. Откат — возврат frontend dev-файлов и команд из предыдущей ревизии,
без удаления томов. Не утверждать CI/ручную приёмку без фактического выполнения.
