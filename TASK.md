# Перенос контейнерных образов в локальный Docker Registry

## Цель

Развернуть Docker Registry в виртуальной машине `192.168.56.111` и перевести на него сборку, проверки, публикацию и запуск InventoryAccountment. Для изолированного стенда использовать HTTP. Предлагаемый порт — `5000`, если он свободен. Образы загружать заранее и закреплять по конкретным версиям и digest. Пакетные репозитории, инфраструктура GitHub Actions и обновления базы Trivy остаются доступны через интернет.

## Порядок работы с пользователем

Создать отдельную ветку `codex/local-docker-registry` от согласованной исходной ветки. Все этапы и исправления по обратной связи выполнять в одной рабочей ветке. Сохранять существующие пользовательские правки. Коммиты и push выполняет пользователь, если он отдельно не поручит их агенту.

Выполнять за один заход только один этап. Каждый этап должен завершаться отдельным набором изменений с понятным результатом, который можно проверить вручную. Рекомендуемый порядок:

1. Конфигурация registry и проверка HTTP, push/pull и сохранения образов после перезапуска.
2. Предварительное наполнение registry и перевод сборок и проверок на локальные образы.
3. Настройка self-hosted CI и публикации проверенных образов только при push в `dev`.
4. Запуск готового набора на сервере и проверка отката на отдельном тестовом томе.

В конце каждого этапа прекратить правки и завершить ответ. Описать результат и изменённые файлы, указать выполненные проверки и причины пропусков, предложить сообщение для коммита. Дать пошаговый сценарий ручной проверки с командами, местом выполнения каждой команды и ожидаемым результатом. Ждать явного разрешения пользователя перейти к следующему этапу. Если поступила обратная связь, исправить текущий этап в той же ветке и снова остановиться после проверки. Недоступность сервера указать как ограничение приёмки этапа, а доступные локальные проверки выполнить.

Доступ к VM не предполагается автоматически. По умолчанию серверные команды выполняет пользователь. Прямой доступ возможен, если с машины агента есть сетевой маршрут до VM и пользователь предоставил SSH-доступ с нужными правами. Не добавлять ключи и пароли в репозиторий и не выводить их в отчёты.

## Реализация

1. Прочитать README.md, AGENTS.md и ближайшие инструкции. Проверить состояние Git и сохранить пользовательские изменения, включая `TODO`, если он присутствует. Соблюдать KISS (Keep It Simple, Stupid!), DRY (Don't Repeat Yourself) и SOLID соразмерно задаче. Комментарии в коде писать на русском языке.
2. Добавить минимальную конфигурацию отдельного Docker Registry с постоянным томом. Ограничить доступ на уровне сети доверенными узлами стенда. Для простого HTTP-варианта принять отсутствие аутентификации как допущение изолированного стенда и явно указать, что доступ к порту даёт возможность читать и записывать образы. Настроить `insecure-registries` только для точного адреса `192.168.56.111:5000` на Docker daemon, которые работают с registry. Не ослаблять настройки остальных registry.
3. Определить начальное наполнение registry. Учесть образ самого registry, базовые образы рабочего и тестового Dockerfile, образы проверок и любые Actions, запускающие Docker-образы. Первоначальную загрузку с внешних источников выполняет администратор на этапе наполнения, включая bootstrap registry. Сохранить используемые платформы. После наполнения сборки и проверки должны брать контейнерные образы из локального registry. Учесть Trivy отдельно: загрузка базы уязвимостей разрешена, даже если она доставляется как OCI-артефакт. Загрузка исполняемых файлов и пакетов по сети допускается. Не использовать `latest`.
4. Перевести задания CI на self-hosted runner с подходящими метками и доступом к `192.168.56.111`. Проверить события запуска. Не выполнять код недоверенных PR на runner, имеющем доступ к локальному registry или Docker хоста. При необходимости ограничить такие события и явно описать результат. Сохранить существующие проверки для доверенных запусков и не ослаблять политику Trivy. Не менять внешние настройки GitHub самостоятельно.
5. Публиковать только при push в `dev` и после успешных обязательных проверок. Загружать проверенные образы из артефактов того же прогона и публиковать без пересборки. Сохранить проверку image ID. Публиковать `backend`, Nginx со статикой под существующим именем `frontend` и производный `db`, чтобы сервер мог запускать весь набор без сборки. Удалить из этого пути публикацию и авторизацию в GHCR. Использовать тег с SHA коммита и сохранять digest опубликованных образов.
6. Настроить серверный запуск на скачивание согласованного набора готовых образов из локального registry с возможностью зафиксировать ожидаемые digest. Сохранить локальный режим разработки и изолированные тесты. Не менять схему БД, постоянные тома и рабочий `.env`. Предусмотреть откат выбором предыдущего набора образов без удаления томов.

Разрешены необходимые изменения существующих файлов и минимальная конфигурация registry. Не создавать отдельные инструкции или лишние файлы. Если нужно описать новый порядок запуска, точечно обновить существующий README.md.

## Приёмка

- Проверить Compose и YAML, затронутые проверки из README и `git diff --check`.
- В изолированной среде проверить, что образы остаются доступны после перезапуска registry, а сборка и проверки используют локальные ссылки на контейнерные образы.
- Проверить условия публикации и соответствие опубликованных образов образам, прошедшим сканирование. При падении обязательной проверки публикация не выполняется.
- Проверить запуск полного набора без сборки на сервере и откат на предыдущий набор с сохранением данных. Использовать отдельный тестовый том и не переключать рабочий стенд без поручения.
- Указать фактически выполненные команды, результаты и причины пропусков. Если runner или виртуальная машина недоступны, подготовить и проверить доступную часть, указать точные оставшиеся действия и не заявлять об успешном развёртывании.
