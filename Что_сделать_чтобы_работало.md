# Локальный registry и CI: быстрая настройка

Цель: Ubuntu Server VM с registry `192.168.56.111:5000` и self-hosted runner. Выполняйте команды на указанной машине. Registry использует HTTP без пароля: любой узел с доступом к порту может читать и записывать образы. Доступ нужно ограничить доверенными узлами; это ограничение на текущем стенде ещё не проверено.

## 1. Сеть VM

В VirtualBox подключите к VM host-only адаптер с адресом `192.168.56.111` и отдельный интернет-адаптер в режиме сетевого моста. На текущем стенде NAT давал TLS EOF к GitHub-хранилищу; через мост проверка прошла. После изменения сетевого адаптера адрес VM в основной сети может измениться.

На **Ubuntu VM** проверьте:

```bash
ip -br addr
ip route
curl -4 -sS -o /dev/null --connect-timeout 5 --max-time 15 \
  -w 'HTTP %{http_code}\n' https://productionresultssa0.blob.core.windows.net/
```

Ожидаются адрес `192.168.56.111`, маршрут в интернет и `HTTP 400` от неавторизованного запроса к хранилищу GitHub. На действующей VM меняйте сетевые адаптеры через консоль VirtualBox, сохранив host-only адаптер.

## 2. Docker и registry

На **Ubuntu VM** установите Docker Engine и Compose v2. В `/etc/docker/daemon.json` добавьте **только точный адрес** `192.168.56.111:5000` в массив `insecure-registries`, сохранив другие параметры и элементы массива. Если файла нет:

```json
{
  "insecure-registries": ["192.168.56.111:5000"]
}
```

Проверьте конфигурацию и перезапустите Docker. Перезапуск прерывает работающие контейнеры:

```bash
sudo dockerd --validate --config-file /etc/docker/daemon.json
sudo systemctl restart docker
```

Из **корня репозитория на VM** запустите registry:

```bash
cd /opt/InventoryAccountment
docker compose -f docker-compose.registry.yml config --quiet
docker compose -f docker-compose.registry.yml pull
docker compose -f docker-compose.registry.yml up -d
curl -fsS http://192.168.56.111:5000/v2/
```

Ожидается `{}`. Первичная загрузка закреплённого образа registry требует Docker Hub. Постоянный том — `inventory-registry_registry_data`; не переопределяйте имя Compose-проекта и не используйте `down -v`.

## 3. Обновить образы в registry

На **Ubuntu VM** выполните блок ниже. Skopeo копирует многоплатформенные индексы под указанными именами и тегами с сохранением digest; при ошибке копирование останавливается, а последняя команда возвращает ненулевой код. Повторный запуск допустим. Для обновления версии сначала проверьте новый digest и согласованно обновите закреплённые ссылки в проекте; одно изменение тега не заменит digest.

```bash
sudo apt-get update
sudo apt-get install skopeo
registry_copy_status=0
while read -r source destination; do
  skopeo copy --all --preserve-digests --dest-tls-verify=false \
    "docker://$source" "docker://192.168.56.111:5000/$destination" || { registry_copy_status=1; break; }
done <<'EOF'
docker.io/library/registry@sha256:a3d8aaa63ed8681a604f1dea0aa03f100d5895b6a58ace528858a7b332415373 library/registry:2.8.3
ghcr.io/astral-sh/uv@sha256:f459f6f73a8c4ef5d69f4e6fbbdb8af751d6fa40ec34b39a1ab469acd6e289b7 astral-sh/uv:0.9.5
registry.access.redhat.com/ubi9/python-312@sha256:19e1e927138b40454858f297884c2c4e2f13f5ba95b3f55faea174d3cbb57067 ubi9/python-312:1
docker.io/nginxinc/nginx-unprivileged@sha256:5aea7cc516b419e3526f47dd1531be31a56a046cfe44754d94f9383e13e2ee99 nginxinc/nginx-unprivileged:1.29.3-alpine
docker.io/library/postgres@sha256:665dc7b37ac52a17e298511414c21d23ffa4e6a6ef6225b3e5d59c7afb35e994 library/postgres:17.11-bookworm
docker.io/library/golang@sha256:dc0963f32053e4bc451d24d87e3892d42d01021b61f093e98eb95c0352bb84b0 library/golang:1.27-bookworm
docker.io/library/python@sha256:f3fa41d74a768c2fce8016b98c191ae8c1bacd8f1152870a3f9f87d350920b7c library/python:3.12.12-slim
docker.io/zricethezav/gitleaks@sha256:b5918eb91b8d2473cec722f066abb4352e4ffdc4ec9f4283ec143aba9ec9ebc4 zricethezav/gitleaks:v8.24.2
docker.io/aquasec/trivy@sha256:029e990b328d149bf0a9ffe355919041e1f86192db2df47e217f8a36dd42ceac aquasec/trivy:0.59.1
EOF
test "$registry_copy_status" -eq 0
```

Производный образ PostgreSQL создаётся отдельно и должен быть доступен с закреплённым digest. Проверьте на **VM**:

```bash
docker pull 192.168.56.111:5000/inventory/postgres:17.11-gosu1.20@sha256:6e831ad1c986ba39e25acc4c510993792be68fd60d331ebe644b3083eeaa6201
```

Если манифест отсутствует, перенесите именно проверенный образ с этого digest из сохранённого источника. Повторная сборка `docker/postgres/Dockerfile` может дать другой digest; новый образ сначала проверяют на изолированной БД и сканируют, затем согласованно обновляют ссылки Compose. Не подменяйте digest без проверки.

## 4. Настроить runner на VM

Runner с доступом к Docker фактически получает права администратора VM. Допускайте к нему только доверенные задания; не выполняйте на нём код непроверенных PR. Дальнейшие команды предназначены для **первой установки**. Если пользователь или каталог уже существуют, не пересоздавайте их — проверьте владельца и текущую конфигурацию.

На **Ubuntu VM**:

```bash
sudo useradd --create-home --shell /bin/bash gha-runner
sudo usermod -aG docker gha-runner
sudo install -d -o gha-runner -g gha-runner -m 0750 /opt/actions-runner
sudo -iu gha-runner docker info
sudo -iu gha-runner curl -fsS http://192.168.56.111:5000/v2/
```

В GitHub откройте **Settings → Actions → Runners → New self-hosted runner**, выберите **Linux x64**. На VM перейдите под `gha-runner` в `/opt/actions-runner`:

```bash
sudo -iu gha-runner
cd /opt/actions-runner
```

Выполните актуальные команды GitHub для скачивания, проверки SHA256 и распаковки, затем команду регистрации `./config.sh` со страницы GitHub, добавив `--labels inventory-registry`. Рабочий каталог оставьте `_work`. Регистрационный токен не сохраняйте в репозитории и не отправляйте в чат.

После регистрации выйдите из сессии `gha-runner` и на **VM под root** запустите службу:

```bash
cd /opt/actions-runner
sudo ./svc.sh install gha-runner
sudo ./svc.sh start
sudo ./svc.sh status
```

Ожидается `active (running)`. В GitHub runner должен быть `Idle` с метками `self-hosted`, `linux`, `x64`, `inventory-registry`.

## 5. Проверить CI

После размещения workflow в доверенной ветке запустите его в GitHub **Actions → CI → Run workflow** для `dev` или `main`. Ручной запуск выполняет проверки, но не публикует образы. Workflow не запускается для PR; настройку защиты веток и альтернативную проверку PR владелец определяет отдельно.

Публикация `backend`, `frontend` и `db` в локальный registry выполняется только при push в `dev` и после успешных обязательных заданий. При ошибке во время последовательной публикации часть тегов может уже существовать — такой набор нельзя считать готовым. Digest успешных отправок сохраняются в artifact `published-images-*`.

На текущем стенде после переключения VM на сетевой мост ручная проверка TLS прошла; полный повторный прогон CI и публикация ещё не подтверждены. Если повторять прежний прогон от push в `dev`, успешный результат автоматически запустит публикацию.
