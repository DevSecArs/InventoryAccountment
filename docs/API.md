# API: текущая версия

## Общие сведения

HTTP API запущен на `http://127.0.0.1:8000`. Все маршруты справочников имеют
префикс `/api/v1`. Интерактивная спецификация OpenAPI доступна по адресу
`http://127.0.0.1:8000/docs`, а исходная схема — по адресу
`http://127.0.0.1:8000/openapi.json`.

Перед вызовом маршрутов справочников должны быть запущены PostgreSQL и
применена миграция:

```powershell
venv\Scripts\python.exe -m alembic upgrade head
```

Запросы и ответы используют JSON и кодировку UTF-8. Каждый ответ API содержит
заголовок `X-Request-ID`. Его можно передать в запросе в формате UUID, чтобы
связать клиентский запрос с журналом приложения; некорректное или отсутствующее
значение будет заменено новым UUID.

## Формат ошибок

Ошибки приложения имеют единый JSON-формат:

```json
{
  "code": "http_404",
  "message": "Единица измерения не найдена",
  "details": null,
  "request_id": "8d9a2e8b-63c8-45f1-85ad-fc2dc2f91b0d"
}
```

На текущей версии используются следующие коды HTTP:

| Код | Когда возвращается |
| --- | --- |
| `201` | Справочник создан. |
| `204` | Запись успешно архивирована; тела ответа нет. |
| `400` | Нарушено бизнес-правило, например повторяется код. |
| `404` | Запрашиваемая запись отсутствует или архивирована. |
| `422` | Не прошла проверка формата входных данных. |
| `500` | Непредвиденная ошибка приложения. |
| `503` | PostgreSQL недоступна при проверке готовности. |

## Проверки состояния

| Метод и путь | Назначение | Успешный ответ |
| --- | --- | --- |
| `GET /health/live` | Проверяет, что HTTP-приложение запущено. | `200 {"status":"ok"}` |
| `GET /health/ready` | Проверяет соединение приложения с PostgreSQL. | `200 {"status":"ok"}` |

Пример:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/health/ready
```

## Общие правила справочников

- `code` единицы измерения, `sku` материала и `code` поставщика приводятся к
  верхнему регистру; начальные и конечные пробелы удаляются.
- `name` не может состоять только из пробелов.
- `DELETE` выполняет архивирование: запись сохраняется в БД, но исключается из
  обычных списков и запросов по идентификатору.
- Для списков доступны одинаковые параметры: `skip` (от `0`, по умолчанию
  `0`), `limit` (от `1` до `1000`, по умолчанию `100`),
  `include_archived` (по умолчанию `false`) и необязательный `search`.
- Списки возвращаются в формате `{"items": [...], "total": 0, "skip": 0,
  "limit": 100}`.

## Единицы измерения

Базовый путь: `/api/v1/units`.

| Метод и путь | Назначение |
| --- | --- |
| `GET /` | Получить список единиц измерения. |
| `POST /` | Создать единицу измерения. |
| `GET /{unit_id}` | Получить единицу по идентификатору. |
| `PUT /{unit_id}` | Изменить код и/или наименование. |
| `DELETE /{unit_id}` | Архивировать единицу. |

Тело запроса при создании:

```json
{
  "code": "KG",
  "name": "Килограмм"
}
```

Тело запроса при изменении содержит любые из тех же полей. Ответ `201` и
успешные ответы чтения содержат `id`, `code`, `name`, `archived_at`,
`created_at` и `updated_at`.

## Материалы

Базовый путь: `/api/v1/materials`.

| Метод и путь | Назначение |
| --- | --- |
| `GET /` | Получить список материалов. |
| `POST /` | Создать материал. |
| `GET /{material_id}` | Получить материал по идентификатору. |
| `PUT /{material_id}` | Изменить материал. |
| `DELETE /{material_id}` | Архивировать материал. |

При создании необходима действующая, неархивная единица измерения:

```json
{
  "sku": "BOLT-M8",
  "name": "Болт М8",
  "description": "Оцинкованный",
  "unit_id": "идентификатор-единицы-измерения"
}
```

Для изменения допустимы `sku`, `name`, `description` и `unit_id`. Ответ
содержит `id`, `sku`, `name`, `description`, `unit_id`, `archived_at`,
`created_at` и `updated_at`.

## Поставщики

Базовый путь: `/api/v1/suppliers`.

| Метод и путь | Назначение |
| --- | --- |
| `GET /` | Получить список поставщиков. |
| `POST /` | Создать поставщика. |
| `GET /{supplier_id}` | Получить поставщика по идентификатору. |
| `PUT /{supplier_id}` | Изменить поставщика. |
| `DELETE /{supplier_id}` | Архивировать поставщика. |

Тело запроса при создании:

```json
{
  "code": "SUP-001",
  "name": "ООО «Поставщик»",
  "contact_person": "Иван Петров",
  "phone": "+7 000 000-00-00",
  "email": "supply@example.invalid",
  "address": "Учебный адрес"
}
```

Поля `contact_person`, `phone`, `email` и `address` необязательны. При
изменении можно передать любое из полей поставщика. Ответ содержит все поля
запроса, а также `id`, `archived_at`, `created_at` и `updated_at`.

## Пример последовательности запросов

1. Создайте единицу измерения через `POST /api/v1/units/`.
2. Скопируйте поле `id` из ответа.
3. Создайте материал через `POST /api/v1/materials/`, передав этот `id` в
   `unit_id`.
4. Создайте поставщика через `POST /api/v1/suppliers/`.

## Пока не реализовано

В текущем API нет маршрутов для поступлений и их строк, проведения через
очередь, outbox, отчётов, экспорта CSV, аутентификации и авторизации. Эти
возможности описаны в техническом задании как следующие этапы реализации.
