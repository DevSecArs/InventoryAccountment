# API текущего MVP

Сверено с app/http.py, app/entities/routers.py и Pydantic-схемами ревизии 9701e9d. API не считается запущенным только по наличию документа. Локальный Backend обычно доступен на 8000, тестовый Make-контур — на 8001; /docs и /openapi.json доступны после запуска. Схему БД предварительно обновляют Alembic до a5b7c9d1e004.

## Общий контракт

Бизнес-маршруты имеют префикс /api/v1. JSON — UTF-8, quantity в ответах — десятичная строка. Идентификаторы хранятся как UUID-строки; не все строковые параметры API валидируются как UUID.

Каждый ответ получает X-Request-ID. Входящий UUID сохраняется; отсутствующее/невалидное значение заменяется. Ошибки:

~~~json
{"code":"http_404","message":"Поступление не найдено","details":null,"request_id":"8d9a2e8b-63c8-45f1-85ad-fc2dc2f91b0d"}

~~~

| HTTP | Использование |
| --- | --- |
| 200 | Чтение, изменение, проведение, в том числе повторное |
| 201 | Создание справочника, пользователя при первичной регистрации или черновика |
| 204 | Архивирование, purge, удаление черновика, logout; без тела |
| 400 | Некоторые бизнес-ошибки справочников, включая проверки уникальности/связей |
| 401 | Нет действующей сессии |
| 403 | Недостаточно прав или невалидный CSRF |
| 404 | Нет сущности; чтение архивного справочника по ID тоже возвращает 404 |
| 409 | Конфликт поступления, регистрации, части purge-операций |
| 422 | Pydantic-валидация или некорректный период |
| 500 | Непредвиденная ошибка; без traceback в ответе |
| 503 | Недоступна БД при /health/ready |

Требование одинакового 409 для всех конфликтов и 503 для недоступности БД в бизнес-маршрутах пока выполнено не полностью. Не предполагать, что все ограничения PostgreSQL корректно преобразуются в прикладные ответы.

## Health

GET /health/live возвращает 200 со status=ok без запроса к БД.
GET /health/ready выполняет SELECT 1; при отказе — 503. Readiness не проверяет актуальность миграций и наличие таблиц. Эти маршруты доступны без сессии.

## Сессия и роли

Все пути в таблицах далее относительно /api/v1.

| Метод и путь | Поведение |
| --- | --- |
| POST /auth/register | Создаёт единственного первого пользователя с ролью admin в пустой таблице users; повтор — 409 |
| POST /auth/login | Вход по login/password; неверные данные — 401 |
| GET /auth/me | Возвращает user и csrf_token |
| PUT /auth/me | Меняет full_name/email, требует CSRF |
| POST /auth/logout | Удаляет текущую сессию, требует CSRF |

Регистрация принимает login (3–64), password (12–256), full_name (1–255), необязательный email (до 255). Пример обезличенного тела:

~~~json
{"login":"demo_admin","password":"example-only-password","full_name":"Учебный администратор","email":"admin@example.invalid"}

~~~

Login нормализуется. Сервер хранит hash пароля и токена сессии. Cookie inventory_session: HttpOnly, SameSite=Strict, срок 7 дней; Secure включён вне development/test. Для production нужен HTTPS. После login/register клиент использует возвращённый csrf_token в X-CSRF-Token для защищённых POST/PUT/PATCH/DELETE.

Права на поступления: admin/operator создают, изменяют, удаляют и проводят; reporter читает. Чтение истории/отчётов доступно авторизованным пользователям. Purge справочников — admin. Обычные мутации справочников сейчас проверяют сессию/CSRF без запрета reporter; это расхождение с целевой read-only ролью, а не обещание полной RBAC. Создания других пользователей и смены ролей через API нет.

## Справочники

| Ресурс | Маршруты |
| --- | --- |
| /units | GET /, POST /, GET /si-options, GET /{id}, PUT /{id}, DELETE /{id}, DELETE /{id}/purge |
| /materials | GET /, POST /, GET /{id}, PUT /{id}, DELETE /{id}, DELETE /{id}/purge |
| /suppliers | GET /, POST /, GET /{id}, PUT /{id}, DELETE /{id}, DELETE /{id}/purge |

DELETE архивирует; purge физически удаляет архивную запись, если связи позволяют. GET по ID исключает архивные записи; список с include_archived=true включает их. Списки: skip=0 (>=0), limit=100 (1–1000), include_archived=false, необязательный search. Ответ: items, total, skip, limit.

Коды/SKU очищаются и приводятся к верхнему регистру. Реализованные лимиты кода/SKU — 50, name — 200 символов. Историческое требование 64/255 не реализовано; расширение требует отдельного изменения схемы/валидации.

| Ресурс | Поля CREATE/PUT |
| --- | --- |
| Единица | code из GET /units/si-options; name берётся из таблицы СИ, произвольные единицы не поддерживаются |
| Материал | sku, name, unit_id; необязательный description |
| Поставщик | code, name; необязательные contact_person (100), phone (50), email (100), address |

Примеры создания:

~~~json
{"code":"KG"}

~~~

~~~json
{"sku":"MAT-001","name":"Учебный материал","unit_id":"<ID единицы>","description":"Пример"}

~~~

~~~json
{"code":"SUP-001","name":"Учебный поставщик","email":"supply@example.invalid"}

~~~

Ответы дополнительно содержат id, archived_at, created_at, updated_at. Материалу нельзя менять unit_id после использования в строке поступления. Физическое удаление ссылочных записей защищено FK; не все такие отказы нормализованы в 409. Названия справочников в истории/отчётах отображаются текущие.

## Поступления

| Метод и путь | Результат |
| --- | --- |
| POST /receipts/ | Создать draft со строками, 201 |
| GET /receipts/ | items/total/skip/limit |
| GET /receipts/{id} | Карточка со строками, 200 |
| PATCH /receipts/{id} | Изменить только draft; переданный items полностью заменяет состав |
| DELETE /receipts/{id} | Удалить draft и строки, 204 |
| POST /receipts/{id}/post | Провести синхронно, 200 |
| GET /receipts/{id}/history | Объект с массивом items |

~~~json
{
  "supplier_id":"<ID поставщика>",
  "document_number":"DOC-001",
  "received_at":"2026-10-12T09:00:00+03:00",
  "items":[{"material_id":"<ID материала>","quantity":"0.100"}]
}

~~~

Документ содержит хотя бы одну строку. Материал не повторяется, quantity > 0, NUMERIC(18,3); лишние знаки отклоняются API. Номер после trim непустой, до 64 символов, уникален у поставщика. Дата обязана содержать пояс. Поставщик, материалы и единицы должны быть активны. Неизвестные поля CREATE/PATCH запрещены; статус нельзя менять PATCH-запросом. Явный null в PATCH пока разрешён схемой для части полей и не всегда обработан корректно; клиенту не передавать null вместо обязательных значений.

Карточка: id, supplier_id, supplier_name, document_number, received_at, status, created_at, updated_at, items. Строка: id, material_id, quantity и отображаемые material_sku/material_name/unit_id/unit_code/unit_name.

Список принимает supplier_id, status, search по номеру, from и to по received_at. Границы для списка необязательны; когда обе заданы — from < to; интервал [from,to). Сортировка created_at DESC, id DESC. Skip/limit как у справочников; total считается до пагинации.

Проведение блокирует документ, повторно проверяет ссылки и атомарно сохраняет posted и одну историю. Повтор для posted возвращает тот же документ без новой истории и изменения updated_at. Это идемпотентность по ID, без обязательного Idempotency-Key. Старые queued/processing/failed не запускают очередь: запрос проведения возвращает 409. Posted нельзя PATCH/DELETE.

История содержит id, receipt_id, from_status, to_status, changed_at, reason. Единственный новый переход — draft → posted. Черновик и старый документ без истории возвращают пустой items; отсутствующий документ — 404. Публичных методов изменения истории нет.

## Отчёт и CSV

GET /reports/supplies и GET /reports/supplies/export принимают обязательные from/to с часовым поясом, from < to, необязательные supplier_id/material_id. В отчёт входят только posted за [from,to) по received_at, включая архивные справочники.

JSON принимает skip=0, limit=100 (1–1000), возвращает:

- items — детальные строки;
- total — число строк всей выборки;
- skip, limit;
- totals — суммы всей выборки по материалу и единице, не только страницы.

Детальная строка: receipt_id, document_number, received_at, supplier_id, supplier_name, material_id, material_sku, material_name, unit_id, unit_code, unit_name, quantity. Totals содержит поля материала/единицы и quantity. Сортировка строк — received_at, receipt_id, material_id; разные единицы не суммируются, это не доступный остаток.

CSV экспортирует всю выборку без пагинации. UTF-8 с BOM, запятая, CRLF, стандартное CSV-экранирование, десятичная точка; имя supplies.csv, Content-Disposition=attachment. Пустой результат имеет заголовок. Для текстов, начинающихся с =, +, -, @, добавляется апостроф; итоговые строки в CSV не добавляются.

## Не реализовано или требует проверки

Нет очереди/outbox, административного API, смены пароля/ролей, отмены проведения, доступных остатков, нескольких складов, метрик/алертов. Полная согласованность items/total/totals при конкурентном проведении и все варианты rollback/ошибок не подтверждены имеющимся набором тестов. Пробелы перечислены в [TASK.md](../TASK.md) и [матрице](TEST_MATRIX.md).
