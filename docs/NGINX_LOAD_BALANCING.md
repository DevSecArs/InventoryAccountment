# Балансировка нагрузки и отказоустойчивость

## Архитектура

В системе InventoryAccountment используется Nginx в отдельном Docker-контейнере для распределения HTTP-запросов между двумя экземплярами FastAPI.

Схема прохождения API-запросов:

```text
Браузер
   |
   v
Frontend (React / Vite)
   |
   | API proxy
   v
Nginx (:80, на хосте 127.0.0.1:8080)
   |
   +----> FastAPI app-1 (:8000) ----+
   |                                |
   +----> FastAPI app-2 (:8000) ----+----> PostgreSQL
```

Frontend доступен через порт `5180`. Backend-контейнеры не публикуют порт `8000` на хосте и принимают запросы через внутреннюю сеть Docker.

## Запуск

```bash
docker compose up -d --build
docker compose ps
```

Для сервиса `app` в Docker Compose задано `deploy.replicas: 2`.

## Проверка балансировки

Каждый backend добавляет HTTP-заголовок `X-Instance-ID`, содержащий hostname контейнера.

Проверка:

```bash
for i in $(seq 1 20); do
  curl -s -D - -o /dev/null \
    http://127.0.0.1:8080/health/live \
    | grep -i '^x-instance-id:'
done
```

Результаты эксперимента:

| Экземпляр | Количество запросов |
|---|---:|
| `d1d2a1e58fe9` | 11 |
| `e0b97a5edd8b` | 9 |

Оба экземпляра обрабатывали запросы. Распределение близко к равномерному.

## Проверка отказоустойчивости

Второй backend был остановлен:

```bash
docker stop inventory-compose-app-2
```

После остановки выполнено 20 HTTP-запросов:

```bash
for i in $(seq 1 20); do
  curl -sS --max-time 10 -o /dev/null \
    -w "Запрос $i: HTTP %{http_code}\n" \
    http://127.0.0.1:8080/health/ready
done
```

Результат: **20 из 20 запросов вернули HTTP 200**.

Все проверенные ответы содержали идентификатор оставшегося экземпляра `d1d2a1e58fe9`.

После эксперимента второй backend восстановлен:

```bash
docker start inventory-compose-app-2
```

Это подтверждает доступность API при остановке одного backend в проверенном сценарии.

## Обработка ошибок

Nginx настроен на повторную отправку подходящих запросов при сетевых ошибках, тайм-аутах и отдельных ответах upstream (`502`, `503`, `504`).

Параметры `max_fails` и `fail_timeout` позволяют временно исключать проблемные backend-узлы из распределения запросов.

Важно: проверка показала успешную работу после остановки одного экземпляра, но не гарантирует отсутствие кратковременных ошибок непосредственно в момент любого отказа.

## Ограничения горизонтального масштабирования

1. **Общая PostgreSQL.** Все backend обращаются к одной базе данных. При увеличении числа экземпляров база может стать узким местом.
2. **Пулы соединений.** Каждый экземпляр FastAPI создаёт собственные соединения с PostgreSQL. Общее количество соединений растёт вместе с числом экземпляров.
3. **Миграции.** Изменение схемы БД должно выполняться централизованно до запуска обновлённых экземпляров.
4. **Общее состояние.** Сессии пользователей должны храниться в общем хранилище, а не только в памяти одного процесса. В проекте для этого используется PostgreSQL.
5. **Локальная файловая система.** Файлы, сохранённые внутри одного контейнера, автоматически не становятся доступны другим экземплярам.
6. **Единая точка отказа.** Один Nginx и один PostgreSQL остаются потенциальными точками отказа. Масштабирование FastAPI не обеспечивает отказоустойчивость всей системы.
7. **Ресурсы сервера.** Все контейнеры используют ресурсы одного Docker-хоста. Масштабирование в пределах одного сервера не защищает от отказа самого сервера.

## Вывод

Балансировка между двумя экземплярами FastAPI работает. Остановка одного backend не привела к недоступности API в проведённом эксперименте.

Для промышленной эксплуатации дополнительно потребуются мониторинг, резервирование критических компонентов, HTTPS и полноценные испытания под нагрузкой.
