# Однократная сборка для verify

Задача для трекера (номер не присвоен): исключить повторные сборки и установку
зависимостей внутри обязательного контура, сохранив все проверки и пороги.
После успеха запустить рабочую среду из проверенных образов. Изменения схемы
и перенос данных не входят в задачу; штатные миграции при запуске сохраняются.

## Запуск

Linux: `make verify`. Windows, из PowerShell: `python -m scripts.verify`.
Нужны Python 3.11+, Git и Docker Compose. Предварительный `make setup` не нужен.
Тестовая команда использует `docker compose run --rm`: у `run` нет параметра
`--no-build`. Повторная сборка исключена отсутствием `build` в сформированной
конфигурации; загрузка образов — `pull_policy: never` и закреплёнными image ID.
Параметр `--no-build` сохраняется для финального `docker compose up`.
Путь к внешним настройкам передаётся только через `ENV_FILE`, включая пути
с пробелами. Тестовые проекты не читают рабочий env-файл и имеют отдельные тома.

## Порядок

1. Проверка политики исходников и Compose; снимок исходников для сборки.
2. Однократная сборка общего образа инструментов, API и Frontend.
   API и миграции используют один image ID; PostgreSQL и pg-tools — другой.
3. В общем образе: pytest с покрытием 80%, Frontend-тесты, Ruff, mypy,
   Bandit, lock-check, audit Python/Node, Frontend quality/build,
   критические мутации, миграционная матрица. Lock-файл pnpm проверяется
   установкой с --frozen-lockfile во время сборки, без повторной установки.
   Зависимости устанавливаются от app/node, исходники копируются с нужным
   владельцем через COPY --chown. Рекурсивный chown дерева зависимостей не нужен.
   Кэши сборки общего образа разделены по UID/GID; смена пользователя не требует
   удаления чужого кэша. Ускорение зависит от диска, сети и наличия кэша.
4. Изолированный запуск рабочих image ID: UID, процессы, healthcheck,
   HTTP smoke, backup/restore и пересоздание PostgreSQL с сохранением схемы.
5. Из общего образа инструментов: Gitleaks и Trivy. Каждый уникальный image ID
   экспортируется один раз; Trivy проверяет уязвимости и секреты, используя
   общий кэш своей базы в пределах прогона. Docker socket в образ не монтируется.
6. Проверки Git и неизменности исходников, затем рабочий Compose up
   с --no-build --pull never и закреплёнными image ID.

При отказе проверки запуск рабочей среды не выполняется. Ошибка уже во время
финального развёртывания возвращает ненулевой код; автоматического отката
миграций и частично обновлённых сервисов нет. Рабочие тома не удаляются.
CI выполняет эту же цепочку и запускает приложение только на своём runner.
Не запускайте параллельно несколько verify для одной рабочей среды.

## Приёмка и диагностика

Критерии: сборка каждого проектного образа только один раз за прогон;
отсутствие установки пакетов в этапах проверок; совпадение image ID сканирования,
контейнерных проверок и запуска; отказ любого обязательного этапа блокирует up.
Регрессионные тесты: `tests/unit/test_verify_pipeline.py`.
Отчёты: `reports/verify.json`, `reports/container-check.json`, `reports/trivy-*.json`,
отчёты тестов и анализаторов. Статус running/checking не означает успешной проверки.

Критические изменения: Makefile (новый порядок verify), Dockerfile.tests
(единые инструменты), scripts/verify.py и verify_checks.sh (оркестрация),
container_check.py (повторное использование ID), workflow (убрана лишняя сборка
make setup), регрессионные тесты и инструкции. Самостоятельные make test,
quality и container-check сохраняют прежний интерфейс.

Для отката верните прежний код оркестрации; для приложения используйте предыдущие
совместимые образы. Не удаляйте рабочий том PostgreSQL. Успешный локальный прогон
не заменяет CI и независимую приёмку.


Мутационные проверки явно разделяют baseline и изменённую копию. Намеренное
падение означает успех только при коде 1, наличии имени целевого теста и заданной
причины в stdout. Baseline, импорт, тайм-аут и выжившая мутация остаются отказами.
Безопасные сводки сохраняются в reports/mutations; repr фикстур и traceback
не печатаются, чтобы не раскрывать токены. Сводка содержит код и признаки
совпадения теста/причины, но не заменяет полную диагностику произвольного pytest.
Восемь мутаций и mutation_import_guard сохранены. Целевые unit-регрессии,
Ruff и mypy прошли; полный запуск восьми мутаций и verify не выполнялся.
Критические изменения: scripts/check_critical_mutations.py и его unit-регрессии.
Откат — revert соответствующего коммита.
