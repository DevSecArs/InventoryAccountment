# Техническое задание: MVP «Складской учёт»

Актуализировано по согласованному синхронному сценарию и исходникам 9701e9d. Документ различает требования, реализованные возможности и незавершённые критерии; наличие кода не означает состоявшуюся приёмку. Очередь из первоначального варианта исключена пользователем, Frontend включён в MVP.

## 1. Назначение и границы

Учёт поступлений материалов на один склад: справочники, документы, проведение, история и отчёт за период с CSV. PostgreSQL — источник данных. API — FastAPI/SQLAlchemy, миграции — Alembic, интерфейс — React/TypeScript.

В MVP не входят RabbitMQ, outbox, publisher/worker/DLQ, списания, перемещения, инвентаризация, резервирование, расчёт доступного остатка и финансовый учёт. Проведение выполняется синхронно: draft → posted. Расширение области требует отдельной задачи и критериев.

## 2. Пользователи и сценарии

- Оператор ведёт справочники, создаёт/редактирует черновик со строками и проводит его.
- Специалист по отчётности читает документы и отчёты; целевая роль reporter не должна менять бизнес-данные.
- Администратор управляет эксплуатацией и имеет разрешённые прикладные действия; не обходит миграции и API для изменения бизнеса.
- Проверяющий независимо оценивает проверки и живую демонстрацию; это роль в процессе, не отдельный пользователь API.

Аутентификация уже реализована: начальный admin, cookie-сессии, CSRF и профиль. Admin/operator могут менять поступления, reporter — читать. В справочниках обычные мутации пока не ограничены ролью reporter: требование остаётся незавершённым. API создания дополнительных пользователей/смены ролей отсутствует.

Основной сценарий: подготовить справочники → создать многопозиционный draft → сохранить/исправить → провести одной транзакцией → прочитать историю → получить отчёт/CSV. Повтор запроса проведения после потери ответа не должен повторно учитывать документ.

## 3. Сущности и реализация

| Сущность | Поля и правила |
| --- | --- |
| Единица | id, code, name, archived_at, created_at, updated_at; фиксированная таблица СИ, один ко многим с материалами |
| Материал | id, sku, name, description, unit_id, архивные/служебные даты |
| Поставщик | id, code, name, необязательные контакты и адрес, архивные/служебные даты |
| Поступление | id, supplier_id, document_number, received_at, status, created_at, updated_at; прежние nullable idempotency_key/error_message сохранены для совместимости |
| Строка | id, receipt_id, material_id, quantity; уникальна пара receipt_id/material_id |
| История | id, receipt_id, from_status, to_status, changed_at, reason; уникальный receipt_id: одно проведение на документ |
| Отчёт | Вычисление по проведённым поступлениям, без отдельной таблицы |
| Пользователь/сессия | users и user_sessions; hash пароля/токена, роль, срок и CSRF |

UUID хранятся строками String(36), связи защищены FK. Head миграций — a5b7c9d1e004. Модель строки объявлена вместе с Receipt; receipt_item.py только переэкспортирует её.

История добавляется только при новом проведении; для старых документов прошлые события не выдумываются. Записи истории не редактируются через API, удаление связанного документа ограничено FK. Сохранённые queued/processing/failed не переопределяются миграцией; проведение таких документов отклоняется.

## 4. Бизнес-инварианты

- Количество — Decimal/NUMERIC(18,3), строго положительное. API отклоняет лишние знаки; не выполнять двоичные вычисления float. В ответах quantity — строка.
- Перед проведением повторно проверяются существование/активность поставщика, материалов, единиц, непустой состав и уникальность материала.
- Номер документа после trim — 1–64 символа; уникальность у поставщика обеспечена в БД.
- Только draft редактируется и удаляется. Posted неизменяем; корректировки и отмена проведения требуют отдельного согласования.
- Переход и запись истории атомарны. Повтор posted возвращает 200 без изменения документа/истории. Блокировки FOR UPDATE OF ограничены таблицами, содержащими проверяемые записи.
- Используемые справочники не удаляются физически. Архивирование сохраняет ссылки; единица материала после использования в строке не меняется.
- Отчёт: только posted, интервал [from,to) по received_at, from < to; группировка по ID материала и единицы, названия текущие. Итоги относятся ко всей выборке. Разные единицы не объединяются.
- Ошибки имеют code/message/details/request_id без внутренних трассировок. Целевые статусы: 422 для ввода, 404 для отсутствия, 409 для конфликтов, 503 для временной недоступности, 500 для неожиданной ошибки. 401/403 применяются к сессии/правам/CSRF.

Фактические расхождения, которые не становятся нормой после актуализации документа:
- У справочников в коде лимиты 50 для code/SKU и 200 для name, вместо исходных требований 64/255. Для изменения необходима отдельная миграция/задача.
- Даты документов, истории и auth используют timezone-aware типы; даты справочников сейчас DateTime без timezone, поэтому требование единого TIMESTAMPTZ выполнено не полностью.
- Некоторые конфликты справочников возвращают 400, часть DB-ошибок может давать 500; 503 гарантирован только readiness.
- Явный null в PATCH и полная конкурентная защита изменений справочников требуют дополнительных проверок.
- Согласованность одного снимка отчёта при параллельном проведении пока не подтверждена.

## 5. Frontend

Требования: рабочие справочники, многопозиционный черновик с редактированием, проведение с подтверждением, просмотр неизменяемого документа и истории, отчёт/CSV, понятные ошибки и состояния, доступность с клавиатуры и адаптивность.

Текущий интерфейс поддерживает справочники, создание поступления с одной строкой, просмотр, проведение/удаление, историю и отчёт. Многопозиционная форма, PATCH-редактирование, расширенные фильтры списка и часть состояний/инвалидации кэша остаются незавершёнными. Ошибка CSV уже отображается. Подробности — [ТЗ интерфейса](WEB_UI_CODEX_SPEC.md).

## 6. Эксплуатация

Реализованы health/live и health/ready, X-Request-ID, Make-команды, Docker-контуры, скрипты backup/restore, тесты и workflow Verify. Ready выполняет SELECT 1 и не подтверждает актуальность схемы. Отдельный Linux test-образ проверяет Backend/Frontend и миграции, но не заменяет полный verify.

Весь стек развёртывается через Docker Compose с новой пустой PostgreSQL.
Внешняя БД исключена. Внешний env-файл выбирается через ENV_FILE без встроенного
пути; рабочие команды передают его Compose, тесты используют отдельные реквизиты.
make down сохраняет том; проверки используют отдельный Compose-проект,
make test-clean удаляет только его ресурсы. Backup/restore работают с db
выбранного проекта. Автоматические миграции предшествуют запуску API.
Схема не изменяется из-за переноса инфраструктуры; цепочка Alembic сохраняется.

Сохраняются целевые RPO ≤24 часа, RTO ≤60 минут, ежедневный backup с хранением минимум 7 дней вне хоста БД и проверяемое восстановление. Это цели эксплуатации; автоматическое расписание, соблюдение RPO/RTO и восстановление рабочего стенда не подтверждены текущим кодом.

Nginx/TLS, структурированные эксплуатационные логи, метрики, dashboard, алерты и CD по проверенному digest не настроены в репозитории. Это оставшиеся этапы доставки/эксплуатации. Для APP_ENV=production cookie Secure требует HTTPS. Наличие учебного Vite dev/preview и health-check не подтверждает production-готовность.

## 7. Процесс и приёмка

Обязательная цепочка: задача → изменение кода → локальные проверки → Git → CI → образ → CD → проверка релиза → наблюдение. Работа в отдельной ветке; прямые изменения основной ветки и обход защиты запрещены.

До слияния нужны make verify, успешный CI актуального SHA и независимое одобрение. Backend coverage минимум 80%; нельзя удалять содержательные тесты, ослаблять анализаторы/пороги или подавлять отказы. Frontend coverage-порог пока не реализован; его отсутствие не доказывает качество UI.

Критические изменения (README/ТЗ/AGENTS, Make/CI/CD, Docker/Compose/Nginx, тесты приёмки и анализаторы, миграции, backup/restore, защита веток/CODEOWNERS) явно перечисляются в PR/MR и проверяются ответственным независимо от автора.

Образ должен сканироваться по тому же image ID, который прошёл контейнерный сценарий. Makefile получает image ID запущенного контейнера; успешное сканирование должно подтверждаться конкретным прогоном. CD обязан использовать проверенный digest; повторная сборка — новый артефакт. Запись релиза связывает задачу, SHA, CI, digest, миграции и план отката.

Приёмка включает живой сценарий «черновик → синхронное проведение → повтор без дубля → история → отчёт», демонстрацию backup/restore и наблюдения, а также контрольное изменение по цепочке либо контролируемый отказ с обнаружением/восстановлением. Очередь и повторная доставка сообщений больше не являются частью сценария MVP. Человеческая приёмка не объявляется состоявшейся по результату автоматического теста.
