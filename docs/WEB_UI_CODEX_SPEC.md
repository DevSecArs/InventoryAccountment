# Техническое задание Codex: веб-интерфейс складского учёта

## 1. Карточка задачи

**Предлагаемое название задачи:** «Разработать веб-интерфейс системы
складского учёта».

Номер задачи отсутствует: трекер к репозиторию не подключён. Перед началом
реализации перенести это описание в трекер и указать присвоенный номер в
ветке и PR/MR. Не выдумывать номер, созданную задачу или запрос на слияние.

**Цель:** создать понятный, надёжный и адаптивный веб-интерфейс для операторов
склада, специалистов по отчётности и администраторов. Интерфейс должен
охватывать все бизнес-возможности, определённые в
`docs/Техническое_задание.md`, и интегрироваться с HTTP API без прямого доступа
к PostgreSQL, RabbitMQ или служебным каталогам.

**Ключевые требования заказчика:**

1. основная цветовая палитра — `#E4DDD3`;
2. второстепенная цветовая палитра — `#00A19B`;
3. стиль — солидный, простой и минималистичный;
4. интерфейс охватывает все возможности приложения.

**Влияние на данные:** UI не меняет схему БД и не обходит API. Создание,
изменение, архивирование и переходы статусов выполняются только через
серверные операции. Количество передаётся как десятичная строка, а не как
JavaScript `number`, чтобы не терять точность `NUMERIC(18,3)`.

## 2. Источники требований и приоритет

Перед изменениями Codex обязан полностью прочитать:

1. `AGENTS.md`;
2. `README.md`;
3. `docs/Техническое_задание.md`;
4. `docs/API.md`;
5. актуальную OpenAPI-схему `/openapi.json` при доступном backend;
6. более близкие `AGENTS.md`, если они появятся в каталоге frontend.

При противоречии источников бизнес-правила берутся из технического задания,
а фактические пути и форматы работающего API — из актуальной OpenAPI-схемы.
Расхождение нужно зафиксировать как блокер или отдельную backend-задачу, а не
скрывать преобразованиями на клиенте.

## 3. Границы задачи

### Входит в задачу

- отдельное frontend-приложение в каталоге `frontend/`;
- адаптивный интерфейс на русском языке;
- навигация и экраны всех ролей и сценариев из раздела 5;
- интеграция с текущими маршрутами справочников;
- типизированный слой API, готовый к подключению будущих маршрутов;
- единые компоненты загрузки, пустого результата, ошибки и подтверждения;
- клиентская валидация, не заменяющая серверную;
- модульные, компонентные и сквозные проверки;
- сборка frontend в воспроизводимом контейнере;
- документация локального запуска и обновление общего командного интерфейса.

### Не входит без отдельной задачи

- изменение бизнес-правил backend;
- ручное создание или изменение таблиц БД;
- реализация отсутствующих API поступлений, отчётов, очереди, аутентификации,
  backup/restore и мониторинга;
- хранение бизнес-данных только в браузере;
- поддельная авторизация, выбор роли пользователем или production-режим на
  моках;
- учёт нескольких складов, списания, перемещения, остатки, финансовый и
  бухгалтерский учёт.

Если необходимого API ещё нет, экран и его компоненты можно реализовать и
проверить на тестовых адаптерах, но production-сборка должна явно показывать
«Функция недоступна: серверный API ещё не реализован». Нельзя имитировать
успешное сохранение данных.

## 4. Технологический стек и структура

Использовать:

- React и TypeScript в строгом режиме;
- Vite для разработки и production-сборки;
- React Router для маршрутизации;
- TanStack Query для серверного состояния, кеширования и отмены запросов;
- React Hook Form и Zod для форм и клиентской валидации;
- Vitest и React Testing Library для модульных и компонентных тестов;
- Playwright для критических сквозных сценариев;
- CSS Modules или обычный CSS с дизайн-токенами. Не подключать тяжёлую
  UI-библиотеку только ради базовых таблиц, полей и диалогов.

Точные версии закрепить lock-файлом. Случайные зависимости, CDN и загрузка
шрифтов во время работы приложения запрещены. Допустим системный стек шрифтов:
`Inter`, `Segoe UI`, `Arial`, `sans-serif` без обязательной сетевой загрузки.

Рекомендуемая структура:

```text
frontend/
├── src/
│   ├── app/            # инициализация, router, providers
│   ├── api/            # клиент, типы, адаптеры и обработка ошибок
│   ├── components/     # переиспользуемые UI-компоненты
│   ├── features/       # units, materials, suppliers, receipts, reports, admin
│   ├── layouts/        # оболочка приложения и защищённые области
│   ├── pages/          # страницы маршрутов
│   ├── styles/         # токены, reset и глобальные правила
│   └── test/           # общая тестовая настройка
├── e2e/
├── public/
├── package.json
├── package-lock.json
├── tsconfig.json
└── vite.config.ts
```

Не создавать абстрактные слои без повторного использования. Компоненты и
API-функции группировать по предметным функциям, а не по случайным типам
файлов.

## 5. Информационная архитектура и экраны

### 5.1. Общая оболочка

- фиксированная верхняя панель с названием системы, текущим окружением,
  состоянием backend и пользовательским меню;
- боковая навигация на широких экранах и выезжающее меню на мобильных;
- пункты: «Обзор», «Единицы измерения», «Материалы», «Поставщики»,
  «Поступления», «Отчёты», «Администрирование»;
- хлебные крошки только глубже первого уровня;
- недоступные по роли пункты не показывать; запрет также обязан проверять
  backend;
- страница 404 с возвратом в безопасный доступный раздел.

### 5.2. Обзор

- состояние API, PostgreSQL, очереди и фонового обработчика;
- количество черновиков, документов в обработке и документов с ошибкой;
- последние поступления и быстрые переходы к созданию черновика и отчёту;
- предупреждения о просроченном backup, росте очереди и неопубликованных
  событиях outbox при наличии соответствующего API;
- карточки без псевдоаналитики: если источник данных отсутствует, показывать
  недоступность, а не `0`.

### 5.3. Единицы измерения

- таблица с кодом, названием, состоянием архива и датой изменения;
- поиск, пагинация, переключатель показа архивных записей;
- создание и редактирование в форме;
- архивирование с подтверждением и пояснением последствия;
- запрет архивирования используемой единицы отображать серверной ошибкой;
- возможность скопировать идентификатор из карточки записи.

### 5.4. Материалы

- таблица с SKU, названием, единицей измерения и статусом;
- поиск, пагинация и фильтр архивных записей;
- создание и редактирование с выбором только активной единицы измерения;
- необязательное описание;
- архивирование с подтверждением;
- недоступные или архивные связанные значения показывать в истории, но не
  предлагать для новых данных.

### 5.5. Поставщики

- таблица с кодом, названием, контактным лицом, телефоном, email и статусом;
- поиск, пагинация и фильтр архивных записей;
- создание, просмотр, редактирование и архивирование;
- необязательные контакты не заменять фиктивными значениями;
- email и телефон показывать как ссылки только после безопасной проверки
  формата.

### 5.6. Поступления

- список с номером документа, поставщиком, датой получения, статусом, датой
  изменения и краткой информацией об ошибке;
- фильтры по периоду, поставщику и статусу, поиск по номеру;
- создание черновика с поставщиком, номером, датой и часовым поясом;
- строки черновика: выбор активного материала, положительное количество с
  точностью не более трёх знаков, запрет повторного материала;
- добавление, изменение и удаление строк только в `draft`;
- сохранение черновика без потери введённых данных при исправимой ошибке;
- отправка с отдельным подтверждением и уникальным ключом идемпотентности;
- отображение переходов `draft → queued → processing → posted`, а также
  `failed → queued` при явном повторе;
- опрос статуса с разумным интервалом только для активных состояний; остановка
  опроса при уходе со страницы или конечном статусе;
- карточка документа с историей статусов и строками;
- проведённый документ и его строки доступны только для чтения;
- для `failed` показывать безопасное сообщение об ошибке и действие «Повторить»
  при наличии разрешения.

### 5.7. Отчёты

- обязательный период `[from, to)` с проверкой `from < to`;
- необязательные фильтры поставщика и материала;
- только проведённые поступления;
- таблица строк и итоги по материалу и единице измерения;
- количества разных единиц никогда не объединять в один итог;
- выгрузка CSV через серверный endpoint, без пересборки отчёта из обрезанной
  клиентской страницы;
- понятные состояния пустого отчёта, загрузки и ошибки;
- параметры отчёта отражать в URL, чтобы ссылку можно было повторно открыть.

### 5.8. Администрирование

- состояние обязательных сервисов, глубина очереди, DLQ, возраст старейшего
  неопубликованного события и последнего успешного backup;
- ссылки на разрешённые панели наблюдения, если они опубликованы безопасно;
- запуск backup/restore только через аутентифицированный серверный API и
  отдельные права;
- восстановление по умолчанию только в отдельную БД; перезапись существующей
  цели требует повторного ввода точного имени окружения и явного подтверждения;
- не показывать секреты, строки подключения и внутренние трассировки;
- если административного API нет, раздел остаётся информационным и явно
  сообщает, какие действия выполняются через утверждённые CLI-инструкции.

## 6. Визуальная система

### 6.1. Палитра

Обязательные базовые токены:

```css
:root {
  --color-surface-main: #E4DDD3;
  --color-accent: #00A19B;
  --color-surface: #F8F6F2;
  --color-surface-raised: #FFFFFF;
  --color-text: #202725;
  --color-text-muted: #59615E;
  --color-border: #C9C1B7;
  --color-accent-dark: #006B67;
  --color-focus: #007C77;
  --color-danger: #B42318;
  --color-warning: #8A5A00;
  --color-success: #287A4B;
}
```

`#E4DDD3` использовать для общей основы, навигации и спокойных крупных
поверхностей. `#00A19B` использовать для акцентов, активных состояний и
основных действий. Белый текст на `#00A19B` не использовать для обычного
мелкого текста без подтверждённого контраста; предпочтителен тёмный текст или
более тёмный акцент `#006B67` с белым текстом.

Состояния успеха, предупреждения и ошибки не кодировать одним цветом: всегда
добавлять текст и при необходимости пиктограмму.

### 6.2. Стиль

- строгая сетка, много свободного пространства, ясная типографическая
  иерархия;
- базовый шаг отступов `4px`, рабочие значения `8/12/16/24/32px`;
- радиусы `6–10px`, тонкие границы и очень умеренные тени;
- никаких градиентов, стеклянных эффектов, неоновых цветов, декоративных
  анимаций и перегруженных карточек;
- анимации только функциональные, `120–200ms`, с поддержкой
  `prefers-reduced-motion`;
- одна основная кнопка на смысловой блок; опасное действие визуально отделено;
- иконки дополняют подписи, но не заменяют их в критических действиях.

### 6.3. Адаптивность

- рабочие ширины: от `360px` до широкого desktop;
- на узком экране боковая навигация скрывается в меню;
- таблицы допускают горизонтальную прокрутку с закреплённым главным столбцом
  либо переходят в компактные карточки;
- формы строятся в одну колонку на мобильном и максимум в две на desktop;
- диалоги не выходят за экран, длинные формы открываются как отдельные страницы.

## 7. Поведение интерфейса

- загрузка: skeleton для структуры и индикатор внутри отправляемой кнопки;
- пустое состояние объясняет причину и предлагает разрешённое следующее
  действие;
- повторный клик по отправляемой форме блокируется;
- несохранённые изменения защищены предупреждением при уходе;
- после успешной операции показывается короткое уведомление и обновляются
  только затронутые запросы;
- серверная ошибка отображает `message`, полезные `details` и копируемый
  `request_id`; трассировка и технические секреты не показываются;
- при `409` сохраняются введённые данные и объясняется конфликт;
- при `422` ошибки привязываются к полям, если `details` содержит путь поля;
- при `503` предлагается повторить запрос, но пользовательский ввод не теряется;
- даты отображаются в локальном часовом поясе пользователя с явным указанием
  зоны в формах; на сервер отправляется ISO 8601 с часовым поясом;
- количество хранится в форме строкой и форматируется без двоичного округления.

## 8. Интеграция с API

- базовый URL задаётся переменной окружения, например `VITE_API_BASE_URL`;
- не помещать секреты в `VITE_*`: эти значения попадают в браузерную сборку;
- клиент следует актуальной OpenAPI-схеме и единому формату ошибок
  `code/message/details/request_id`;
- каждый запрос передаёт валидный UUID в `X-Request-ID` и сохраняет полученный
  идентификатор для диагностики;
- поддержать отмену запросов через `AbortSignal`;
- не использовать optimistic update для проведения документа, повторной
  обработки и административных операций;
- кеши разделять по фильтрам, пагинации и роли;
- после смены роли или выхода очищать пользовательские кеши;
- токен не хранить в `localStorage`; предпочтительна защищённая HttpOnly-cookie
  с CSRF-защитой, если такой способ реализует backend;
- CORS, HTTPS и политика cookie настраиваются на сервере, а не обходятся
  расширениями браузера.

Текущие маршруты справочников описаны в `docs/API.md`. Для ещё не
реализованных возможностей сначала согласовать OpenAPI-контракт отдельной
backend-задачей. Не хардкодить предположительные production-endpoint'ы.

## 9. Доступность и локализация

- соответствие WCAG 2.2 AA для контраста, клавиатуры, focus state и подписей;
- семантические `header`, `nav`, `main`, `form`, `table` и корректная иерархия
  заголовков;
- все поля имеют видимые подписи; placeholder не заменяет label;
- модальные окна удерживают фокус и возвращают его инициатору;
- ошибки форм объявляются через `aria-live` и связаны с полями;
- минимальная область нажатия — `44×44px` для мобильных действий;
- язык интерфейса первой версии — русский; тексты централизовать, чтобы не
  распределять строки по компонентам и подготовить будущую локализацию;
- форматы дат и чисел определять через `Intl`, не собирать вручную.

## 10. Безопасность

- не использовать `dangerouslySetInnerHTML` для серверных данных;
- не выводить секреты, stack trace и полные внутренние ошибки;
- проверять и кодировать параметры URL;
- для внешних ссылок с новым окном задавать `rel="noopener noreferrer"`;
- формы опасных операций защищать от случайного повтора;
- соблюсти Content Security Policy, запретить inline-скрипты в production;
- dependency-аудит не должен содержать необработанных High/Critical находок;
- frontend не должен предоставлять действия, запрещённые ролью, но
  окончательное решение всегда остаётся за backend.

## 11. Проверки

### Модульные и компонентные

- нормализация и проверка форм;
- точное хранение количества строкой;
- преобразование серверных ошибок в сообщения полей;
- таблицы: загрузка, пустой результат, данные, ошибка и пагинация;
- запрет изменения проведённого документа;
- доступность диалогов и управление фокусом;
- разрешения навигации для каждой роли.

### Интеграционные

- клиент корректно работает с актуальной OpenAPI-схемой;
- отменённые запросы не меняют состояние страницы;
- `request_id` отображается при ошибке;
- повторное нажатие не создаёт второй запрос;
- недоступный backend даёт восстанавливаемое состояние без потери формы.

### Сквозные

Минимальные сценарии:

1. создать единицу измерения, материал и поставщика, найти и архивировать их;
2. создать черновик поступления с несколькими строками и отправить его;
3. увидеть смену статуса до `posted` без двойного проведения;
4. получить ошибку обработки и выполнить разрешённый повтор;
5. сформировать отчёт за период, проверить раздельные единицы и скачать CSV;
6. проверить ограничения ролей;
7. имитировать недоступность API и восстановить работу без потери данных формы;
8. пройти основной сценарий клавиатурой на ширинах `360px`, `768px` и desktop.

Тесты используют отдельное окружение и изолированные данные. Не обращаться к
рабочей БД. Моки допустимы в компонентных тестах, но сквозной сценарий перед
слиянием должен работать с реальными тестовыми API, PostgreSQL и очередью.

## 12. Критерии приёмки

Задача готова к PR/MR, когда одновременно выполнены условия:

- реализованы все доступные роли и экраны из раздела 5;
- текущие справочники работают с реальным API;
- для отсутствующих backend-контрактов есть явные состояния недоступности и
  зарегистрированные задачи, без фиктивного сохранения;
- палитры `#E4DDD3` и `#00A19B` используются через дизайн-токены;
- интерфейс визуально цельный, минималистичный и адаптивный;
- все интерактивные состояния доступны с клавиатуры и проходят WCAG AA;
- ошибки API сохраняют пользовательский ввод и показывают `request_id`;
- количество не проходит через `number` и не теряет точность;
- production-сборка воспроизводима из lock-файла и не требует CDN;
- компонентные и сквозные тесты проходят;
- `make setup`, `make run`, `make test`, `make quality`, `make verify`,
  `make up`, `make down` и `make container-check` включают frontend там, где
  это применимо;
- README, инструкция запуска и API-документация обновлены;
- `make verify` проходит на актуальном коммите;
- выполнена живая демонстрация основного сценария и адаптивности; её результат
  зафиксирован человеком в задаче или записи релиза.

## 13. Порядок выполнения для Codex

1. Зафиксировать матрицу «экран → действие → API → роль → состояние ошибки».
2. Снять актуальную OpenAPI-схему и перечислить отсутствующие контракты.
3. Создать дизайн-токены и статический каркас оболочки.
4. Реализовать вертикальный срез справочника единиц: список, создание,
   изменение, архивирование, ошибки и тесты.
5. Распространить проверенный подход на материалы и поставщиков.
6. Реализовать поступления, отчёты и администрирование по мере появления
   подтверждённых API-контрактов.
7. Добавить адаптивность, доступность и сквозные сценарии.
8. Интегрировать команды разработки, CI и контейнерную сборку.
9.  Выполнить `make verify`, проверить production-образ и подготовить PR/MR.

## 14. Содержание PR/MR

В описании указать:

- номер и цель задачи;
- реализованные экраны и роли;
- использованные и отсутствующие API-контракты;
- результаты проверок и скриншоты основных разрешений экрана;
- результаты проверки доступности;
- изменения критических файлов: Makefile, CI/CD, Dockerfile, Compose, Nginx,
  тесты приёмки, пороги качества, README и технические требования;
- миграции и влияние на данные — ожидается «нет», если backend не менялся;
- способ отката frontend-сборки;
- известные ограничения и задачи продолжения.

Успешная локальная сборка не означает выпуск. До слияния нужны обязательные
проверки актуального коммита и независимое одобрение, а до объявления релиза —
CI/CD, проверка образа, готовности, сквозного сценария и наблюдение.
