# Политика контейнеров

Задача для трекера (номер не назначен): запретить небезопасную конфигурацию
контейнеров и проверять её командой `make container-check`. Границы: Dockerfile,
три Compose-контура, Make, тесты, резервное копирование и документация.
Схема БД не меняется. Критерий: негативные тесты политики, запуск с ненулевым UID,
готовность сервисов и реальное восстановление в изолированную БД.

## Обязательные правила

- Запрещены `latest` и ссылки на образы без тега или digest, включая `FROM`.
- Все запущенные контейнеры работают без root: PostgreSQL, API, UI, миграции,
  backup/restore, тесты и анализаторы. Запрещены `--user root`, UID 0,
  `privileged`, host network и добавление capabilities в Compose.
  Root во время **сборки** допустим для установки пакетов и назначения владельцев;
  он не должен оставаться пользователем запуска готового проектного образа.
- Секреты запрещены в `ARG`, `ENV`, `COPY` и слоях образа. Настройки передаются
  при запуске. При необходимости секретов для сборки применяют BuildKit secret
  mounts, а не build args. `.env`, ключи и каталоги `secrets` исключены из контекста.
  Сканер проверяет собранные образы; эвристический поиск не доказывает отсутствие
  любого произвольного секрета и не заменяет проверку изменений человеком.
- У PostgreSQL, API и UI обязателен healthcheck. `disable: true` и `NONE` запрещены.
  Одноразовые миграции, backup/restore и тесты проверяются по коду завершения;
  бессодержательный healthcheck для них не добавляется.
- На хост разрешены только API 8000 и UI 5173, по одному TCP-пробросу на
  `127.0.0.1`. Номера портов хоста настраиваются. PostgreSQL, миграции и инструменты
  портов не публикуют. Новые сервисы требуют явного изменения политики и ревью.

## Команды

Нужны Docker/Compose и Python 3.11+ на хосте для оркестрации; зависимости Python
для самой проверки устанавливать не нужно. Приложение и тесты остаются в Docker.

Linux:

```bash
make container-check
make verify
```

PowerShell из корня репозитория:

```powershell
python scripts/container_check.py
```

Проверка читает три Compose-файла с пустым `compose.test.env`, игнорирует рабочий
`ENV_FILE`, создаёт уникальный проект `inventory-policy-*`, использует учебные
реквизиты и свободные loopback-порты. Проверяет конфигурацию, UID процессов,
готовность, миграции, backup/restore и секреты образов через Trivy по image ID.
Рабочий проект не останавливает. Тома собственного проекта удаляет в `finally`,
в том числе при отказе. Образы остаются в Docker для повторного использования.
Результат: `reports/container-check.json`. Только `status: passed` подтверждает
успех полного запуска; `running` после прерывания успехом не является.

Для быстрой диагностики без сборки и запуска:

```powershell
python scripts/container_check.py --static-only
```

Это не заменяет полный `container-check` или `verify`. В `make verify` статическая
политика проверяется до сборки, а контейнерные сценарии — после тестов, на уже
собранных image ID. Статус `runtime-passed` означает, что сканирование ещё
предстоит в общем контуре. После всех проверок verify запускает рабочую среду.
Порядок и критерии: [VERIFY_PIPELINE.md](VERIFY_PIPELINE.md).

## Пользователи и каталоги

PostgreSQL запускается сразу как `70:70` (postgres в выбранном Alpine-образе).
Путь `/var/lib/postgresql/data` и UID не изменены. Новый именованный том получает
исходные права каталога из образа; entrypoint не выполняет root-инициализацию.
Существующий исправный том с владельцем 70 продолжает использоваться.

Для остальных сервисов используются `LOCAL_UID` и `LOCAL_GID`: Make и Linux
обёртка Compose берут UID/GID оператора, Windows по умолчанию использует 1000:1000.
Сборка и запуск должны использовать одинаковые значения. Запуск Make от root
отклоняется. Прямые команды Linux запускайте после:

```bash
export LOCAL_UID="$(id -u)" LOCAL_GID="$(id -g)"
python3 scripts/container_check.py --prepare-only
```

На Windows перед первым запуском backup или тестов можно подготовить каталоги без Python:

```powershell
New-Item -ItemType Directory -Force backups, reports, reports/unix-tests
```

Скрипт создаёт `backups`, `reports` и `reports/unix-tests` от оператора и проверяет
возможность записи. Он не делает chown существующих данных. Backup-файлы сохраняют
umask 077. Старые root-owned отчёты/копии на Linux требуют исправления владельца
администратором **на хосте**, после проверки точных путей; не используйте для этого
root-контейнер и не открывайте каталоги через chmod 777. Если существующие данные
PostgreSQL имеют другого владельца, остановитесь и согласуйте обслуживание тома;
автоматическая смена владельца рабочей БД запрещена.

После старых запусков от root проверьте не только сам `reports`, но и существующие
файлы внутри: новый пользователь может создавать файлы, но не перезаписывать
старый `junit.xml` или `.coverage`. Перед первым новым прогоном, когда проверки
остановлены, сохраните прежние отчёты в другом каталоге на хосте. Например, в
PowerShell (имя архива должно быть свободно):

```powershell
Move-Item reports reports-before-nonroot
New-Item -ItemType Directory -Force reports, reports/unix-tests
Move-Item reports-before-nonroot reports/archive-before-nonroot
```

В Linux аналогично переместите каталог силами оператора; если прав недостаточно,
исправление владельца выполняет администратор хоста по проверенному пути.
Не архивируйте каталог во время активной проверки и не добавляйте отчёты в Git.

Кэш pnpm теперь отдельный: `inventory-accountment-pnpm-store-nonroot-<UID>`.
Каталог `/pnpm/store` в образе принадлежит пользователю frontend. Старый кэш
сохраняется; при выборе собственного `PNPM_STORE_VOLUME` он должен быть доступен
новому UID. Смена UID требует пересборки образов и проверки прав существующих файлов.

Trivy в `image-scan` работает с ненулевым UID и дополнительной группой Docker socket.
Доступ к Docker daemon остаётся административной возможностью оператора, даже
при непривилегированном UID процесса; в рабочие сервисы socket не передаётся.

## Проверка и откат

Ревью требует отдельного внимания к Makefile, Dockerfile/Dockerfile.tests,
Compose, `.dockerignore`, скриптам сборки/политики и регрессионным тестам.
Сохраните отчёты `container-check`, полного `verify` и CI актуального коммита.
Для отката верните совместимую версию исходников и пересоберите образы с прежними
UID/GID; именованный том БД не удаляйте. Изменение инфраструктуры само по себе
не является человеческой приёмкой или релизом.

Основания: [пользователи PostgreSQL](https://hub.docker.com/_/postgres),
[права и заполнение Docker volumes](https://docs.docker.com/engine/storage/volumes/),
[секреты сборки](https://docs.docker.com/build/building/secrets/).


## Диагностика Frontend — 22.10.2026

Задача без номера: TASK.md. Причина исходного отказа **не подтверждена**:
сохранённый лог не идентифицирует команду. Управляемая модель удаления status
во время чтения подтверждает возможность гонки, но не её наличие в исходном запуске.
Новая POSIX sh-проверка требует валидные UID и проверенный PID 1, проверяет real/effective
UID, допускает только исчезновение файла после неудачного чтения. Ошибки чтения
существующего файла и некорректные данные блокируют проверку.

Команды сообщают этап и сервис; отказы сохраняют код и уникальный отчёт
reports/container-check-command-*.log. Произвольный stdout/stderr скрыт;
сохраняется только безопасный протокол PID, без argv/env/inspect и команд процессов.
Тайм-ауты и ошибки запуска сообщаются отдельно. Ошибка cleanup сохраняется вместе
с исходной ошибкой; очистка ограничена созданным изолированным Compose-проектом.

Проверки в существующем inventory-accountment-tests:local с bind mount, без сборки
и сети: Ruff format --check, Ruff check, mypy для двух скриптов и двух unit-модулей;
pytest -o addopts= --no-cov tests/unit/test_container_policy.py
 tests/unit/test_critical_mutations.py -q: 15 passed, 22 subtests passed.
Короткий запуск PROCESS_CHECK в существующем Frontend-образе (UID 1000,
network none, timeout 10) успешен. Первый пробный файл имел CRLF и был отклонён sh;
после исправления только пробного файла на LF сценарий успешен.

Полный verify/container-check не запускались по ограничению пользователя.
Проверка всех сервисов, CI и человеческая приёмка не проводились. Регрессии cleanup
и реального отказа доступа в Linux отдельно не воспроизводились; проверен отказ
инструмента чтения на существующем status. Рабочая среда и данные не менялись.
Критические изменения: scripts/container_check.py и регрессии политики контейнеров.
Откат — revert коммита, без удаления томов и изменения БД.


## HTTP smoke — 22.10.2026

Подтверждён дефект диагностики: прежний фильтр принимал только PID и терял
контекст HTTP smoke. Теперь этап app: HTTP smoke отделён от pg-tools: backup/restore.
Протокол smoke-v1 содержит только фиксированные шаг, метод, путь, состояние,
категорию и числовой статус. Поля, типы, длина и значения проверяются; raw
stdout/stderr, traceback и тела HTTP не сохраняются. Отчёты:
reports/container-check-command-*.log. Ошибка без события не доказывает отказ API.

Воспроизведение: уникальный inventory-smoke-<случайный суффикс>, новая БД,
только db/migrate/app из разрешённой Compose-конфигурации, без опубликованных
портов. Существующий runtime-образ использован только как среда зависимостей:
актуальные app/scripts/migrations подключены read-only. Образы не пересобирались.
Smoke дважды прошёл, очистка проекта завершилась успешно. Последний отчёт:
reports/container-check-command-3e4b19c09b2d.log. Первопричина исходного отказа
не воспроизведена и не устранена; API не изменялся. Требуется безопасный отчёт

Целевые проверки: Ruff format --check, Ruff check, mypy (три изменённых Python-файла),
