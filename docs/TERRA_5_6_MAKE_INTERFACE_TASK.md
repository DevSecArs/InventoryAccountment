# Техническое задание для агента 5.6 Terra

## 1. Цель работы

В ветке `feature/make-interface-setup` создать единый воспроизводимый локальный контур разработки и проверки проекта InventoryAccountment.
```text
задача → изменение → Docker-развёртывание → локальные проверки →
предложение коммита пользователю → Git → CI → образ → проверка релиза
```

Номер задачи во внешнем трекере не предоставлен. Не выдумывать номер, созданную задачу, коммит, PR или результаты CI.

## 3. Обязательные ограничения

1. Соблюдать KISS, DRY и SOLID. Новый слой абстракции добавлять только при наличии двух или более реальных потребителей либо отдельной ответственности, которую нельзя ясно оставить в текущем модуле.
2. Не добавлять фиктивные успешные цели Make, заглушки проверок, пустые миграции и тесты без значимых утверждений.
3. Не удалять и не ослаблять существующие тесты. Не снижать пороги, не отключать анализаторы, не добавлять `noqa`, `type: ignore`, исключения покрытия или SAST без воспроизводимой причины и отдельного согласования пользователя.
4. Не использовать SQLite вместо PostgreSQL в интеграционных и миграционных тестах.
5. Не применять `Base.metadata.create_all()` вместо Alembic при создании тестовой схемы.
6. Не хранить количества в `float`; использовать `Decimal` и PostgreSQL `NUMERIC(18,3)`.
7. Не хранить секреты, реальные `.env`, дампы и отчёты с пользовательскими данными в Git.
8. Не выполнять destructive restore в обычную БД по умолчанию. Без явного подтверждения восстановление выполняется только в новой или тестовой БД.
9. `make down` без `LOCAL=1` не удаляет тома. Удаление временных томов допускается только для изолированного тестового Compose-проекта.
10. Очередь, outbox, worker, отчёты, Nginx, мониторинг и CD не реализовывать в этой ветке. Они остаются отдельными этапами ТЗ.
11. Не переписывать существующую архитектуру каталогов и аутентификации без необходимости для текущего задания.
12. При неустранимой неоднозначности, необходимости ослабить проверку или риске изменения нетестовых данных остановиться и задать пользователю один конкретный вопрос.

## 4. Правило «одна задача — один коммит»

Ниже определены семь задач. Каждая задача соответствует ровно одному осмысленному коммиту.

Агент **не выполняет `git commit`**. После каждой задачи агент обязан:

1. развернуть актуальное состояние проекта локально в Docker;
2. выполнить указанные проверки и сохранить реальные результаты;
3. проверить `git diff --check` и `git status --short`;
4. перечислить изменённые критические файлы и объяснить влияние на приёмку;
5. остановиться и предложить пользователю самостоятельно проверить и закоммитить изменение;
6. вывести рекомендуемый заголовок и тело коммита;
7. не переходить к следующей задаче до явного сообщения пользователя, что коммит выполнен или продолжение разрешено.

Перед продолжением проверить, что изменения предыдущей задачи больше не находятся в рабочем дереве. Не изменять и не объединять чужие незакоммиченные правки.

## 5. Режимы команд

Пользователь подтвердил следующий интерфейс:

```bash
make <target> LOCAL=1  # отдельная PostgreSQL разворачивается в Docker
make <target>         # подключение к серверу по настройкам из .env
```

Правила режимов:

- `LOCAL=1` использует отдельный Compose project, отдельную БД с именем, явно содержащим суффикс `_test`, отдельные реквизиты и временный том.
- Тестовый режим не читает обычный `DATABASE_URL` из `.env` и не публикует PostgreSQL наружу без необходимости.
- Backend-тесты и служебные команды в тестовом режиме запускаются в контейнере в одной Docker-сети с тестовой БД.
- Перед любой очисткой тестовый скрипт проверяет имя Compose project, имя БД и `APP_ENV=test`.
- Без `LOCAL=1` команды используют `.env`, не создают PostgreSQL автоматически и не меняют целевую БД без явно выбранной команды.
- Повторный `setup`, `up` и `migrate` должен быть безопасным.

## 6. Итоговый контракт Makefile

| Команда | Обязательное поведение |
| --- | --- |
| `make setup [LOCAL=1]` | Проверить версии инструментов, установить зависимости строго по lock-файлам, создать `.env` из примера только при отсутствии файла; не перезаписывать пользовательскую конфигурацию |
| `make run [LOCAL=1]` | Запустить FastAPI; в тестовом режиме использовать контейнерную тестовую БД, без тестового режима — `DATABASE_URL` из `.env` |
| `make test [LOCAL=1]` | Запустить unit-, integration- и API-тесты, frontend-тесты, проверить покрытие, сформировать JUnit и coverage-отчёты |
| `make quality [LOCAL=1]` | Проверить форматирование без изменения файлов, выполнить lint, типизацию и SAST; frontend также должен пройти форматирование и типизацию |
| `make migrate [LOCAL=1]` | Выполнить `alembic upgrade head` в явно выбранном окружении |
| `make backup [LOCAL=1]` | Создать проверяемый дамп PostgreSQL и метаданные копии; вывести путь, время, checksum и Alembic revision без секретов |
| `make restore BACKUP=<path> [LOCAL=1]` | Проверить файл и checksum, восстановить в отдельную целевую БД, применить/проверить миграции и контрольные данные; перезапись требует явного подтверждения |
| `make up [LOCAL=1]` | Собрать и запустить соответствующее контейнерное окружение, дождаться readiness |
| `make down [LOCAL=1]` | Остановить окружение; обычный режим сохраняет тома, тестовый удаляет только свои временные ресурсы |
| `make container-check LOCAL=1` | В изолированном Compose project собрать образ, применить миграции, проверить health и сквозной API-сценарий, затем удалить только тестовые ресурсы |
| `make verify LOCAL=1` | Последовательно выполнить все обязательные локальные проверки; первая ошибка немедленно завершает команду ненулевым кодом |

Допустимы внутренние цели `migration-check`, `backup-restore-check` и `mutation`, если они реально используются `verify` и документированы. Пользовательский интерфейс из таблицы обязателен.

## 7. Требования к зависимостям и образам

- Зафиксировать точные версии прямых и транзитивных Python-зависимостей единым lock-файлом. Предпочтительный вариант — `uv.lock` и `uv sync --frozen`; версия самого `uv` также фиксируется в Dockerfile/инструкции.
- Не оставлять диапазоны как единственный источник установки. `pyproject.toml` остаётся описанием проекта, lock-файл — источником воспроизводимой установки.
- Frontend устанавливать только через `pnpm install --frozen-lockfile`; сохранить `packageManager: pnpm@11.19.0` либо обновить его только вместе с lock-файлом и обоснованием.
- Зафиксировать совместимые версии Python, Node.js, pnpm и PostgreSQL. Контейнерные базовые образы закрепить точным тегом; для приёмочного/CI-контура предпочтительно также закрепить digest.
- Разделить runtime- и development-зависимости. В production-слой не включать pytest, линтеры и исходные отчёты.
- Dockerfile должен быть воспроизводимым, использовать непривилегированного пользователя, не копировать `.env`, дампы, `.git` и локальные артефакты.

## 8. Требования к тестированию

### 8.1. Структура

Использовать простую структуру:

```text
tests/
├── unit/
├── integration/
├── migrations/
└── acceptance/
```

- Unit-тесты не обращаются к сети и БД.
- Integration-тесты работают с настоящей PostgreSQL тестового Compose-проекта.
- API-тесты проверяют приложение через FastAPI-клиент и настоящую тестовую транзакцию/БД.
- Migration-тесты создают БД исключительно миграциями Alembic.
- Acceptance-тесты проверяют контейнерный smoke-сценарий и backup/restore.

### 8.2. Изоляция

- Добавить отдельный пример тестовой конфигурации без секретов.
- При старте тестов аварийно завершаться, если `APP_ENV != test`, имя БД не содержит `_test` или URL совпадает с обычным `DATABASE_URL`.
- Каждый тест получает предсказуемое состояние. Разрешены транзакционный rollback либо очистка таблиц в корректном порядке внутри тестовой БД.
- Параллельные запуски не должны использовать один Compose project или один том; добавить уникальный суффикс запуска либо сериализовать доступ явно.

### 8.3. Минимальный набор сценариев

Проверить как минимум:

- нормализацию и границы кодов, SKU, логина, имён и строковых полей;
- пустые строки, внешние пробелы, регистр, значения ровно на границе и на один символ длиннее;
- допустимые и недопустимые коды СИ;
- уникальность кодов, SKU, логинов и бизнес-ключей на уровне приложения и PostgreSQL;
- внешние ключи и откат транзакции после ошибки;
- поиск, пагинацию, архивирование и запрет выбора архивных значений;
- аутентификацию, истечение/отсутствие сессии, CSRF и права администратора;
- `/health/live`, `/health/ready`, недоступную БД и заголовок `X-Request-ID`;
- единый формат ошибок и статусы 401, 403, 404, 409, 422, 500 и 503 там, где они применимы;
- для поступлений: положительность и точность количества, непустой список позиций, уникальность материала в документе, архивные справочники и неизменяемость нечернового документа;
- сохранность данных при миграции и после backup/restore.

### 8.4. Покрытие и связь с ТЗ

Создать `docs/TEST_MATRIX.md`: строка требования ТЗ → тест → уровень теста → команда запуска.

- Не менее 40% функциональных областей раздела «Функции» в `docs/Техническое_задание.md` должны иметь исполняемые автоматические сценарии. Итог этой ветки должен покрывать как минимум health/ошибки, аутентификацию, справочники, черновики поступлений, миграции и backup/restore.
- Покрытие строк основной backend-бизнес-логики — не ниже 80% согласно действующему ТЗ и `AGENTS.md`.
- Порог фиксируется конфигурацией pytest/coverage и проверяется командой, а не только указывается в документации.
- Отчёты: JUnit XML, `coverage.xml` и HTML coverage. Каталог отчётов игнорируется Git, кроме при необходимости пустого маркера.

### 8.5. Мутационная устойчивость

Подключить закреплённую версию средства мутационного тестирования, например `mutmut`, и ограничить его основной бизнес-логикой. Проверка не должна модифицировать рабочее дерево: выполнять мутации в контейнерной копии исходников или временном каталоге.

Критические мутации должны уничтожаться тестами:

- `>` заменено на `>=` для количества;
- разрешён архивный поставщик или материал;
- удалена проверка уникальности позиции;
- допустим запрещённый статус или редактирование нечернового документа;
- отключена проверка CSRF/роли;
- readiness возвращает успех при недоступной БД.

Нельзя добавлять исключение мутации только для получения зелёного результата.

## 9. Требования к миграциям

Alembic уже подключён. Не создавать новый механизм миграций параллельно существующему.

Итоговая линейная цепочка должна содержать не менее трёх содержательных ревизий:

```text
80e51d31f477 → d2a2c780d001 → новая ревизия черновиков поступлений
```

Две существующие ревизии засчитываются. Не дробить новую схему на пустые или искусственные миграции ради числа файлов.

Автоматическая проверка миграций должна:

1. создать чистую временную БД и выполнить `alembic upgrade head`;
2. проверить наличие таблиц, индексов, внешних ключей, уникальных ограничений и check constraints;
3. создать вторую временную БД на предыдущей поддерживаемой ревизии;
4. заполнить её каталогами, пользователем и связанными данными;
5. выполнить обновление до `head`;
6. доказать сохранность исходных строк и работоспособность новой функции;
7. проверить хотя бы `downgrade -1`/повторный `upgrade head` для новой ревизии, если downgrade не разрушает предшествующие данные;
8. завершаться ошибкой при нескольких heads, пустой миграции или расхождении моделей и схемы.

## 10. Новая функция приложения

Реализовать минимальную законченную функцию: **создание, просмотр, список и редактирование черновика поступления с позициями**.

### 10.1. Схема

Новая третья миграция создаёт:

- `receipts`: UUID-идентификатор, `supplier_id`, нормализованный `document_number`, `received_at`, статус `draft`, временные поля и поля, необходимые для дальнейшего безопасного расширения;
- `receipt_items`: UUID-идентификатор, `receipt_id`, `material_id`, `quantity NUMERIC(18,3)`;
- уникальность `(supplier_id, document_number)`;
- уникальность `(receipt_id, material_id)`;
- check constraint `quantity > 0` и допустимого статуса;
- внешние ключи и индексы по требованиям ТЗ.

Не добавлять outbox, историю статусов и очередь в эту миграцию: отправка и асинхронное проведение не входят в текущую функцию.

### 10.2. Правила

- Черновик содержит минимум одну позицию.
- Поставщик и материалы существуют и не архивированы.
- Единица материала существует; исторические связи не обходятся ручными значениями.
- Количество принимает не более трёх знаков после запятой и строго больше нуля.
- Один материал встречается в черновике один раз.
- Номер документа после `strip` не пуст, ограничен 64 символами и уникален у поставщика.
- Изменять или удалять позиции можно только при статусе `draft`.
- Проверки приложения дублируются ограничениями БД там, где это возможно.
- Ошибки преобразуются в существующий единый HTTP-формат: 404 для отсутствующей сущности, 409 для конфликта, 422 для неверного ввода.
- Использовать существующие транзакции сессии; не делать вложенные скрытые `commit` в CRUD-функциях сущностей.
- Использовать существующие зависимости аутентификации и CSRF, не копировать их реализацию.

### 10.3. HTTP API

Добавить минимальные маршруты `/api/v1/receipts`:

- `POST /` — создать черновик с позициями;
- `GET /` — список с пагинацией;
- `GET /{receipt_id}` — получить черновик с позициями;
- `PATCH /{receipt_id}` — изменить реквизиты и/или полный состав позиций атомарно.

Удаление, отправка в очередь, проведение и frontend-экран не входят в эту задачу. Не публиковать неработающие маршруты.

## 11. Backup и restore

- Использовать штатные `pg_dump` и `pg_restore` той же основной версии PostgreSQL, что и сервер.
- Формат копии — custom либо directory; рядом создать метаданные с UTC-временем, именем исходной БД, Alembic revision, размером и SHA-256.
- Пароль и полный URL с реквизитами в имя файла, журнал и метаданные не включать.
- Перед restore проверить существование файла, checksum, читаемость архива и совместимость версии.
- По умолчанию восстанавливать в новую БД. Для перезаписи требовать `TARGET_DATABASE_URL` и точное подтверждение имени целевой БД отдельной переменной.
- Автоматический `backup-restore-check LOCAL=1` обязан:
  1. заполнить тестовую БД известными связанными данными;
  2. создать копию;
  3. намеренно удалить либо изменить часть данных;
  4. восстановить копию в отдельную тестовую БД;
  5. сравнить контрольные значения, связи, количество строк и Alembic revision;
  6. удалить только временные БД и дампы тестового запуска.

## 12. Quality, SAST и отчёты

Закрепить версии инструментов и настроить:

- Python: `ruff format --check`, `ruff check`, `mypy`, `bandit`;
- зависимости: проверку известных уязвимостей lock-файла подходящим закреплённым инструментом;
- frontend: проверку форматирования, lint и `tsc` без изменения файлов;
- тесты: pytest/Vitest, JUnit и coverage-отчёты;
- контейнер: сборку и минимальную проверку образа; находки High/Critical должны блокировать проверку, если нет отдельно согласованного временного исключения.

Конфигурации анализаторов находятся в репозитории. `make quality` только проверяет и не исправляет файлы.

## 13. Состав `make verify LOCAL=1`

Команда должна печатать понятное название каждого шага и завершаться при первой ошибке:

1. проверка lock-файлов и воспроизводимой установки;
2. `make quality LOCAL=1` — форматирование, lint, типизация, SAST и аудит зависимостей;
3. `make test LOCAL=1` — unit/integration/API/frontend, отчёты и порог покрытия;
4. целевой mutation-check критической бизнес-логики;
5. migration-check на чистой и заполненной БД;
6. backup-restore-check с намеренным повреждением тестовых данных;
7. `make container-check LOCAL=1` — сборка образа, миграция, readiness и сквозной API-сценарий;
8. проверка отсутствия незаявленных изменений схемы и оставшихся тестовых контейнеров/томов текущего запуска.

CI в GitHub Actions должен вызывать тот же `make verify LOCAL=1`, а не дублировать его шаги в YAML. Загружать тестовые и coverage/SAST-отчёты как артефакты даже при неуспехе. Успешный локальный запуск не считать успешным CI или релизом.

В README объяснить назначение каждого шага `verify`, ожидаемые артефакты и типичные причины отказа.

## 15. Контрольная проверка на защите

После пользовательского коммита задачи 7 выполнить без новых правок:

1. **Контрольное изменение условия.** Во временной контейнерной копии заменить одно условие основной логики, например `quantity > 0` на `quantity >= 0`. Показать падение конкретного теста. Удалить временную копию; рабочее дерево не менять.
2. **Чистая БД.** Создать новую тестовую БД, выполнить миграции от `base` до `head`, проверить API черновика.
3. **Заполненная БД.** Развернуть предыдущую ревизию, загрузить данные, обновить до `head`, доказать сохранность строк и работу новой таблицы.
4. **Восстановление.** Создать backup, удалить или изменить известную строку, восстановить копию в отдельную БД и показать исходное значение.
5. **Объяснение verify.** Для каждого шага `make verify` назвать назначение, входы, артефакты и пример ошибки, которая блокирует продолжение.
6. **Чистота.** Показать отсутствие забытых контейнеров и временных томов данного запуска, а также чистое рабочее дерево.

Живая демонстрация и человеческая приёмка фиксируются пользователем. Агент не объявляет защиту, PR, CI или релиз состоявшимися без фактического подтверждения.

## 16. Критерии завершения

Работа завершена, когда одновременно выполнены условия:

- все семь задач представлены отдельными пользовательскими коммитами;
- полный командный интерфейс Make реализован и документирован;
- обычный режим использует `.env`, тестовый — изолированную PostgreSQL в Docker;
- версии и lock-файлы закреплены, установка воспроизводима;
- backend-покрытие не ниже 80%, а тестовая матрица охватывает не менее 40% функциональных областей ТЗ;
- тесты проверяют ошибки, границы, ограничения БД и обязательные правила;
- mutation-check обнаруживает изменение критических условий;
- цепочка Alembic содержит минимум три содержательные ревизии и проходит чистое/заполненное обновление;
- черновики поступлений реализованы через новую схему и API;
- backup/restore реально восстанавливает намеренно повреждённые тестовые данные;
- `make verify LOCAL=1` проходит целиком и объясним по шагам;
- CI вызывает тот же `make verify LOCAL=1` и сохраняет отчёты;
- правила запрета ослабления проверок закреплены в документации;
- нет секретов, дампов, отчётов и тестовых данных в Git;
- критические файлы перечислены в описании будущего PR с причиной и влиянием на приёмку.
