# Техническое задание на исправление проекта перед приёмкой

## 1. Цель

Устранить дефекты, обнаруженные при предварительной приёмке ветки
`feature/make-interface-setup`, и получить воспроизводимый обязательный контур,
который полностью проходит локально в Docker и затем тем же способом запускается
в CI.

После выполнения задания проект должен обеспечивать следующий путь изменения:

```text
задача → отдельная ветка → изменение и тесты → локальный Docker-контур →
make verify LOCAL=1 → коммит пользователя → PR/MR → CI → одобрение → слияние
```

Номер задачи во внешнем трекере не предоставлен. Исполнитель не выдумывает
номер, созданный PR/MR, результаты CI или факт приёмки.

## 2. Обязательное изменение командного интерфейса

Публичный параметр Make `TEST` переименовать в `LOCAL` во всём репозитории.

Новый интерфейс:

```bash
make setup LOCAL=1
make run LOCAL=1
make test LOCAL=1
make quality LOCAL=1
make migrate LOCAL=1
make backup LOCAL=1
make restore LOCAL=1 BACKUP=backups/<имя>.dump
make verify LOCAL=1
make up LOCAL=1
make down LOCAL=1
make container-check LOCAL=1
```

Правила переименования:

1. `LOCAL=1` означает запуск в изолированном локальном Docker-контуре с
   отдельной PostgreSQL и временными данными.
2. Без `LOCAL=1` команды используют настройки обычного окружения из `.env` и
   не должны автоматически удалять его тома или данные.
3. Старый параметр `TEST` удалить из Makefile, workflow, скриптов, README,
   руководств и технических документов. В исторических описаниях допускается
   оставить его только в явно помеченной записи о миграции интерфейса.
4. Передача `TEST=1` не должна молча запускать обычное окружение. Makefile обязан
   завершить команду ошибкой и вывести указание использовать `LOCAL=1`.
5. Внутренние признаки тестового окружения `APP_ENV=test`, `TEST_DATABASE_URL`,
   `.env.test` и суффикс имени БД `_test` не переименовывать: они описывают
   назначение данных, а не пользовательский режим Make.
6. Все примеры и сообщения об ошибках должны использовать новое имя `LOCAL`.

## 3. Исходные проблемы

Перед изменениями исполнитель повторно проверяет состояние репозитория. На
момент составления задания подтверждены следующие проблемы:

- `make verify TEST=1` завершается с ненулевым кодом на `git diff --check` при
  запуске Linux-инструментов над Windows checkout;
- финальная проверка `git diff --check` не проверяет уже закоммиченную разницу
  ветки с базовой веткой;
- PATCH черновика поступления принимает номер, состоящий только из пробелов;
- отсутствует обязательная часть граничных, ошибочных и мутационных сценариев;
- контейнерный образ и репозиторий не проверяются на High/Critical уязвимости и
  утечки секретов в обязательном контуре;
- локальные параллельные запуски используют одно имя Compose project и один том;
- `GUIDE.md` отсутствует, а `docs/INITIAL_RUN.md` содержит устаревшее описание;
- текущая ветка не опубликована, поэтому успешный CI актуального коммита не
  подтверждён;
- отсутствует `.github/CODEOWNERS` и нет подтверждения настроенной защиты
  основной ветки.

## 4. Общие ограничения

1. Соблюдать KISS, DRY и SOLID. Не добавлять слой абстракции без отдельной
   ответственности или нескольких реальных потребителей.
2. Не удалять и не ослаблять тесты, анализаторы и проверки ради зелёного
   результата. Не снижать порог покрытия 80%.
3. Не добавлять необоснованные `noqa`, `type: ignore`, исключения SAST,
   исключения уязвимостей или переживших мутантов.
4. Интеграционные, миграционные и backup/restore-проверки выполнять только с
   PostgreSQL. SQLite и `Base.metadata.create_all()` не использовать.
5. Не хранить количества в `float`. Использовать `Decimal` и
   `NUMERIC(18,3)`.
6. Не изменять обычную БД и её тома во время локальных проверок. Разрушительные
   сценарии допустимы только в проверенном изолированном окружении.
7. Не коммитить `.env`, секреты, дампы, отчёты, кэши и рабочие данные.
8. Не объявлять CI, независимое одобрение, слияние, релиз или живую приёмку
   состоявшимися без фактического подтверждения.

## 5. Порядок выполнения и коммитов

Одна задача из раздела 6 соответствует одному осмысленному коммиту. Исполнитель
не выполняет `git commit` самостоятельно.

После каждой задачи исполнитель обязан:

1. развернуть актуальный проект локально в Docker;
2. применить миграции, если задача затрагивает приложение или схему;
3. выполнить затронутые тесты и полный доступный обязательный контур;
4. проверить `git diff --check` и `git status --short`;
5. перечислить изменённые критические файлы и влияние на приёмку;
6. остановиться, сообщить реальные результаты и предложить пользователю
   проверить изменение;
7. вывести рекомендуемые заголовок и тело коммита;
8. продолжить следующую задачу только после сообщения пользователя о коммите
   либо явного разрешения продолжить.

После задачи 1 все команды последующих задач используют только `LOCAL=1`.

## 6. Задачи реализации

### Задача 1. Переименовать Make-параметр и стабилизировать базовый контур

Изменить пользовательский интерфейс `TEST=1` на `LOCAL=1` во всех исполняемых
файлах и документации. Добавить явный отказ при использовании старого
параметра.

Одновременно:

- нормализовать текстовые файлы через `.gitattributes`, включая LF для shell,
  Makefile, Python, YAML, TOML и Markdown;
- исправить уже существующие whitespace-ошибки;
- разделить проверку чистоты рабочего дерева и проверку разницы ветки с её
  merge-base;
- не использовать жёстко заданное имя Compose project для всех локальных
  запусков: применять безопасный уникальный суффикс запуска либо документированную
  сериализацию;
- при очистке удалять только ресурсы текущего локального запуска;
- обеспечить повторный запуск `make setup LOCAL=1`, включая случай существующих
  локальных `node_modules` и кэшей.

Минимальные проверки:

```bash
make setup LOCAL=1
make up LOCAL=1
make migrate LOCAL=1
make container-check LOCAL=1
make down LOCAL=1
make verify TEST=1        # ожидаемый управляемый отказ с подсказкой
git diff --check <merge-base>...HEAD
```

Рекомендуемый коммит:

```text
[FIX] Переименовать локальный Make-режим в LOCAL

Заменён параметр TEST на LOCAL, добавлен безопасный отказ для старого имени,
нормализованы окончания строк и изолированы ресурсы параллельных запусков.
```

### Задача 2. Исправить инварианты черновика поступления

Для создания и изменения поступления обеспечить одинаковые правила:

- номер после `strip` не пуст и не длиннее 64 символов;
- номер уникален в пределах поставщика;
- конфликт уникальности, включая конкурентную вставку, возвращает HTTP 409, а
  не HTTP 500;
- список позиций не пуст;
- материал в документе уникален;
- количество строго больше нуля и укладывается в `NUMERIC(18,3)`;
- архивные поставщик, материал и единица недоступны для нового документа;
- изменять можно только документ со статусом `draft`;
- ошибка полностью откатывает транзакцию.

Непустой номер закрепить ограничением PostgreSQL. Изменение схемы выполнить
новой последовательной миграцией Alembic с корректным downgrade. Миграция
должна безопасно обрабатывать уже существующие данные: при обнаружении
несовместимых строк завершаться понятной ошибкой без частичного изменения.

Минимальные проверки:

```bash
make test LOCAL=1
make migration-check LOCAL=1
make verify LOCAL=1
```

Рекомендуемый коммит:

```text
[FIX] Закрепить инварианты черновика поступления

Валидация создания и изменения приведена к единым правилам, конфликты
возвращают 409, а непустой номер защищён приложением и PostgreSQL.
```

### Задача 3. Дополнить тесты ошибочных и граничных случаев

Добавить unit-, API- и integration-тесты минимум для следующих сценариев:

- пустая строка, строка из пробелов, 64 и 65 символов в номере документа;
- нормализация внешних пробелов;
- дубликат номера у одного поставщика и допустимость такого номера у другого;
- повтор материала в позициях;
- количество `0`, отрицательное, минимальное положительное, слишком точное и
  выходящее за разрядность;
- пустой список позиций;
- неизвестные и архивные ссылки;
- изменение нечернового документа;
- откат транзакции после ошибки;
- конфликт ограничения PostgreSQL;
- 404, 409 и 422 в едином формате ошибки;
- readiness при недоступной БД возвращает 503;
- отсутствие и истечение сессии, CSRF и права администратора;
- границы пагинации и поисковых параметров.

Обновить `docs/TEST_MATRIX.md`: для каждого обязательного правила указать
конкретный тест, уровень и команду. Порог покрытия оставить не ниже 80%, но не
использовать покрытие строк как замену функциональным сценариям.

Проверки:

```bash
make test LOCAL=1
make verify LOCAL=1
```

Рекомендуемый коммит:

```text
[TEST] Покрыть обязательные граничные правила

Добавлены проверки поступлений, ошибок API, недоступности БД, сессий и
транзакционного отката; матрица тестов связана с требованиями.
```

### Задача 4. Усилить мутационную защиту

Мутационная проверка должна уничтожать критические изменения:

- `quantity > 0` заменено на `quantity >= 0`;
- разрешён архивный поставщик или материал;
- удалена проверка уникальности материала в документе;
- разрешено редактирование нечернового документа;
- отключена проверка CSRF или роли;
- readiness возвращает успех при недоступной БД.

Тайм-ауты, ошибки подготовки и неожиданные исключения не считать уничтоженным
мутантом. Проверка должна подтвердить ожидаемую причину отказа теста. Задать
ограниченный и документированный порог времени; необработанные тайм-ауты и
выжившие критические мутанты завершают команду ошибкой.

Проверки:

```bash
make mutation LOCAL=1
make verify LOCAL=1
```

Рекомендуемый коммит:

```text
[TEST] Усилить мутационную защиту бизнес-правил

Критические мутации поступлений, доступа и readiness блокируют проверку;
тайм-ауты и ошибки запуска больше не засчитываются как успешное уничтожение.
```

### Задача 5. Добавить проверки безопасности поставки

Закрепить версии инструментов и включить в обязательный контур:

- SAST Python-кода;
- аудит Python- и frontend-зависимостей по lock-файлам;
- поиск подтверждённых секретов в истории и текущей разнице;
- сканирование собранного контейнерного образа;
- блокировку неподтверждённых High/Critical находок.

Исключение допускается только отдельным файлом политики с причиной, ссылкой на
задачу, владельцем, сроком действия и независимым одобрением. Не добавлять
исключения в рамках этой задачи только ради зелёного результата.

Сформировать машинно-читаемые отчёты в `reports/` и загружать их из CI при
успехе и отказе. Проверка образа должна анализировать тот же image ID или digest,
который прошёл `container-check`.

Проверки:

```bash
make quality LOCAL=1
make container-check LOCAL=1
make verify LOCAL=1
```

Рекомендуемый коммит:

```text
[SEC] Проверять секреты и контейнерный образ

Обязательный контур блокирует утечки и неподтверждённые High/Critical находки,
а CI сохраняет отчёты анализа.
```

### Задача 6. Актуализировать руководство и правила приёмки

Создать `GUIDE.md` с воспроизводимыми инструкциями:

- требования к Git, GNU Make, Docker Compose, Python, Node.js и pnpm;
- первоначальная настройка через `make setup LOCAL=1`;
- запуск, миграции, тесты, backup и restore;
- назначение каждого шага `make verify LOCAL=1`;
- расположение отчётов и диагностика типичных отказов;
- безопасная очистка локального окружения;
- контрольная демонстрация перед приёмкой.

Обновить README, `docs/INITIAL_RUN.md`, `docs/TEST_MATRIX.md`, AGENTS.md и
остальные актуальные документы. Удалить утверждения о том, что уже реализованные
поступления, quality или verify отсутствуют. Все команды должны использовать
`LOCAL`, а фактическое поведение документации должно совпадать с Makefile.

Проверки:

```bash
rg -n "TEST=|\$\(TEST\)|TEST \?=" . \
  -g '!docs/CODE_FIX_ACCEPTANCE_TASK.md' -g '!.git/**'
make verify LOCAL=1
git diff --check
```

Первый `rg` должен не найти использования старого публичного параметра.

Рекомендуемый коммит:

```text
[DOC] Актуализировать локальный запуск и приёмку

Добавлен GUIDE.md, устранены устаревшие инструкции и описан полный контур с
параметром LOCAL.
```

### Задача 7. Подготовить CI и организационные проверки

Workflow GitHub Actions должен:

- запускать `make setup LOCAL=1` и тот же `make verify LOCAL=1`;
- не дублировать бизнес-логику Makefile в YAML;
- сохранять JUnit, coverage, SAST, dependency, secret и image-scan отчёты при
  любом результате;
- использовать минимальные permissions;
- закреплять сторонние actions неизменяемыми commit SHA;
- отменять устаревший запуск той же ветки, не смешивая ресурсы разных веток.

Добавить `.github/CODEOWNERS` для критических файлов. Конкретного пользователя
или команду не выдумывать: если владелец не указан пользователем или настройкой
репозитория, остановиться и запросить его перед созданием файла.

Пользователю предоставить список настроек защиты основной ветки:

- запрет прямой записи;
- обязательный успешный workflow актуального SHA;
- минимум одно независимое одобрение;
- обязательное одобрение CODEOWNERS для критических файлов;
- сброс одобрения после новых изменений;
- запрет merge при нерешённых обсуждениях.

Рекомендуемый коммит:

```text
[CI] Закрепить обязательный контур приёмки

CI запускает make verify LOCAL=1, сохраняет отчёты и назначает отдельную
проверку критических файлов через CODEOWNERS.
```

## 7. Состав итоговой команды `make verify LOCAL=1`

Команда выполняет шаги последовательно и прекращает работу после первой ошибки:

1. проверка окружения и гарантии использования локальной тестовой БД;
2. проверка Python- и frontend-lock-файлов;
3. форматирование, lint и типизация без изменения файлов;
4. SAST, аудит зависимостей и поиск секретов;
5. unit-, integration-, API- и frontend-тесты;
6. проверка покрытия не ниже 80% и создание отчётов;
7. мутационная проверка критических правил;
8. миграции на чистой и заполненной БД, downgrade и повторный upgrade;
9. backup, намеренное повреждение данных, restore в отдельную БД и сравнение;
10. сборка контейнерного образа и блокирующее сканирование уязвимостей;
11. применение миграций, readiness и HTTP-сценарий через запущенные контейнеры;
12. проверка отсутствия оставшихся ресурсов текущего запуска;
13. проверка незаявленного расхождения моделей и схемы;
14. проверка рабочего дерева и committed diff ветки относительно merge-base.

Команда формирует понятное название каждого шага и возвращает ненулевой код при
любом нарушении. Cleanup выполняется через `trap` и не маскирует исходную ошибку.

## 8. Итоговая контрольная проверка

Перед повторной приёмкой выполнить в чистом checkout:

```bash
make setup LOCAL=1
make verify LOCAL=1
```

Затем провести живую демонстрацию:

1. Изменить `quantity > 0` на `quantity >= 0` во временной копии и показать,
   что mutation-check завершается ошибкой по ожидаемой причине.
2. Создать чистую БД и применить все миграции.
3. Создать данные на предыдущей схеме, обновить до `head` и подтвердить их
   сохранность.
4. Создать backup, повредить контрольные данные, восстановить их в отдельную БД
   и сравнить значения, связи, количество строк и Alembic revision.
5. Показать назначение, входы, артефакты и типичный отказ каждого шага verify.
6. Отправить PATCH с номером из пробелов и получить HTTP 422 в едином формате.
7. Показать, что после завершения не осталось локальных контейнеров и томов
   текущего запуска.

После публикации ветки обязательны успешный CI актуального commit SHA,
независимое одобрение и отдельная проверка изменений критических файлов.

## 9. Критерии готовности

Работа готова к повторной приёмке, только если одновременно выполнены условия:

- старый публичный параметр `TEST` удалён, `LOCAL=1` работает во всех командах;
- `make setup LOCAL=1` повторяемо проходит в чистом и уже настроенном окружении;
- `make verify LOCAL=1` полностью проходит локально в Docker;
- все инварианты поступления защищены приложением, БД и тестами;
- критические мутации уничтожаются без тайм-аутов и ложноположительных причин;
- миграции проходят на чистой и заполненной БД;
- backup/restore реально восстанавливает повреждённые данные;
- High/Critical находки и подтверждённые секреты блокируют контур;
- параллельные локальные запуски не разделяют контейнеры, сети, БД и тома;
- `GUIDE.md`, README и остальные инструкции согласованы с реализацией;
- ветка опубликована, CI актуального SHA успешен, PR/MR содержит перечень
  критических файлов и получено независимое одобрение;
- живая демонстрация проведена и её результат зафиксирован пользователем.

## 10. Вне объёма задания

В эту работу не входят очередь, outbox, worker, проведение поступлений, отчёты,
Nginx, production CD и мониторинг. Они выполняются отдельными задачами после
